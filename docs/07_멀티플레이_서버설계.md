# 멀티플레이 서버 설계

> 대상: 유저 로그 · 아이템 시스템 · 아이템 발견 · 거래 · 랭킹
> 상태: **설계만. 구현 없음.** 코드를 쓰기 전에 경계를 정하기 위한 문서다.

## 0. 지금 상태 — 서버에 저장되는 것은 아무것도 없다

| 대상 | 실태 |
|:--|:--|
| DB | 없음. sqlite/postgres/redis 흔적 자체가 없다 |
| 백엔드 | nginx 자리표시자. `/api/health` 만 200, 나머지 501 |
| `volume/` | 비어 있음 |
| 세이브 | 브라우저 `localStorage` (규칙표·프리셋·직전 판) |
| 사용자 식별 | 없음. 서버는 누가 접속했는지 모른다 |

시뮬레이션이 100% 브라우저에서 돈다. **서버 권위가 0이다.**
이 상태로 랭킹을 붙이면 점수를 위조하는 데 개발자 도구 하나면 된다.

## 1. 이 프로젝트가 가진 특별한 자산 — 결정론

TDD §1.1 이 결정론을 최우선에 둔 실질적 이유가 여기서 회수된다.

- 리플레이 = `(시드 + 규칙표 + 코어 버전)` 뿐이다. 수 KB (TDD §9)
- TS 코어와 Python 코어가 **비트 단위로 같다**. 게이트 G3 에서 25케이스 · 로그 4,805행을
  필드 단위로 대조해 확인했고, 오프셋 순서 하나를 뒤집는 반증 시험으로 그 대조가
  공허하지 않음을 증명했다

그래서 **서버는 점수를 받지 않는다. 받아서 다시 계산한다.**

```
클라이언트  →  (seed, ruleset, core_version) 제출        수 KB
서버        →  Python 코어로 재시뮬레이션 (런당 약 94ms)
            →  결과를 서버가 확정. 클라이언트의 주장은 저장하지 않는다
```

대부분의 게임은 이 성질이 없어 서버 권위형으로 다시 짓는다. 여기서는 이미 있다.
**TDD §1.2 가 "버릴 코드" 로 규정했던 Python 코어가 검증 서버로 살아남는다.**

## 2. 서버 권위 경계 — 무엇을 믿고 무엇을 안 믿는가

| 대상 | 누가 정하는가 | 근거 |
|:--|:--|:--|
| 시드 | **서버가 발급** | 클라이언트가 정하면 유리한 시드만 골라 제출한다 |
| 규칙표 | 클라이언트 (서버가 검증) | 플레이어의 창작물. 검증기가 슬롯·CPU·미해금 블록을 본다 |
| 전투 결과 | **서버가 재시뮬레이션** | 클라이언트가 보낸 결과는 저장조차 하지 않는다 |
| 아이템 획득 | **서버가 재현해 검증** | §4 참조 |
| 소유권 이전(거래) | **서버 단독** | 재현으로 검증할 수 없는 유일한 축 |
| 해금·도감 | 서버 (검증된 런의 부산물) | 런이 검증되면 해금도 따라 확정된다 |

**핵심 원칙: 재현할 수 있는 것은 검증하고, 재현할 수 없는 것만 서버가 단독으로 정한다.**

## 3. 최소 스키마

정규화보다 **감사 가능성**을 우선한다. 결정론이 있으므로 결과가 아니라 입력을 저장하면
언제든 다시 계산해 대조할 수 있다.

```
account(id, handle, created_at, ...)              계정
meta_save(account_id, unlocked_blocks[], slot_cap,     메타 세이브 (사망해도 유지)
          bestiary[], presets[8], updated_at)          지금 localStorage 에 있는 것

run_ticket(id, account_id, seed, floor, mode,          서버가 발급한 시드
           issued_at, expires_at)                      이것 없이는 제출을 받지 않는다
run_submission(id, ticket_id, ruleset_json,            클라이언트 제출 (입력만)
               core_version, submitted_at)
run_result(submission_id, outcome, ticks, player_hp,   서버 재시뮬 결과
           cleared_rooms, verified_at, verdict)        verdict: verified | mismatch | rejected

item_instance(id, owner_account_id, origin_run_id,     아이템 (§4)
              floor, node_id, roll_index,
              affixes_json, created_at)
trade(id, from_account, to_account, item_id,           거래 원장 (append-only)
      offered_at, settled_at, state)

leaderboard(mode, core_version, account_id,            랭킹 (버전별로 분리)
            score, run_result_id, rank_at)
```

**`run_submission` 에 결과 컬럼이 없는 것이 의도다.** 클라이언트가 보낸 결과를 저장할
자리를 아예 두지 않아야, 나중에 누가 "빠르니까 그냥 믿자" 는 지름길을 못 낸다.

## 4. 아이템 — 결정론 안에 넣어야 한다

GDD §6 의 아이템은 스탯 접사 / 모듈 접사 / 저주 접사 세 축이다.
아이템을 **서버가 발급하면 결정론이 깨지고, 클라이언트가 만들면 위조된다.**

해법: **아이템도 시드에서 파생시킨다.**

```
아이템 = f(run_seed, floor, node_id, roll_index)
```

`DeterministicRng.create_stream("floor:2/node:5/loot")` 가 이미 그 형태를 지원한다
(TDD §7.3 의 서브 시드). 그러면:

- 클라이언트가 아이템을 만들어 보내도 서버가 같은 자리를 재현해 **거짓을 잡는다**
- 저장하는 것은 아이템의 스탯이 아니라 **획득 경로**(런 id, 층, 노드, roll_index) 다
- `affixes_json` 은 조회 편의를 위한 캐시일 뿐이며, 진위는 언제나 재현으로 판정한다

**미결:** 아이템 파생을 코어에 넣으면 골든 리플레이가 아이템까지 포함해야 한다.
지금 골든은 전투 로그만 대조한다. Phase 4 아이템 시스템을 설계할 때 함께 정해야 한다.

## 5. 거래 — 재현으로 풀리지 않는 유일한 축

아이템의 **진위**는 §4 로 검증되지만 **소유권**은 재현할 수 없다. 서버가 단독으로 정한다.

- 원장은 append-only. 소유권은 원장을 접어서 계산한다(현재 소유자 컬럼은 캐시)
- 거래는 2단계(제안 → 확정)로 두고 확정만 원장에 남긴다
- **경제 설계가 선행되어야 한다** — 봇 파밍, 인플레이션, 계정 간 자전거래.
  이것은 기술 문제가 아니라 기획 문제이고, GDD 에 아직 없다

## 6. 코어 버전과 랭킹

TDD §9: "코어 버전이 바뀌면 기존 리플레이는 구버전 배지 표시 후 **검증 대상에서 제외**한다."

- **랭킹은 `core_version` 별로 갈라야 한다.** 밸런스를 고치면 과거 기록은 재현되지 않는다
- 이미 겪은 사례: 쿨타임 배선 하나로 `spring_camp` 승률이 47% → 0% 로 바뀌었다
- 시즌 개념으로 쓰면 자연스럽다 — 코어 버전이 곧 시즌이다

## 7. 도입 순서

앞 단계 없이 뒷 단계를 하면 되돌려야 한다.

| 순서 | 내용 | 없으면 생기는 일 |
|:-:|:--|:--|
| 1 | **시드 서버 발급** | 유리한 시드만 골라 제출. 나중에 고치면 기존 기록 전부 무효 |
| 2 | 계정 + 메타 세이브 서버 이전 | 기기 바꾸면 사라짐. 랭킹에 붙일 주체가 없음 |
| 3 | 재시뮬 검증 파이프라인 | 점수를 믿게 됨 |
| 4 | 랭킹 · 데일리 챌린지 | — |
| 5 | 아이템 파생 결정론화 | 아이템이 위조 가능해짐 |
| 6 | 거래 원장 + 경제 설계 | — |

**1번이 가장 싸고 가장 되돌리기 어렵다.** 지금 고치면 한 줄이고, 랭킹이 생긴 뒤에 고치면
그때까지의 기록이 전부 무효가 된다.

## 8. 규모 감각

- 검증 1건 = 런당 약 94ms (헤드리스 실측, TDD §11 목표 300ms 대비 여유)
- 4코어 기준 **초당 약 40건**, 하루 300만 건. 데일리 챌린지 규모로는 충분하다
- 다만 아이템·거래가 붙으면 상시 트래픽이 생겨 **지금의 "정적 파일만 주는" 구조가 끝난다.**
  현재 용량 계산(사용자당 오리진 1.2KB, 플레이 중 서버 트래픽 0)은 그 시점에 무효가 된다
