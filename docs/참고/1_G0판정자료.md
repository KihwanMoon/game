# G0 판정 자료 — Phase 0 산출물

> **게이트 G0:** 규칙표 예시 3개를 손으로 써서 "이 규칙이면 이 방을 클리어한다"가
> 종이 위에서 성립하는가?
>
> 판정은 이 문서를 읽고 사람이 한다. 로드맵 §10 — 게이트 판정은 혼자 하지 않는다.

## 규칙표 예시 3개

제약은 슬롯 5, CPU 예산 8, 비용 1항=1 / 2항=2 / 3항=4 다. 전부 거짓이면 DEFAULT
행동(가장 가까운 적에게 접근)이 나간다(TDD §5.2).

### A. 근접 압박 — `open_field` (슬롯 4 / CPU 6)

```
[1] HP% < 25  AND  포션 > 0                  → 포션 사용                cpu 2
[2] 적거리 <= 1  AND  쿨타임[SKILL_1] 완료    → SKILL_1 @가장가까운적    cpu 2
[3] 적거리 <= 1                              → 기본공격 @가장가까운적    cpu 1
[4] 방 체류 틱 > 35                          → 문/계단으로 이동          cpu 1
                                     (전부 거짓) → 가장 가까운 적에게 접근
```

**종이 위 추적:** 개활지는 엄폐가 없어 포위가 성립한다. 접근 → 인접 → 강타/기본공격
순환으로 돌격병(hp 40)을 4틱에 하나씩 지운다. [4]가 추격자 스폰(당시 40틱, W6 실측 후
20틱 — docs/참고/2_전략공간실측)보다 앞서 있어
장기전이 되면 방을 뜬다. **성립한다.**

**약점:** 소환사를 따로 노리지 않으므로 잡몹이 계속 는다. `spring_bait` 처럼
소환사가 있는 방에서는 [4]가 먼저 뜨는 방식으로 도망칠 뿐 이기지는 못한다.

### B. 카이팅 — `corridor` (슬롯 4 / CPU 7)

```
[1] HP% < 30  AND  포션 > 0                   → 포션 사용                cpu 2
[2] 적거리 <= 1                               → 후퇴 @가장가까운적  SET FLAG_A=true   cpu 1
[3] FLAG_A  AND  쿨타임[SKILL_2] 완료          → 사격 @가장가까운적  SET FLAG_A=false  cpu 2
[4] 적거리 <= 4  AND  쿨타임[SKILL_2] 완료     → 사격 @가장가까운적       cpu 2
```

**종이 위 추적:** GDD §3.5 가 예시로 든 구조 그대로다. 통로 방에서 좁은 목으로
물러나면 근접 적이 한 번에 하나만 붙으므로 [2]→[3] 순환이 성립한다. **성립한다.**

**전제:** 플레이어에게 원거리 수단이 있어야 한다. 아래 F-4 참조.

### C. 엄폐 우선 — `pillars` (슬롯 5 / CPU 7)

```
[1] HP% < 30  AND  포션 > 0                       → 포션 사용             cpu 2
[2] 위험 예고 타일 위                              → 엄폐물 뒤로 이동       cpu 1
[3] LOS 노출  AND  적유형존재[RANGED]              → 엄폐물 뒤로 이동       cpu 2
[4] 적거리 <= 1                                    → 기본공격 @가장가까운적  cpu 1
[5] 쿨타임[SKILL_2] 완료                           → 사격 @소환사 유형      cpu 1
```

**종이 위 추적:** 기둥 방에서 [3]이 궁수의 LOS 를 끊고, [5]가 소환사를 먼저 지운다.
[2]가 예고 타일 회피를 맡는다. **성립한다.**

**약점:** [5]에 사거리 조건이 없어 소환사가 4칸 밖이면 헛친다. 아래 F-1 과 같은
문제다 — 조건이 "그 셀렉터가 고를 대상"의 거리를 물을 수 없다.

**세 규칙표가 서로 다른 행동으로 갈린다**(강타 / 후퇴 / 엄폐 이동). GDD §11 의
"단일 정답 수렴 여부" 지표를 볼 최소 조건은 갖췄다.

## 판정 전에 정해야 하는 것 6가지

규칙표를 실제로 써 보면서 나온 것이다. 블록 목록은 "이후 변경 금지"이므로 **동결을
확정하기 전에** 정하는 편이 싸다.

### F-1. 조건이 참조하는 "대상"이 정의되지 않았다 ★ 가장 중요

인지 변수에 `대상 HP%`·`대상이 시전 중인가` 가 있는데, **대상은 행동의 TARGET
셀렉터가 고른다.** 조건은 행동보다 먼저 평가되므로, 조건 평가 시점에 "대상"이
무엇인지 정의가 없다.

예시 C의 `[5] 쿨타임 완료 → 사격 @소환사` 가 이 문제에 걸린다. 소환사가 사거리
밖이어도 규칙이 발동해 틱을 버린다. `적거리` 는 *가장 가까운* 적까지의 거리일 뿐
소환사까지의 거리가 아니다.

선택지:
- (a) 규칙마다 TARGET 을 먼저 확정하고, 조건의 "대상"은 그것을 가리킨다.
- (b) `대상` 계열 인지에 셀렉터 인자를 준다 — `대상거리[TYPE_SUMMONER] <= 4`.
- (c) 그대로 두고 헛치는 것을 플레이어 책임으로 둔다.

(a)가 자연스럽지만 RuleVM 의 평가 순서가 바뀐다. **W2 전에 정해야 한다.**

### F-2. 조건 우변이 리터럴뿐인가

TDD §3.3 의 예시는 `{"rhs": 20}` 처럼 숫자만 보여준다. 그런데 디자인 시트의 규칙 행은
`적거리(2) <= 사거리(3)` 로 **스탯을 우변에** 둔다.

리터럴만 허용하면 사거리가 장비로 바뀔 때 `적거리 <= 1` 이라고 적어 둔 규칙이
조용히 틀린다 — 모듈로 사거리를 늘려도 규칙이 그것을 모른다. 아이템이 "로직 표현력을
확장"하는 축(GDD §6.2)이라는 설계와 어긋난다.

### F-3. 회복타일이 있는지 물을 방법이 없다

행동에 `회복타일로 이동` 이 있는데, 인지에는 `내 위치가 회복타일인가`(이미 위에
있는지)뿐이다. **회복타일이 방에 있는지, 얼마나 먼지 물을 블록이 없다.**

디자인의 규칙 행 상태 시트가 `회복타일(없음) != null → 회복타일로 이동` 을 예시로
쓰고 있어, 디자인은 이 블록이 있다고 전제한다. 인지 18개 동결과 정면으로 충돌한다.

선택지: `가장 가까운 문/계단 거리` 를 `가장 가까운 목표 거리[문|계단|회복타일]` 로
일반화하면 개수를 늘리지 않고 해결된다.

### F-4. 플레이어의 원거리 수단 — 이미 조정했음, 확인 필요

밸런스 초안에서 SKILL_1·SKILL_2 의 사거리를 둘 다 1로 뒀더니 **GDD §3.5 가 대표
예시로 든 카이팅이 성립 불가**였다. 그 예시가 `쿨타임[사격]` 을 전제하기 때문이다.

SKILL_2 를 사거리 4 / 계수 110% / 쿨 2 의 "사격" 으로 바꿨다. 예시 B가 이것에 의존한다.
**이 조정이 의도와 맞는지 확인이 필요하다.**

### F-5. 이동이 4방향인가 8방향인가

`주변 8칸 중 이동 가능 칸 수(포위도)` 는 8칸을 세는데, 이동 자체가 4방향인지
8방향인지 어디에도 없다. 거리 정의(맨해튼/체비셰프)도 여기 딸려 온다 — `적거리 <= 1`
이 대각선 적을 포함하는지가 달라진다.

룸 도달성 검사는 4방향으로 했다. 4방향으로 닿으면 8방향으로도 닿으므로 더 엄격한
쪽이다. **W1 에서 확정해야 한다.**

### F-6. 인자를 받는 블록의 JSON 표현이 TDD 에 없다

`쿨타임[스킬]`·`플래그[A~D]`·`적유형존재[유형]` 은 인자를 받는데, TDD §3.3 의
term 형식에는 자리가 없다. 예시에서 `lhs_param` 을 임시로 더했다. **확정 전이다.**

### S-1 — SUMMON 을 행동에 넣은 이유

GDD §5 는 "몬스터도 플레이어와 완전히 동일한 DSL 로 기술한다" 를 몬스터 설계의 축으로
둔다. 그런데 소환만 `balance.json` 의 kind 속성이었고 엔진이 UPKEEP 에서 처리했다.
결과적으로 **도감이 소환 주기만 규칙표 밖에서 따로 보여줘야 하는 예외**가 생겼고,
그 예외 하나 때문에 "적의 논리를 읽고 카운터를 설계한다" 는 학습 경로가 끊겼다.

주기는 `쿨타임[SUMMON]` 이 맡는다. 새 인지 변수를 만들지 않고 기존 쿨타임 블록의 인자를
하나 늘린 것이라 인지 개수는 18 그대로다.

`ai_summoner` 는 `IF 쿨타임[SUMMON] 완료 AND 대상거리[NEAREST] <= 사거리 THEN SUMMON`
으로 적었다. 조건에 사거리 항을 함께 둔 것이 핵심이다 — 쿨타임만으로 두면 그 규칙이
매 틱 참이 되어 아래 규칙도 DEFAULT(접근)도 영영 평가되지 않고, 소환사가 제자리에
굳어 버린다. 규칙 순서가 결과를 가른다는 §11 의 관찰이 적 규칙표에도 그대로 적용된다.

### H-1~H-3 — 치유형을 DSL 로 다루기 위해 연 것

GDD §5 는 치유형을 "아군 HP% 낮으면 회복" 으로 정의하고, 그 존재 이유를 플레이어의
`TARGET LOWEST_HP` 판단에 **오류를 유발**하는 것이라고 적었다. W7 이 `mender_acolyte`
를 넣었지만 그 상호작용은 하나도 없었다 — 동결된 행동 13개에 아군 회복이 없고, 셀렉터
7개가 전부 `list_hostiles` 로 시작해 아군을 가리킬 수단 자체가 DSL 에 없었기 때문이다.
사제는 자기 포션을 마시는 것으로 근사돼 있었고, 그것은 치유형이 아니라 포션을 든
사격형이다.

동결을 여는 원칙은 **P3(제약이 재미다)를 먼저 지키는 것**이다. 블록이 늘면 조합 공간이
곱으로 커지고, 그 대부분이 뜻 없는 칸이면 플레이어가 고를 것이 늘어난 게 아니라 읽을
것만 늘어난다. 그래서 셋만 열었다.

#### H-1. 유형 인자에 HEALER

`enemy_type_present` 의 허용값 하나가 늘었다. 인지 변수 개수는 18 그대로이며, v3 이
`쿨타임[SUMMON]` 을 더한 것과 같은 방식이다. 이것이 없으면 `IF 적 유형 존재[HEALER]`
가 아예 적히지 않는다.

#### H-2. `TYPE_HEALER` 를 더한다 — `TYPE_*` 를 인자화하지 않는다

**버린 안:** 셀렉터 `TYPE_RANGED`·`TYPE_SUMMONER` 를 `TYPE[유형]` 하나로 합치기.
헤드라인 개수는 7 로 유지되지만 값이 없다. 지목할 수 있는 대상의 가짓수는 어느 쪽이든
같으므로 **조합 공간이 전혀 줄지 않는다.** 대신 값을 치른다 — 셀렉터는 지금 규칙표의
`target` 과 인지 변수 `대상 거리` 의 `lhs_param` 양쪽에서 **그냥 문자열**이다.
인자화하면 그 두 자리가 중첩 구조가 되어 규칙표 스키마·검증기·에디터·TS 코어가 모두
바뀐다. 개수를 줄이려고 표현을 복잡하게 만드는 것은 P3 를 지키는 게 아니라 P3 를
핑계로 삼는 것이다.

`TYPE_HEALER` 가 필요한 이유는 카운터다. 소환형에는 `TARGET TYPE_SUMMONER` 라는 답이
있고(GDD §5), 치유형의 같은 답이 "사제를 먼저 끊는다" 이다. 지목할 수 없으면 카운터가
규칙표에 적히지 않는다.

`MELEE`·`BOMBER` 에는 여전히 셀렉터가 없다. 그 둘은 `NEAREST` 로 충분히 잡히므로
지금은 열지 않는다 — 이 비대칭은 v3 에도 있던 것이고, 필요해지면 그때 근거를 남기고
연다.

#### H-3. 아군은 행동 `HEAL` + 셀렉터 `ALLY_WOUNDED` 하나로 연다

세 안을 놓고 골랐다.

**(b) 셀렉터에 진영 인자 — `LOWEST_HP[ALLY]` — 버렸다.** 진영을 셀렉터의 축으로 만들면
지목 가능한 뜻이 9 에서 18 로 두 배가 되는데, 늘어난 아홉 중 여덟이 뜻이 없다
(`시전 중인 아군`·`위협도가 가장 높은 아군`…). 문법이 만들어 낸 칸의 대부분을 검증기가
도로 막아야 한다면 그 축이 틀린 것이다. P3 가 여기서 가장 크게 깨진다.

**(c) `HEAL` 이 암묵적으로 아군 최저 HP 를 고른다 — 버렸다.** 셀렉터를 건드리지 않으니
싸 보이지만, 조건을 쓸 수 없다는 문제가 남는다. 회복할 아군이 있는지 물을 방법이 없으면
`쿨타임[HEAL] 완료 → HEAL` 은 쿨타임이 찬 매 틱 참이 되고, 회복할 대상이 없는 틱에는
행동이 실패해 쿨타임도 걸리지 않아 **그 규칙에 사제가 영구히 굳는다** — `ai_summoner`
가 이미 겪은 함정이다. 이것을 피하려면 `아군 최저 HP%` 라는 **19번째 인지 변수**를
새로 만들어야 하고, 그러면 GDD §8.2 가 요구하는 실측값 병기가 `아군 최저 HP%(40)` 처럼
**누구의 값인지 말하지 않는 로그**가 된다.

**(a) 채택 — 행동 `HEAL` 하나, 아군 셀렉터 하나.** 인지 변수는 하나도 늘지 않는다.
이미 있는 두 일반화가 아군까지 그대로 덮기 때문이다.

* `대상 HP%` 는 그 규칙의 TARGET 을 읽는다. TARGET 이 아군이면 아군의 HP% 다 —
  GDD §5 의 "아군 HP% 낮으면" 이 **그대로** 한 항이 된다.
* `대상 거리[ALLY_WOUNDED]` 는 F-1 의 일반화에서 공짜로 따라온다.

그리고 F-1 이 정한 "셀렉터가 아무도 못 고르면 그 규칙은 발동하지 않는다" 가 (c)의
굳음 문제를 구조적으로 없앤다. `ALLY_WOUNDED` 는 이름 그대로 **부상한** 아군만 후보로
두므로, 다칠 아군이 없으면 회복 규칙은 발동 자체를 하지 않고 다음 규칙으로 넘어간다.

자기 자신은 후보가 아니다. 자기 회복은 이미 `USE_POTION` 의 자리이고, 넣으면 아군이
없는 판에서도 `HEAL` 이 쿨타임짜리 무한 포션이 되어 플레이어 쪽 밸런스에 구멍이 난다.

**진영은 셀렉터의 속성으로 선언한다.** 셀렉터마다 `faction`, 대상을 받는 행동마다
`target_faction` 이 `blocks.json` 에 있고, 검증기가 어긋난 조합을 거부한다.

```
[1] HEAL 는 아군 셀렉터가 필요하다 — NEAREST 는 적대 셀렉터다
[1] ATTACK 는 적대 셀렉터가 필요하다 — ALLY_WOUNDED 는 아군 셀렉터다
```

막지 않으면 `HEAL @NEAREST` 가 적을 회복하고 `ATTACK @ALLY_WOUNDED` 가 아군을 때린다.
둘 다 문법으로는 만들어지므로, 검증기가 없으면 규칙표가 **조용히 반대로 돈다**.

#### 사제가 실제로 무엇을 하는가

`ai_mender` v2 는 적의 제약(CPU 4 / 슬롯 3)을 그대로 지키며 이렇게 적힌다.

```
[1] 대상거리[NEAREST] <= 2                                   → 후퇴 @가장가까운적      cpu 1
[2] 대상거리[ALLY_WOUNDED] <= 사거리 AND 쿨타임[HEAL] 완료    → 회복 @부상한아군        cpu 2
[3] 대상거리[NEAREST] <= 사거리                              → 기본공격 @가장가까운적  cpu 1
```

[2]의 두 항은 역할이 다르다. 거리 항이 없으면 사거리 밖 아군에게 헛돌며 쿨타임도 걸리지
않아 이 규칙에 굳고, 쿨타임 항이 없으면 매 틱 참이 되어 [3]도 DEFAULT 도 영영 평가되지
않는다. '부상했는가' 는 셀렉터가 답하므로 세 번째 항이 필요 없다 — CPU 4 안에 세 줄이
들어가는 이유가 그것이다.

포션은 뺐다. 네 번째 줄을 살 예산이 없어 `USE_POTION` 이 규칙표에서 빠졌고, 쓰지 않는
포션을 도감이 3 이라고 적으면 그 자체가 P1 을 깨는 거짓말이기 때문이다.

회복량은 대상 최대 HP 의 30%, 쿨타임 3틱, 사거리는 시전자의 `attack_range`(사제는 2)다.
플레이어 화력이 틱당 약 11 이므로 3틱당 12 의 회복은 앞선다 — **집중 사격이 흩어지는
것**이 손해의 본체이지 회복량이 아니다. 카운터는 둘이다: `TARGET TYPE_HEALER` 로 사제를
먼저 끊거나, 사거리 2 밖으로 상대를 떼어 놓는 것.

시야(LOS)는 묻지 않는다. 대상별 시야를 묻는 인지 변수가 DSL 에 없어서, 요구하면
조건이 참인데 영영 실패하는 규칙을 플레이어가 고칠 방법이 없어진다 (P1). 사거리는
`대상 거리[ALLY_WOUNDED]` 로 물을 수 있으므로 사정이 다르고, 그래서 사거리만 잰다.

#### 이식 중 드러난 것 (G3)

골든을 다시 만들자 `visible_enemy_count` 에서 두 코어가 갈렸다. 파이썬은 격자를 받지
않은 호출에서 이 키를 **만들지 않는데**(LOS 로 좁힌 값만 사실로 둔다) TypeScript 는
방 전체 적 수를 미리 깔고 있었다. 저장돼 있던 골든이 그 변경 이전 것이라 대조가 통과해
왔다. 파이썬이 정본이므로 TS 를 고쳤다 — 격자를 받은 호출에서도 `Map` 이 첫 삽입 자리를
지켜 키 순서가 어긋나던 문제까지 같이 사라진다.

### P-1~P-2 — 층이 올라가면 무엇이 달라지는가

`balance.json` 에 `floor_scale`(HP +25%/층 · 공격력 +20%/층)이 적혀 있었지만 그 절을
읽는 코드가 저장소에 없었다. 층을 내려가도 적이 그대로였다는 뜻이고, 그러면 "층"은
이름만 있고 압력이 없는 축이 된다. 같은 결에서 적 8종 중 다섯(`bomb_slime` ·
`mender_acolyte` · `veteran_rusher` · `longbow_archer` · `arch_summoner`)이 어느 룸
템플릿의 `enemy_spawns` 에도 없었다 — 정의와 규칙표와 도감은 있는데 플레이에 나오지
않는 적이었다. 둘은 같은 문제의 두 면이라 함께 다뤘다.

#### P-1. 층 깊이 스케일 — 어디서 곱하고, 체류 스케일과 어떻게 합성하는가

**적용 지점은 개체를 만드는 자리다.** 방 배치(`run_battle.build_engine`) · 소환물
(`abilities.create_minion`) · 추격자(`pressure.create_hunter`) 셋이며, 전부
`scaling.get_scaled_enemy_stats` 하나를 거친다. 피해 계산 시점에 곱하지 않은 이유는
최대 HP 때문이다 — HP 는 매 틱 다시 계산할 수 있는 값이 아니라 개체가 태어날 때
정해지는 값이고, 두 값을 다른 시점에 곱하면 "HP 는 층 3 인데 공격력은 층 1" 같은 상태가
생긴다. 한 자리라도 빠뜨리면 같은 층에 서로 다른 기준의 적이 섞이므로, 골든에 세 경로를
각각 태우는 케이스를 넣었다(`open_field`·`pillars`·`spring_bait` 층 3).

**보너스는 `pct * (층 - 1)` 이다.** 층 1 에서 아무것도 곱하지 않아야 `balance.json` 의
값이 "층 1 의 그 적" 이라는 뜻을 그대로 갖는다. 전부 정수 퍼센트 내림 나눗셈이다 (R5).

**층 체류 스케일(`pressure.py`)과는 다른 축이고, 둘은 곱한다.** 세는 것이 다르다 —
이쪽은 "몇 층까지 내려왔는가"(공간, 생성 시 1회), 저쪽은 "이 층에서 몇 틱을
끌었는가"(시간, 매 틱 재계산)다. 합이 아니라 곱으로 정한 근거는 이렇다.

> 체류 압력이 값 매기는 것은 **시간을 끄는 대가**다. 그 대가는 "지금 이 적이 가진 힘의
> 몇 %" 여야 한다. 더하기로 두면 +1%p 가 층 1 에서나 층 5 에서나 같은 절대량이 되어,
> 정작 시간을 끌고 싶어지는 깊은 층에서 압력이 희석된다 — GDD §7 이 막으려던 방향과
> 정반대다.

구현상으로도 곱이 자연스럽다. `PressureTracker` 는 첫 적용 때의 공격력을
`base_attacks` 에 기준으로 잡아 두는데, 그 값이 이미 층 깊이로 스케일된 값이므로
`pressure.py` 를 한 줄도 고치지 않고 합성이 성립한다. 이것은 근거가 아니라 확인이다.

**버린 안: 피해 공식에 층 항을 하나 더 넣기.** `damage_formula` 는 이미
`soft_cap_per_floor` 로 층을 본다(방어 감쇠). 거기에 공격력 배수까지 넣으면 한 수식이
층을 두 번 읽게 되어, 밸런스를 만질 때 어느 항이 얼마를 냈는지 분해할 수 없다.
최대 HP 는 그 수식에 자리도 없다.

#### 이중 적용은 없었다 — 확인한 것

`balance.json` 의 주석은 새 5종을 "층 2~3 을 상정한 값" 이라 적어 두었고, 그대로면
스케일이 두 번 곱해지므로 층 1 기준으로 되돌려야 했다. 되돌려 보니 앞뒤가 맞지 않았다.

| 정예 | 원본 | 실제 비율 | 층 3 스케일(HP 1.5 · 공격 1.4)로 되돌리면 |
|:--|:--|:--|:--|
| `veteran_rusher` 70/13 | `goblin_rusher` 40/8 | HP 1.75배 | 46/9 — 성립 |
| `longbow_archer` 34/14 | `goblin_archer` 26/10 | HP 1.31배 | 22/10 — **원본보다 약하다** |
| `arch_summoner` 55/7 | `goblin_summoner` 34/5 | HP 1.62배 | 36/5 — **공격력이 같아진다** |

세 쌍의 비율이 서로 다르고 1.5 근처에 모이지도 않는다. 이 값들은 같은 층의 원본과
나란히 놓고 손으로 잡은 것이지 스케일이 곱해진 값이 아니다. 되돌리면 "정예가 원본보다
약하다" 는 모순이 생기므로 **되돌리지 않았다**. 대신 주석이 들고 있던 "층 2~3" 이라는
정보를 데이터로 옮겼다 — 그것이 P-2 다.

#### P-2. 난이도 곡선은 적 스탯이 아니라 `min_floor` 가 만든다

룸 템플릿에 `min_floor`(기본 1)를 더하고 `build_floor.list_floor_templates` 가 그 값으로
후보를 거른다. 어느 적을 만나는가는 **어느 방이 나오는가**로 정해지고, 같은 방을 층 3
에서 다시 만나면 P-1 이 그 적을 세게 만든다. 두 장치가 겹치지 않고 각자 한 가지만
책임진다.

거르지 않으면 층 배치가 템플릿을 균등하게 뽑으므로 층 1 첫 방에서 대소환사를 만난다.
"첫 방은 배울 수 있어야 한다" 가 무너지고, 그것은 규칙 설계 실패와 구분되지 않는다 (P1).

방 다섯을 새로 그렸다. 전부 12x9 이고 도달성 검사를 통과한다.

| 방 | `min_floor` | 적 | 가르치는 것 |
|:--|:-:|:--|:--|
| `blast_yard` | 1 | 폭탄 슬라임 ×2 | 예고 타일에서 비켜서기. 가운데 덩어리가 물러설 방향을 두 갈래로 가른다 |
| `chapel` | 2 | 수복 사제 + 돌격병 ×2 | 사제를 먼저 끊거나 사거리 2 밖으로 떼어 놓기 |
| `longshot` | 2 | 장궁병 + 돌격병 | 사거리 5 > 사격 4. 엄폐 기둥을 타고 붙기 |
| `warlord_gate` | 2 | 정예 돌격병 + 궁수 | 틈 하나로 유인해 1:1 만들기 |
| `summoner_vault` | 3 | 대소환사 | 궁수가 늘기 전에 소환사를 끊기 |

`bomb_slime` 만 층 1 에 둔 것은 그 적이 예고(TELEGRAPH)의 유일한 사용처이기 때문이다.
예고를 한 번도 못 본 채 층 2 에 내려가면 `위험 예고 타일 위에 있는가` 블록이 플레이어
에게 영영 죽은 블록이 된다. HP 22 · 근접 공격 4 로 위협이 자폭 하나뿐이라 첫 방으로
안전하다.

#### 실측 — 실제로 도는가

벤치마크 규칙표 11종 × 시드 10개(= 110판)를 방마다 돌렸다. 보상 없는 기본 스탯이다.

| 방 | 층 | 승 | 이기는 규칙표 |
|:--|:-:|:-:|:--|
| `blast_yard` | 1 | 100/110 | `sniper` 만 진다 |
| `chapel` | 2 | 58/110 | 광역·문지키기·최저HP·위협·카이팅·샘점거 |
| `warlord_gate` | 2 | 30/110 | 문지키기·최저HP·카이팅 |
| `longshot` | 2 | 20/110 | 최저HP·위협 |
| `summoner_vault` | 3 | 30/110 | 광역·문지키기·샘점거 |

비교를 위한 기존 방: `open_field` 80 · `hazard_field` 65 · `corridor` 30 · `pillars` 30 ·
`spring_bait` 7. 새 방들이 기존 폭 안에 들어오고, 층이 깊어질수록 어려워진다.

층 단위로도 확인했다. `g0_kite` 로 시작~보스까지(`run_room_loop`) 시드 30개를 돌린 결과다.

| 층 | 층 클리어 | 그 층에 나온 방 |
|:-:|:-:|:-:|
| 1 | 17/30 | 6개 |
| 2 | 9/30 | 9개 |
| 3 | 3/30 | 10개 전부 |

두 축이 함께 일한 결과다 — 층이 깊어질수록 후보 방이 늘어(P-2) 어려운 방을 만날 확률이
오르고, 같은 방을 만나도 적이 세다(P-1).

**단위 테스트가 아니라 전투 로그로 확인한 것 둘.**

```
T006 | bomb_slime_0  [1] 내 쿨타임[스킬] 완료[AREA_ATTACK](참) == 참 AND 대상 거리[NEAREST](1) <= 사거리(1) → AREA_ATTACK
T006 | bomb_slime_0  [1] AREA_ATTACK → 예고 4칸 — 2틱 뒤 발동
T007 | player        [3] ATTACK @bomb_slime_0 → bomb_slime_0 HP 0/22 사망 (-12)
T008 | bomb_slime_0      AREA_ATTACK 예고 취소 → 시전자 사망
```

자폭형이 예고를 걸고, `cancel_on_death` 가 "사거리 밖에서 먼저 죽인다" 는 두 번째 답을
살린다 (`blast_yard` · `g0_pressure` · 시드 1). 예고를 읽는 규칙표는 같은 방에서
`위험 예고 타일 위에 있는가(참) == 참 → MOVE_TO_COVER` 로 무피해로 넘긴다.

```
T004 | mender_acolyte_0 [2] 대상 거리[ALLY_WOUNDED](2) <= 사거리(2) AND 내 쿨타임[스킬] 완료[HEAL](참) == 참 → HEAL @goblin_rusher_2
T004 | mender_acolyte_0 [2] HEAL @goblin_rusher_2 → goblin_rusher_2 HP 48/50 (+15)
```

치유형이 규칙표로 아군을 회복한다 (`chapel` · `focus_threat` · 시드 31337 · 층 2).
`50` 과 `+15` 가 층 스케일의 실측이다 — 돌격병의 최대 HP 40 이 층 2 에서 50 이 되고,
회복량 30% 가 12 에서 15 로 함께 오른다.

#### 남은 결함 — `arch_summoner` 는 지금 균형이 맞지 않는다

`summoner_vault` 를 그리는 동안 드러났다. 대소환사는 **어느 층 · 어느 지형에서도**
의도한 카운터(`focus_summoner` = `TARGET TYPE_SUMMONER` 우선 처리)로 이길 수 없다.
층 1 에서 단독으로 두어도 11종 × 10시드가 전부 패배다. 원인은 소환물이 원거리라는 것
이다 — 궁수 4마리가 사거리 4 에서 틱당 40 을 내는데 플레이어의 화력으로는 그 안에
소환사에게 닿지 못한다. `max_alive` 를 2 로 낮춰도, 엄폐를 깔아도, 막다른 곳에 몰아도
결과가 같았다.

지금 `summoner_vault` 가 30/110 인 것은 **플레이어가 소환사 코앞(거리 2)에서 시작하도록
배치했기 때문**이다. 방 설계로 증상을 덮은 것이지 균형을 맞춘 것이 아니며, 이기는
셋(`area_sweep`·`door_hold`·`spring_camp`)도 의도한 카운터가 아니다. 이 값을 고치려면
승률 재측정이 필요하고 그것은 docs/참고/2_전략공간실측 갱신과 함께 다뤄야 한다 — 이번 과업 범위 밖이라
남긴다. 기존 골든 `pillars__g0_cover__555`(대소환사를 덧붙인 층 1 케이스)가 이미
`PLAYER_LOSS` 인 것으로 보아 v4 이전부터 있던 결함이다.

### F-2 — 조건 우변에 스탯을 허용한 이유

리터럴만 허용하면 `적거리 <= 1` 로 박아 둔 규칙이 모듈로 사거리를 늘린 뒤에도 1 을
본다. 아이템이 로직 표현력을 확장하는 축(GDD §6.2)이라는 설계와 정면으로 어긋난다.

JSON 표현은 `{"rhs": {"stat": "attack_range"}}` 다. 객체 한 겹으로 감싼 이유는 언어
중립성이다 — Phase 3 의 TypeScript 코어가 `typeof rhs === "object"` 만으로 분기할 수
있고, 문자열 우변으로 뒀을 때와 달리 뒷날 문자열 리터럴을 더해도 뜻이 겹치지 않는다.

허용 스탯은 `blocks.json` 의 `rhs_stats` 에 닫힌 목록으로 둔다 — `attack_range`,
`attack`, `defense`, `hp_max`, `cpu_budget`, `potions` 여섯이며 검증기가 그 밖의 이름을
거부한다. 열어 두면 오타 난 스탯이 조용히 거짓이 되어 규칙이 영영 발동하지 않는다.

로그는 GDD §8.2 가 요구하는 형태로 양변에 실측값을 병기한다.

```
T008 | [2] 내 쿨타임[스킬] 완료[SUMMON](참) == 참 AND 대상 거리[NEAREST](3) <= 사거리(3) → SUMMON
```

기존 규칙표 JSON 은 손대지 않아도 그대로 돈다. 리터럴 우변은 v2 와 같은 경로를 탄다.

## 실측 — 규칙표가 결과를 바꾸는가

셋 다 폴백(단순 접근·공격)을 이기고, 낭비 틱이 0이다. 결과 프로파일이 서로 다르다.

| 규칙표 | 방 | 결과 | 폴백 |
|:--|:--|:--|:--|
| `g0_pressure` | open_field | WIN 15틱 HP 52 | LOSS 17틱 |
| `g0_kite` | corridor | WIN 14틱 HP 62 | LOSS 54틱 |
| `g0_cover` | pillars | WIN 20틱 HP 51 | WIN 20틱 HP 23 |

GDD §0 의 주축(퍼즐형 — 성장은 로직 설계 실력으로)이 성립한다는 첫 증거다.

> **Phase 2 W6 통합 후 재측정 (같은 시드 12345).** 위 표는 W1 시점 값이며 그대로
> 둔다 — 판정 기록이기 때문이다. 통합 이후 값은 아래와 같다.
>
> | 규칙표 | 방 | 결과 | 폴백 |
> |:--|:--|:--|:--|
> | `g0_pressure` | open_field | WIN 11틱 HP 51 | WIN 13틱 HP 30 |
> | `g0_kite` | corridor | WIN 14틱 HP 82 | LOSS 34틱 |
> | `g0_cover` | pillars | **LOSS 37틱** | LOSS 22틱 |
>
> `g0_cover` 가 뒤집힌 것은 종이 위 추적(위 C절)이 틀렸기 때문이 아니라, 그 추적이
> 전제한 "[3]이 궁수의 LOS 를 끊고 [5]가 소환사를 지운다"에서 **[3]이 [5]를 굶긴다**
> 는 순서 문제를 놓쳤기 때문이다. LOS 가 실제로 도는 지금 [3]의 조건이 거의 매 틱
> 참이라 [5]까지 평가가 내려가지 않는다. 상세는 docs/참고/2_전략공간실측 의 `g0_cover` 절에 있다.
