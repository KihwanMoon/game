# 저장과 멀티플레이 설계

> 대상: 개인별 아이템 상태 · 획득 정보 · 행동 로직 · 성장 · 거래 · 랭킹 — **전부 저장한다.**
> 상태: **설계만. 구현 없음.** 코드를 쓰기 전에 경계와 순서를 정하기 위한 문서다.

## 0. 지금 저장되는 것과 안 되는 것

**서버에는 아무것도 없다.** DB 흔적 자체가 없고, 백엔드는 `/api/health` 만 200 을 주는
nginx 자리표시자이며, `volume/` 은 비어 있다.

브라우저 `localStorage` 키 하나(`game.rule-editor`)에 이것만 들어간다:

```ts
EditorSave { ruleset, presets, roomId, seed, lastResult }
```

| 항목 | 상태 | 막고 있는 것 |
|:--|:--|:--|
| 행동 로직(규칙표)·프리셋 | **저장됨** | — |
| 해금·도감·최고 층 | **안 붙음** | 스키마(`game/schemas/meta_save.py`)와 서비스
(`manage_meta.py`·`record_bestiary.py`)가 이미 있는데 **호출하는 쪽이 하나도 없다.** TS 포팅 + 런 배선만 하면 된다 |
| 아이템 상태·획득 정보 | **시스템이 없음** | 접사 코드가 한 줄도 없다. 저장 이전 문제다 (Phase 4 W15) |
| 성장(레벨) | **기획에 없음** | §5 참조 — 넣는 방식이 설계 원칙과 충돌할 수 있다 |
| 기기 간 이어하기 | 불가 | 계정·서버 |
| 랭킹·거래 | 불가 | 공용 저장소 + 서버 권위 |

**죽으면 정말 아무것도 안 남는다.** GDD §2.3 의 핵심 설계 —
*"도감으로 적의 AI 규칙이 공개되므로 실패한 런조차 자산을 남긴다"* — 가 아직 성립하지 않는다.

## 1. 이 프로젝트가 가진 자산 — 결정론

- 리플레이 = `(시드 + 규칙표 + 코어 버전)` 뿐이다. 수 KB (TDD §1.1, §9)
- TS 코어와 Python 코어가 **비트 단위로 같다.** 게이트 G3 에서 25케이스 · 로그 4,805행을
  필드 단위로 대조했고, 오프셋 순서 하나를 뒤집는 반증 시험으로 그 대조가 공허하지 않음을
  확인했다

그래서 **서버는 결과를 받지 않는다. 받아서 다시 계산한다.**

```
클라이언트 → (seed, ruleset, core_version) 제출        수 KB
서버      → Python 코어로 재시뮬 (런당 약 94ms)
          → 결과를 서버가 확정. 클라이언트의 주장은 저장하지 않는다
```

대부분의 게임은 이 성질이 없어 서버 권위형으로 다시 짓는다. 여기서는 이미 있다.
**TDD §1.2 가 "버릴 코드" 로 규정했던 Python 코어가 검증 서버로 살아남는다.**

## 2. 저장 계층 세 단계

전부 서버에 두면 오프라인에서 아무것도 못 하고, 전부 로컬에 두면 위조가 열린다.
**항목마다 어느 계층인지 먼저 정한다.**

| 계층 | 어디 | 무엇 | 성질 |
|:--|:--|:--|:--|
| **L1 기기 로컬** | `localStorage` | 편집 중인 규칙표, UI 설정, 오프라인 캐시 | 즉시·무료. 기기 종속·위조 자유 |
| **L2 계정 소유** | 서버 DB | 메타 프로그레션, 아이템, 성장, 도감 | 기기를 넘는다. 서버가 쓰기를 통제 |
| **L3 공용 원장** | 서버 DB (append-only) | 거래, 랭킹 제출·검증 결과 | 되돌릴 수 없다. 감사 대상 |

**L1 은 L2 의 캐시로만 쓴다.** L1 을 정본으로 두면 나중에 L2 로 올릴 때 그때까지 쌓인
것을 신뢰할 수 없다 — §9 가 이 문제를 다룬다.

## 3. 항목별 배치

| 항목 | 계층 | 검증 방법 | 비고 |
|:--|:--|:--|:--|
| 편집 중 규칙표 | L1 | — | 저장 실패가 편집을 막지 않는다 |
| 프리셋 8슬롯 | L1 → L2 | 검증기(슬롯·CPU·미해금 블록) | 공유 코드는 지금도 왕복한다 |
| 블록 해금 | L2 | 검증된 런의 부산물 | 런이 검증되면 해금도 확정 |
| 규칙 슬롯 상한 | L2 | 최고 층 기록에서 파생 | GDD §2.3 — 층 도달에 따라 +1, 최대 +4 |
| 몬스터 도감 | L2 | 검증된 런에서 조우·처치 기록 | **적의 규칙표를 그대로 보여준다** |
| 최고 층 | L2 | 재시뮬로 확정 | |
| **아이템 인스턴스** | L2 | **획득 경로 재현** (§4) | 스탯이 아니라 경로를 저장한다 |
| **아이템 획득 정보** | L2/L3 | 같음 | 언제·어느 런·어느 노드에서 |
| **성장** | L2 | 검증된 런의 부산물 | §5 — 무엇이 오르는가가 먼저 |
| **거래** | **L3** | 서버 단독 | 재현으로 풀리지 않는 유일한 축 |
| **랭킹** | **L3** | 서버 재시뮬 | 코어 버전별로 분리 (§7) |

## 4. 아이템 — 결정론 안에 넣는다

> 분류·슬롯·인벤토리·사용 제한은 `docs/09_아이템_시스템_설계.md` 가 다룬다.
> 여기서는 **저장과 검증**만 본다.

GDD §6 의 아이템은 스탯 접사 / 모듈 접사 / 저주 접사 세 축이다.
**서버가 발급하면 결정론이 깨지고, 클라이언트가 만들면 위조된다.**

해법: **아이템도 시드에서 파생시킨다.**

```
아이템 = f(run_seed, floor, node_id, roll_index)
```

`DeterministicRng.create_stream("floor:2/node:5/loot")` 가 이미 그 형태를 지원한다
(TDD §7.3 의 서브 시드). 그러면:

- 클라이언트가 아이템을 만들어 보내도 서버가 같은 자리를 재현해 **거짓을 잡는다**
- 저장하는 것은 아이템의 스탯이 아니라 **획득 경로**다
- `affixes_json` 은 조회 편의를 위한 캐시일 뿐이며, 진위는 언제나 재현으로 판정한다

**지금 정해야 하는 이유**: 아이템 도입 후에 파생 방식을 바꾸면 그때까지 나온 아이템이
전부 무효가 된다. 거래가 얹혀 있으면 되돌릴 수 없다.

**미결**: 아이템 파생을 코어에 넣으면 골든 리플레이가 아이템까지 포함해야 한다.
지금 골든은 전투 로그만 대조한다. Phase 4 W15 설계 시 함께 정한다.

## 5. 성장 — "레벨" 을 넣기 전에 정할 것

**GDD §0 이 이 게임의 주축을 못박았다**:

> 주축(Primary): 퍼즐형 — 플레이어의 성장은 *로직 설계 실력*으로 이루어진다.
> 보조축: 파밍 — 아이템은 스탯을 올리는 것이 아니라 **로직 표현력을 확장**하는 수단이다.
> 결과: "좋은 장비를 먹어서 이겼다" 가 아니라
> **"좋은 장비 덕분에 더 정교한 로직을 짤 수 있어서 이겼다"** 가 되도록 설계한다.

따라서 **경험치로 스탯이 오르는 레벨은 이 주축과 정면으로 충돌한다.** 레벨을 올려
HP·공격력을 키우면 로직을 고치지 않고도 이기게 되고, 그 순간 P1(실패는 정보다)이 죽는다.

정합적인 대안 — **레벨이 표현력을 올린다**:

| 오르는 것 | 효과 | 이미 있는 것 |
|:--|:--|:--|
| 규칙 슬롯 상한 | 규칙을 더 쓸 수 있다 | GDD §2.3 (층 기록당 +1, 최대 +4) |
| CPU 예산 | 정교한 조건을 쓸 수 있다 | 모듈 "연산 코어 +3" |
| 블록 해금 | 새 인지·행동을 쓸 수 있다 | GDD §2.3 |
| 플래그 개수 | 상태 기억이 는다 | 모듈 "서브루틴 +1" |

**즉 "레벨" 은 이미 다른 이름으로 존재한다.** 숫자 하나로 묶어 보여줄지, 지금처럼 네 축을
따로 둘지가 결정 사항이다. 스탯이 오르는 레벨을 넣으려면 GDD §0 을 함께 고쳐야 한다.

## 6. 거래 — 재현으로 풀리지 않는 유일한 축

아이템의 **진위**는 §4 로 검증되지만 **소유권**은 재현할 수 없다. 서버가 단독으로 정한다.

- 원장은 append-only. 소유권은 원장을 접어서 계산한다(현재 소유자 컬럼은 캐시)
- 거래는 2단계(제안 → 확정)로 두고 확정만 원장에 남긴다
- **경제 설계가 선행되어야 한다** — 아이템 획득률, 인플레이션, 봇 파밍, 계정 간 자전거래.
  기술 문제가 아니라 기획 문제이고, GDD 에 아직 없다 (`docs/08` §2.8)

## 7. 코어 버전과 랭킹

TDD §9: *"코어 버전이 바뀌면 기존 리플레이는 구버전 배지 표시 후 검증 대상에서 제외한다."*

- **랭킹은 `core_version` 별로 갈라야 한다.** 밸런스를 고치면 과거 기록은 재현되지 않는다
- 이미 겪었다: 쿨타임 배선 하나로 `spring_camp` 승률이 47% → 0% 가 됐다
- 코어 버전을 **시즌**으로 쓰면 자연스럽다
- **아이템·메타 프로그레션은 버전을 넘겨 유지한다.** 랭킹만 시즌으로 끊는다 —
  그러지 않으면 밸런스를 고칠 때마다 플레이어의 자산이 사라진다

## 8. 스키마

정규화보다 **감사 가능성**을 우선한다. 결정론이 있으므로 결과가 아니라 입력을 저장하면
언제든 다시 계산해 대조할 수 있다.

```
account(id, handle, created_at)

meta_save(account_id, best_floor, slot_cap,              L2 — 사망해도 남는 것
          unlocked_perceptions[], unlocked_actions[],
          bestiary[], presets[8], core_version, updated_at)

run_ticket(id, account_id, seed, floor, mode,            서버가 발급한 시드
           issued_at, expires_at)                        이것 없이는 제출을 받지 않는다
run_submission(id, ticket_id, ruleset_json,              클라이언트 제출 — **입력만**
               core_version, submitted_at)
run_result(submission_id, outcome, ticks, player_hp,     서버 재시뮬 결과
           cleared_rooms, verified_at, verdict)          verdict: verified|mismatch|rejected

item_instance(id, owner_account_id,                      L2 — 스탯이 아니라 경로 (전체 스키마는 docs/09 §12)
              origin_run_id, floor, node_id, roll_index,
              affixes_json, verified_at, created_at)     affixes_json 은 조회 캐시
item_event(id, item_id, kind, account_id, at)            획득·장착·해제·소멸 이력

trade(id, from_account, to_account, item_id,             L3 — append-only
      offered_at, settled_at, state)

leaderboard(mode, core_version, account_id,              L3 — 버전별 분리
            score, run_result_id, rank_at)
```

**`run_submission` 에 결과 컬럼이 없는 것이 의도다.** 클라이언트가 보낸 결과를 저장할
자리를 아예 두지 않아야, 나중에 누가 "재시뮬 느리니까 그냥 믿자" 는 지름길을 못 낸다.

## 9. 마이그레이션 — L1 에 쌓인 것을 L2 로 올릴 때 ★ 함정

localStorage 에 아이템·성장을 먼저 넣고 나중에 서버로 옮기려 하면, **그때까지 쌓인 것을
신뢰할 수 없다.** 개발자 도구로 무엇이든 넣을 수 있었기 때문이다.

선택지와 대가:

| 안 | 내용 | 대가 |
|:--|:--|:--|
| (a) 전부 폐기하고 새로 시작 | 서버 도입 시 L1 자산을 버린다 | 플레이어가 잃는다. 초기 이탈 |
| (b) 재현 가능한 것만 승계 | 아이템은 획득 경로가 있으면 재시뮬로 검증해 승계, 나머지는 폐기 | 경로를 처음부터 남겨 둬야 성립한다 |
| (c) 전부 승계 | 검증 없이 그대로 올린다 | 거래·랭킹의 신뢰가 처음부터 깨진다 |

**(b) 를 쓰려면 L1 단계에서부터 획득 경로를 함께 저장해야 한다.** 즉 아이템을 넣는
그 시점에 §4 의 시드 파생을 이미 적용해 두어야 한다. 나중에 붙일 수 없다.

**거래를 할 생각이 있다면 아이템 도입 시점에 §4 를 함께 넣는다.** 이것이 이 문서에서
가장 되돌리기 어려운 결정이다.

## 10. 도입 순서

앞 단계 없이 뒷 단계를 하면 되돌려야 한다.

| 순서 | 내용 | 계층 | 없으면 생기는 일 |
|:-:|:--|:--|:--|
| 1 | **메타 프로그레션 배선** (해금·도감·최고 층) | L1 | 죽으면 아무것도 안 남는다. GDD §2.3 이 성립하지 않는다. **스키마가 이미 있어 TS 포팅 + 런 배선뿐이다** |
| 2 | **시드 서버 발급** | L2 | 유리한 시드만 골라 제출. 나중에 고치면 기존 기록 전부 무효 |
| 3 | 계정 + 메타 세이브 서버 이전 | L2 | 기기를 못 넘는다. 랭킹에 붙일 주체가 없다 |
| 4 | 재시뮬 검증 파이프라인 | — | 점수를 믿게 된다 |
| 5 | 랭킹 · 데일리 챌린지 | L3 | — |
| 6 | **아이템 (§4 시드 파생 포함)** | L2 | 나중에 파생 방식을 바꾸면 기존 아이템이 무효 |
| 7 | 거래 원장 + 경제 설계 | L3 | 경제가 먼저 무너진다 |

**1번은 지금 바로 할 수 있고 체감이 가장 크다.** 2번은 가장 싸면서 가장 되돌리기 어렵다 —
지금 고치면 한 줄, 랭킹이 생긴 뒤에 고치면 그때까지의 기록이 전부 무효가 된다.

## 11. 규모 감각

- 검증 1건 = 런당 약 94ms (헤드리스 실측, TDD §11 목표 300ms 대비 여유)
- 4코어 기준 **초당 약 40건**, 하루 300만 건. 데일리 챌린지 규모로는 충분하다
- 저장량: 리플레이 수 KB, 메타 세이브 수 KB, 아이템은 경로만 저장하므로 행당 수백 B
- 다만 아이템·거래가 붙으면 상시 트래픽이 생겨 **지금의 "정적 파일만 주는" 구조가 끝난다.**
  현재 용량 계산(사용자당 오리진 1.2KB, 플레이 중 서버 트래픽 0)은 그 시점에 무효가 된다
