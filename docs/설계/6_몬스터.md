# 몬스터 시스템 설계

> 범위: 등급 · 성장 · 경험치 · 지속 몬스터 · 결정론 경계 · 데이터 대칭.
> 상태: 설계 초안. 결정 항목은 §9 → `docs/결정/1_결정대기목록.md`.
> **요구 5(멀티플레이 공존)가 이 프로젝트의 근간(R5)을 건드린다. §5 가 그것을 다룬다.**

## 0. 출발점 — 적은 이미 플레이어와 같은 것을 쓴다

이 시스템의 절반은 이미 있다. 적은 **규칙표로 행동한다.**

```
game/resources/rulesets/enemies.json   적 8종의 규칙표
policies: dict[str, DecisionPolicy]    개체마다 다른 정책
record_bestiary.py                     도감 — 적의 규칙표를 그대로 공개한다
scaling.py                             층 깊이 스케일 (정수 내림, R5)
```

**플레이어와 적을 코드가 가르지 않는다.** 둘 다 `Entity` 이고 둘 다 RuleVM 을 돈다.
몬스터에 레벨·스킬·장비를 붙인다는 것은 새 시스템을 짓는 게 아니라 **이 대칭을 끝까지
미는 일**이다.

## 1. 등급 3종 × 지속성 2종

등급과 지속성은 **직교한다.** 하나의 축으로 묶으면 "지속되는 일반 몬스터" 를 표현할 수
없고, 나중에 갈라야 한다.

| 등급 | 생성 | 규칙표 | 성장 | 보상 |
|:--|:--|:--|:--|:--|
| **일반** `NORMAL` | 시드 파생 (방 템플릿 `enemy_spawns`) | 카탈로그 고정 | 층 스케일만 | 소모품·재료 |
| **엘리트** `ELITE` | 시드 파생 + 접사·스킬 추가 굴림 | 카탈로그 + 추가 규칙 | 층 스케일 + 개체 성장 | 장비·모듈 |
| **보스** `BOSS` | **설계된 개체** (카탈로그 고정) | 손으로 짠 규칙표 | 설계값 | 확정 보상 · 해금 |

| 지속성 | 뜻 | 어디에 |
|:--|:--|:--|
| `EPHEMERAL` | 런이 끝나면 사라진다 | 일반은 **항상** 이것. 엘리트·보스 기본값 |
| `PERSISTENT` | 서버에 레코드로 남는다. 여러 플레이어가 같은 개체를 만난다 | **특정 개체만** (§5) |

**일반 몬스터는 지속되지 않는다.** 지속시키면 세계에 개체가 무한히 쌓이고, 그것을 전부
스냅샷에 실어야 해서 런 티켓이 감당할 수 없어진다.

## 2. 성장 — 무엇이 오르는가

플레이어와 **같은 규격**을 쓴다 (`docs/설계/4_아이템` §6 요구조건, `docs/설계/5_스킬` 스킬).
레벨·스탯·스킬·장비가 같은 필드다.

여기서 이 게임 특유의 선택이 하나 있다.

> **몬스터의 성장은 스탯만이 아니라 규칙 슬롯·CPU 예산을 올린다.**

몬스터도 규칙표로 행동하므로, 슬롯이 늘면 **몬스터의 판단이 정교해진다.**
레벨 3 고블린 궁수는 "적이 보이면 쏜다" 지만, 레벨 20 은 "엄폐를 유지하며 사거리를
재고 회복 타일을 끊는다".

이것이 중요한 이유는 셋이다.

1. **도감이 그 변화를 그대로 보여준다.** 규칙표가 공개되므로 플레이어는 몬스터가 어떻게
   똑똑해졌는지 **읽을 수 있다.** 스탯만 오르면 "숫자가 커졌다" 로 끝난다
2. **P1 을 지킨다.** 진 이유가 "몬스터 공격력이 높아서" 가 아니라 "몬스터 규칙 4번이
   내 규칙 2번을 받아친다" 가 된다. 고칠 곳이 특정된다
3. **GDD §0 과 같은 축이다.** 플레이어의 성장이 로직 표현력이라면, 적의 성장도 그래야
   대칭이 성립한다

**대가**: 몬스터 규칙표를 누가 쓰는가. 손으로 짜면 레벨마다 필요하고, 자동 생성하면
품질을 보증할 수 없다. §9 의 M2 다.

### 층 스케일과 개체 성장은 다른 것이다

지금 `scaling.py` 의 층 스케일은 **개체가 아니라 배치**에 붙는다 — 5층의 고블린은
1층 고블린보다 세지만 같은 개체가 아니다. 개체 성장(`level`)은 그 위에 얹힌다.

```
최종 능력치 = 카탈로그 기본값
            → 개체 레벨 성장 적용
            → 층 스케일 적용 (정수 내림)
```

**순서를 고정한다.** 뒤집으면 값이 달라진다 (`docs/설계/4_아이템` §9 와 같은 이유).

## 3. 경험치 — 사냥으로 오른다

| 획득원 | 조건 | 비고 |
|:--|:--|:--|
| **플레이어 처치** | 플레이어가 그 몬스터에게 죽음 | 요구 3·4 |
| **다른 몬스터 처치** | 몬스터끼리의 전투 | 요구 3. §6 참조 |
| (선택) 시간 경과 | — | §9 M4 |

경험치·레벨 곡선은 정수 테이블이다. 공식에 부동소수를 쓰지 않는다 (R5).

**경험치는 검증된 런에서만 적용된다.** 클라이언트가 "내가 졌다" 고 보고해서 몬스터가
크는 구조면, 자기 몬스터를 키우려고 일부러 지는 어뷰징이 열린다. `run_result.verdict`
가 `verified` 인 런만 원장에 반영한다 (`docs/설계/3_저장과_멀티플레이` §8).

## 4. 유저 사냥 — 몬스터가 아이템을 가져간다

요구 4. **이것이 이 게임에서 가장 강한 동기를 만든다.**

플레이어가 죽으면 몬스터가 그 아이템을 획득한다. 그리고 **도감이 몬스터의 장비를
보여준다.** 그러면:

```
내 [연산 코어 +3] 을 레벨 14 고블린 궁수가 들고 있다
→ 그 개체를 다시 찾아가 되찾는다
```

원한이 생긴다. 지속 몬스터(§5)가 게임적으로 성립하는 이유가 이것이다.

**다만 대가가 크다.** 아이템을 잃는 것은 로그라이크의 "사망 시 소멸"(GDD §2.3)과 다르다 —
소멸은 아무도 안 가져가지만 이것은 **남에게 넘어간다.** 완화 장치 없이 넣으면 신규
플레이어가 이탈한다.

| 안 | 내용 |
|:--|:--|
| (a) 전량 | 장착·인벤토리 전부 넘어간다 |
| (b) 일부 | 정해진 개수·확률만. 나머지는 소멸 |
| (c) 귀속 제외 | `bound` 아이템은 안 넘어간다 (`docs/설계/4_아이템` §12) |
| (d) 사본 | 몬스터는 사본을 들고, 원본은 규칙대로 소멸 |

**(c)+(b) 를 권한다.** 귀속 규칙(`docs/결정/1_결정대기목록` #07)이 이미 결정 대기 중이므로 그것과 함께
정한다. (d)는 아이템 총량이 늘어 거래 경제를 흔든다.

**퀘스트 아이템은 넘어가지 않는다** (`docs/설계/4_아이템` §4 — 사망 시 보존).

## 5. 지속 몬스터 — 결정론을 어떻게 지키는가 ★★

요구 5 가 이 프로젝트의 근간을 건드린다.

**이 게임의 전부는 이 등식이다:**

```
런 결과 = f(시드, 규칙표, 코어 버전)
```

리플레이·데일리 챌린지·헤드리스 밸런싱·서버 재검증이 전부 여기 얹혀 있다.
그런데 **여러 플레이어가 공유하는 살아 있는 몬스터**는 이 등식 밖의 입력이다.

- 몬스터의 능력치는 시드에서 나오지 않는다. 세계 상태다
- 두 플레이어가 동시에 같은 개체와 싸우면 어느 쪽 결과를 반영하는가
- 어제의 리플레이를 오늘 재생하면 몬스터가 더 세져 있어 재현되지 않는다

### 해법 — 스냅샷 봉인

**런이 시작될 때 몬스터의 상태를 티켓에 얼려 넣는다.**

```
런 시작 요청
  → 서버가 run_ticket 발급
      seed
      monster_snapshot[]   ← 이 런이 만날 지속 몬스터의 상태 전부
      core_version
  → 클라이언트는 그 스냅샷으로만 시뮬레이션한다

런 결과 = f(시드, 규칙표, 코어 버전, 몬스터 스냅샷)
                                   └─ 티켓에 박혀 있으므로 재현된다
```

- **등식이 유지된다.** 스냅샷이 입력의 일부가 됐을 뿐이다. 서버는 같은 스냅샷으로
  재시뮬해 검증할 수 있고, 리플레이도 스냅샷을 함께 저장하면 영원히 재현된다
- **동시 사냥이 성립한다.** 두 플레이어가 같은 스냅샷을 상대한다. 결과는 검증 순서대로
  원장에 반영된다
- **오프라인 플레이가 가능하다.** 티켓만 받아 두면 전투는 브라우저에서 돈다.
  지금의 "코어가 브라우저 안에서 돈다" 구조를 버리지 않아도 된다

`docs/설계/3_저장과_멀티플레이` §8 의 `run_ticket` 에 `monster_snapshot` 을 더하면 된다. **새 아키텍처가
아니라 기존 티켓의 확장이다.**

### 남는 문제 — 동시 처치

두 플레이어가 같은 개체를 각자 잡았다. 둘 다 유효한 검증된 런이다.

| 안 | 내용 | 대가 |
|:--|:--|:--|
| (a) 선착 | 먼저 검증된 쪽만 처치 인정. 나머지는 "이미 처치됨" | 늦은 쪽이 헛수고 — 나쁜 경험 |
| (b) 양쪽 인정 | 둘 다 보상. 개체는 한 번 죽는다 | 보상이 복제된다. 경제 영향 |
| (c) 인스턴스 | 스냅샷 시점에 개체가 분기. 각자의 몬스터를 잡는다 | 공존감이 옅어진다 |

**(b) 를 권한다.** (a)는 시간을 쓴 플레이어를 벌하고, (c)는 요구 5 를 형해화한다.
보상 복제는 처치 보상을 "아이템" 이 아니라 "그 몬스터가 들고 있던 것 중 자기 것"
으로 한정하면 대부분 막힌다 — §4 의 되찾기 동기와도 맞는다.

### 남는 문제 — 성장 폭주

몬스터가 플레이어를 사냥해 계속 크면 **신규 플레이어가 들어갈 자리가 없다.**
지속 세계형 게임이 전부 겪는 문제이며, 장치 없이는 반드시 발생한다.

- 레벨 상한 (구역·층별)
- 처치 시 리셋 또는 감쇠 — 죽으면 레벨이 내려간다
- 구역 격리 — 저층 몬스터는 저층에만
- 성장률 체감

**최소 하나는 필수다.** 어느 것을 쓸지는 §9 M5.

## 6. 몬스터끼리의 전투

요구 3. 이미 절반 있다 — `policies: dict[str, DecisionPolicy]` 로 개체마다 다른 규칙표를
돌리고 있으므로, **faction 을 늘리면 몬스터끼리 싸운다.**

다만 **누가 그 전투를 시뮬레이션하는가**가 문제다. 플레이어가 없는 전투를 브라우저가
돌릴 이유가 없다.

| 안 | 내용 |
|:--|:--|
| (a) 서버 배치 시뮬 | 주기적으로 서버가 돌린다. 헤드리스 러너가 이미 있다 (`scripts/`) |
| (b) 목격 시에만 | 플레이어가 그 방에 있을 때만 실제로 싸운다 |
| (c) 안 넣는다 | 경험치원을 플레이어 사냥으로만 |

**(a) 가 자연스럽다.** 런당 94ms 라 하루 300만 건이 가능하고(`docs/설계/3_저장과_멀티플레이` §11),
그 결과가 다음 스냅샷에 반영된다. 세계가 플레이어 없이도 움직인다.

## 7. 데이터 대칭 — 하나의 레코드

플레이어와 지속 몬스터는 **같은 형태**다. 스키마를 가르지 않는다.

```sql
entity_record(
  id, kind,                    -- PLAYER | MONSTER
  owner_account_id,            -- PLAYER 만. MONSTER 는 NULL
  catalog_id,                  -- MONSTER 만. 어느 종인가
  tier,                        -- NORMAL | ELITE | BOSS
  persistence,                 -- EPHEMERAL | PERSISTENT
  level, xp,
  stat_json,                   -- 요구조건 판정의 소재 (docs/설계/4_아이템 §7)
  ruleset_json,                -- 규칙표. 도감이 이것을 공개한다
  rule_slots, cpu_budget,      -- 성장이 올리는 것 (§2)
  origin_run_id, spawn_seed,   -- 시드 파생 개체의 재현 근거
  zone_id, floor,              -- 어디에 있는가 (PERSISTENT 만)
  alive, updated_at
)
-- 장비·인벤토리·스킬은 entity_record 를 참조한다.
-- docs/설계/4_아이템 §12 의 equipment_slot·inventory_slot 의 account_id 를 entity_id 로 일반화한다.

monster_kill(id, entity_id, victim_kind, victim_id,   -- 경험치 원장
             run_result_id, xp_gained, at)
monster_snapshot(ticket_id, entity_id, state_json)    -- §5 의 봉인
```

**`ruleset_json` 이 몬스터 레코드에 있는 것이 이 설계의 중심이다.**
몬스터의 정체는 스탯이 아니라 규칙표다. 도감이 공개하는 것도, 성장이 바꾸는 것도 그것이다.

## 8. 도감이 하는 일이 커진다

`record_bestiary.py` 는 지금 스탯을 기록한다. 여기에 붙는다:

| 보여줄 것 | 왜 |
|:--|:--|
| 규칙표 (현재 레벨 기준) | GDD §2.3 — 실패한 런도 자산이 된다 |
| 레벨과 성장 이력 | 지난번보다 얼마나 세졌는가 |
| **장비 — 내 아이템이 있는가** | §4 의 되찾기 동기 |
| 스킬 목록 | `docs/설계/5_스킬` §7 |
| 마지막 목격 위치 | 다시 찾아가려면 필요하다 |

지속 몬스터에게 도감은 **위키가 아니라 표적 목록**이 된다.
