# 코딩형 로그라이크 그리드 RPG — 기술 설계서 (TDD v1)

---

## 1. 기술 방향 및 스택

### 1.1 핵심 원칙: 결정론적 시뮬레이션

- **시뮬레이션 코어와 렌더링을 완전히 분리한다.** 코어는 화면 없이 단독 실행 가능해야 한다.
- 모든 무작위성은 **시드 기반 PRNG** 를 통해서만 발생한다. 시스템 시간·해시 순서·부동소수 오차에 의존 금지.
- **효과:**
  - 리플레이 = `(시드 + 규칙표 + 버전)` 만 저장하면 완전 재현 (용량 수 KB)
  - 밸런싱을 헤드리스 배치 실행으로 자동 검증 가능 (1,000런 시뮬 → 승률 통계)
  - 데일리 챌린지·유령 대결·순위 검증이 서버 없이 성립

### 1.2 스택 제안

| 단계 | 스택 | 근거 |
|:--|:--|:--|
| Phase 1 프로토타입 | **Python 3.11** (표준 라이브러리 + 텍스트/pygame 렌더) | 사내 표준 언어, 검증 속도 최우선, 헤드리스 시뮬 작성 용이 |
| Phase 3 프로덕션 | **TypeScript (코어) + React (에디터 UI) + Canvas (전투 렌더)** | 규칙 에디터가 이 게임의 메인 UI → 웹 UI 생태계가 압도적으로 유리. 웹 즉시 배포 후 Electron/Steam 래핑 |

- **대안:** Godot 4 (C#) — 파티클/사운드 품질 우위지만, 드래그 기반 복잡 에디터 UI 구현 비용이 큼. 에디터 UX 비중을 고려하면 비권장.
- **이관 리스크 완화:** Python 프로토타입은 **버릴 코드**로 명시적으로 취급한다. 단, 규칙 DSL 스키마와 밸런스 JSON은 그대로 이식되도록 언어 중립 포맷(JSON)으로 작성한다.

### 1.3 코드 규약

- Python 구간은 사내 표준 준수: `{동사}_{목적어}` 네이밍, 전역 상수 대문자, 2회 이상 사용 기능 함수화, Google 스타일 독스트링
- TypeScript 이관 시 동일 원칙을 camelCase로 매핑 (`calculate_final_stats` → `calculateFinalStats`)

## 4. 틱 엔진

### 4.1 페이즈 순서 (고정)

| # | 페이즈 | 처리 |
|:-:|:--|:--|
| 1 | UPKEEP | 쿨타임 감소, 상태이상 지속시간, 회복 연산, 타일 피해(용암) |
| 2 | TELEGRAPH | 예고 공격 카운트다운, 발동 시 피해 적용 |
| 3 | PERCEPTION | 전 엔티티의 인지 변수 스냅샷 생성 (**이 시점에 고정**) |
| 4 | DECIDE | RuleVM으로 각 엔티티 행동 결정 (부작용 없음) |
| 5 | ACT | 결정된 행동 실행 (이동→공격 순) |
| 6 | RESOLVE | 피해 정산, 사망 처리, 타일 상태 갱신 |
| 7 | CLEANUP | 이벤트 로그 flush, 승패 판정 |

> **중요:** PERCEPTION과 DECIDE를 분리하는 이유는 **동시성 공정성**이다. 모든 엔티티가 "같은 시점의 세계"를 보고 판단해야 한다. 순차 갱신하면 처리 순서가 유리/불리를 만든다.

### 4.2 이동 충돌 처리

- 같은 칸을 목표로 하는 엔티티가 복수일 때: `entity_id` 사전순이 아니라 **엔티티의 이니셔티브 값(스탯)** 으로 결정, 동률 시 시드 PRNG로 결정 → 결정론 유지
- 이동 실패 시 그 틱은 제자리 (행동 낭비)

## 5. RuleVM (DSL 실행기)

### 5.1 컴파일 파이프라인

```
JSON 규칙표 → 검증(Validator) → 컴파일(클로저 배열) → 캐시
```

- 방 진입 시 1회 컴파일, 이후 틱마다 재사용
- 검증 단계에서 확인할 것: 미해금 블록 사용 여부, CPU 예산 초과, 슬롯 수 초과, 잘못된 셀렉터-행동 조합

### 5.2 실행 규약

- 규칙은 우선순위 오름차순 평가, **최초 참인 1개만 실행**, 나머지는 무시
- 전부 거짓이면 `DEFAULT` 행동 (기본: 가장 가까운 적에게 접근)
- **조건 평가는 반드시 순수 함수** (부작용 금지) → 무한루프 원천 차단
- 틱당 행동은 정확히 1개 → 프레임 폭주 불가

### 5.3 CPU 비용 산식

```
cpu_cost(rule) = 1 (1항) | 2 (2항) | 4 (3항)
sum(cpu_cost) <= entity.cpu_budget
```

### 5.4 인지 변수 구현 주의점

- `자기 위치가 시야에 노출됨(LOS)` 은 O(적 수 × 사거리) → 방 진입 시 **가시성 맵 사전 계산** 후 적 이동분만 갱신
- 인지 스냅샷은 틱당 1회만 생성하고 전 규칙이 공유 (중복 계산 금지)

## 6. 길찾기

- **초기 구현은 BFS/Dijkstra로 충분.** 방 크기가 최대 20×15 수준이므로 A\*의 휴리스틱 이득이 미미하고 코드 복잡도만 증가.
- **최적화 방식: Distance Field(거리장) 캐싱**
  - 방 진입 시 문·계단·회복타일 각각에 대해 flood fill 거리장을 1회 계산
  - "문으로 이동", "회복타일로 이동" 은 거리장 기울기를 따라가면 되므로 **탐색 비용 0**
  - 적 추적만 매 틱 갱신 (적 수가 적으므로 부담 없음)
- 가시덤불 등 이동 코스트 타일 때문에 BFS가 아닌 **가중 Dijkstra** 사용

## 7. 절차적 생성

### 7.1 층 그래프
- 깊이 기반 DAG 생성: 시작 노드 1개 → 분기 2~3 → 수렴 → 보스
- 노드 유형 배치 비율: 전투 60% / 이벤트 15% / 회복 15% / 상점 10%

### 7.2 방 생성
- **완전 랜덤 금지.** 손으로 만든 룸 템플릿(30~50개) + 무작위 회전/미러 + 스폰 지점 셔플
- 이유: 순수 랜덤 그리드는 전술적으로 무의미한 공간을 대량 생산함
- **검증 필수:** 생성 직후 flood fill로 `시작점 → 모든 문` 도달 가능성 확인, 실패 시 재생성

### 7.3 결정론 보장
- 생성 로직은 `seed + floor_index + node_id` 를 결합한 서브 시드 사용
- 동일 시드는 동일 던전을 반드시 생성 (골든 테스트로 회귀 검증)

## 8. 전투 수식

```
final_stat = (base + sum(flat_affixes)) * (1 + sum(percent_affixes) / 100)

damage = max(1, floor(attack * skill_coef * (1 - defense / (defense + 50 + 10 * floor))))

surrounded_penalty = 1 + 0.1 * (인접 적 수 - 1)   # 최대 1.4
final_damage = damage * surrounded_penalty
```

- 방어력은 **감쇠식(soft cap)** 사용 → 방어 스택 무적화 방지
- 층이 올라갈수록 방어 효율이 낮아지도록 `floor` 항 포함 → 스탯 뭉개기 억제 (기획서 §7 대응)

## 9. 저장 및 직렬화

| 대상 | 내용 | 비고 |
|:--|:--|:--|
| 런 스냅샷 | 시드, 현재 노드, 엔티티 상태, 인벤토리, 규칙표 | 방 클리어 시 자동 저장 |
| 메타 세이브 | 해금 블록, 슬롯 상한, 도감, 프리셋 8슬롯 | 사망해도 유지 |
| 프리셋 공유 코드 | `v2:` + gzip(JSON) + base64 | 버전 접두어로 마이그레이션 판정 |
| 리플레이 | 시드 + 규칙표 + 코어 버전 | 수 KB, 서버 저장 가능 |

- **버전 마이그레이션 정책:** 코어 버전이 바뀌면 기존 리플레이는 "구버전" 배지 표시 후 검증 대상에서 제외. 프리셋은 마이그레이션 스크립트로 변환 시도, 실패 시 미해금 블록만 제거 후 로드.

## 10. 테스트 전략

| 유형 | 내용 | 자동화 |
|:--|:--|:--|
| 골든 리플레이 | 저장된 (시드+규칙표)가 항상 동일 결과를 내는지 | CI 매 커밋 |
| 헤드리스 배치 밸런싱 | 표준 규칙표 5종 × 1,000런 → 층별 승률/평균 틱 | 야간 배치 |
| 룸 생성 검증 | 10,000회 생성 → 도달 불가 방 0건 | CI |
| DSL 퍼징 | 무작위 규칙표 생성 → 크래시/무한루프 0건 | 야간 배치 |
| AI vs AI | 신규 몬스터 추가 시 기존 상위 규칙표와 대전, 승률 확인 | 수동 트리거 |

> **밸런싱을 감이 아니라 데이터로 한다.** 이것이 결정론 코어를 최우선으로 두는 실질적 이유.
