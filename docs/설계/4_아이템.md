# 아이템 시스템 설계

> 범위: 분류 · 장비 슬롯 · 소모품 · 인벤토리 · **사용 제한(레벨·스탯)** · 결정론 · DSL 노출 ·
> 모듈 배치 · DB 스키마.
> 상태: **설계만. 구현 없음.** Phase 4 W15 의 착수 문서다.
> 저장 계층·위조·마이그레이션은 `docs/설계/3_저장과_멀티플레이.md` 를 따른다.

## 0. 두 개의 상위 제약

이 시스템은 두 가지를 어길 수 없다. 어기면 아이템이 아니라 게임이 깨진다.

**(1) GDD §0 — 아이템은 스탯이 아니라 로직 표현력을 준다.**
*"좋은 장비를 먹어서 이겼다" 가 아니라 "좋은 장비 덕분에 더 정교한 로직을 짤 수 있어서
이겼다."* 장비 6슬롯이 전부 공격력 덩어리면 규칙표를 고칠 이유가 사라지고 P1(실패는
정보다)이 죽는다. 슬롯이 늘어나는 만큼 **모듈 접사(§6.2)의 자리가 늘어나야** 한다.

**(2) R5 — 결정론.** 같은 시드는 같은 결과를 낸다.
- 아이템은 **서버가 발급하지도, 클라이언트가 만들지도 않는다.** 시드에서 파생한다 (§8)
- 인벤토리를 **딕셔너리·집합 순회로 만들지 않는다.** 칸 번호로 정렬된 배열이다
- 스탯 합산에 **부동소수를 쓰지 않는다.** 정수 나눗셈이며 연산 순서가 고정이다 (§9)
- **장착 순서가 결과를 바꾸면 안 된다.** §7 이 이것을 다룬다

## 1. 분류 — 3종

| 종류 | 장착 | 소모 | 인벤토리 칸 | 스택 | 사망 시 |
|:--|:-:|:-:|:-:|:-:|:--|
| **장비** (EQUIPMENT) | O | X | 1칸/개 | X (개체 고유) | 소멸 |
| **소모품** (CONSUMABLE) | X | O | 1칸/스택 | O | 소멸 |
| **퀘스트** (QUEST) | X | X | **별도 주머니** (§5) | X | **보존** |

분류는 카탈로그가 정하는 정적 값이다. 런 중에 바뀌지 않는다.

## 2. 장비 — 슬롯 6개

```
        ┌─────────┐
        │  HEAD   │  투구
┌───────┼─────────┼───────┐
│ HANDS │  BODY   │ WEAPON_MAIN │  주무기
│ 장갑  │  갑옷   │ WEAPON_OFF  │  보조 (한손무기 · 방패)
└───────┼─────────┼───────┘
        │  FEET   │  신발
        └─────────┘
```

`slot ∈ {WEAPON_MAIN, WEAPON_OFF, HEAD, BODY, FEET, HANDS}` — **고정 순서다.**
스탯 합산이 이 순서로 돈다 (§9).

### 2.1 무기 손 규격

무기 카탈로그는 `hands ∈ {ONE, TWO, OFFHAND}` 를 가진다.

| `hands` | 예 | 점유 |
|:--|:--|:--|
| `ONE` | 검, 단검, 도끼, 지팡이(한손) | MAIN 또는 OFF 하나 |
| `TWO` | 대검, 창, 활, 대형지팡이 | **MAIN 을 점유하고 OFF 를 봉인** |
| `OFFHAND` | 방패, 보조기 | OFF 전용 |

**방패는 무기 계열의 `OFFHAND` 다.** 별도 슬롯을 만들지 않는다 — 만들면
"양손무기 vs 한손+방패" 라는 트레이드오프(P3)가 사라진다.

봉인은 상태가 아니라 **파생값**이다. `WEAPON_OFF` 를 읽을 때 MAIN 이 `TWO` 면 비어 있는
것으로 계산한다. 실제로 아이템을 옮겨 두면 착용/해제 순서에 따라 상태가 갈린다.

```python
def get_effective_slots(equipped: EquipmentSet) -> tuple[SlotBinding, ...]:
    """봉인을 반영한 유효 장비 구성. 저장된 상태가 아니라 매번 계산한다."""
```

### 2.2 무기가 바꾸는 것

`attack_range` 는 이미 코어에 있고 규칙표가 읽는다(`target_distance <= 사거리`).
**무기 종류가 사거리를 바꾸면 같은 규칙표가 다른 전투를 만든다** — 이것이 P2 를 만족하는
지점이다. 활(사거리 4)로 바꾸면 `g0_kite` 는 살고 `door_hold` 는 무너진다.

무기는 사거리 · 공격력 · **모듈 접사 자리 수** 를 정한다. 마지막 것이 GDD §0 의 축이다.

## 3. 소모품

- 1회용 주문서 · 물약 · 전투용 공격/방어 아이템
- **스택**한다. 한 칸에 같은 종류 N 개
- 전투 중 사용은 **규칙표가 지시한다.** 플레이어가 버튼을 누르지 않는다 — 캐릭터를
  직접 조종하지 않는 게임이다 (GDD §1)

지금 코어는 `Entity.potions: int` 스칼라 하나이고 `USE_POTION` 행동 하나가 그것을 쓴다.
종류가 늘면 이 둘을 확장해야 한다 (§10 블록 v5).

**사용 시점 규칙**: 소모는 ACT 페이즈에서 일어나고, 효과 판정은 RESOLVE 다. 한 틱에
소모품 하나 — 그러지 않으면 물약 스택을 한 틱에 쏟아붓는 어뷰징이 열린다 (GDD §7).

## 4. 퀘스트 아이템

소모 불가 · 장비 불가 · 거래 불가. **퀘스트 시스템은 추후 업데이트**이므로 지금은
자리만 만든다.

지금 정해 둘 것은 하나 — **인벤토리 칸을 먹지 않는다.** 별도 주머니에 둔다.
칸을 먹게 하면 퀘스트가 진행될수록 인벤토리 관리 퍼즐이 되고, 그것은 이 게임이 파는
퍼즐이 아니다. 나중에 분리하려면 저장 구조를 갈라야 하므로 지금 갈라 둔다.

**사망 시 보존**한다 (§1 표). 퀘스트가 런을 넘어 이어지지 않으면 퀘스트가 아니다.

## 5. 인벤토리

- 칸 수 상한이 있다. 기본값은 밸런스 데이터가 정한다 (초안 20칸)
- 획득 시 **가장 낮은 빈 칸**에 들어간다. 빈 칸이 없으면 획득이 **보류**되고 플레이어가
  버릴 것을 고른다
- 자동 폐기를 넣지 않는다. 자동 폐기는 결정론적 규칙을 요구하는데, 그 규칙이 플레이어의
  의도와 어긋나면 "왜 사라졌는지" 를 설명할 수 없다 (P1)
- 전투 중에는 획득이 없다. 보상은 방 클리어 후다 (GDD §2.2) — 그래서 인벤토리가 가득 찬
  상태로 전투에 들어가도 전투가 막히지 않는다

```
inventory: tuple[InventorySlot | None, ...]   # 길이 = 칸 수. 인덱스가 곧 칸 번호
```

**`dict[int, Item]` 을 쓰지 않는다.** 빈 칸이 표현되지 않고, 순회 순서가 보장되지 않는다.

## 6. 사용 제한 — 요구조건 ★

아이템은 레벨·스탯 요구조건을 가진다. **일반화한 정수 비교 하나로 표현한다.**

```json
"requirements": [
  {"stat": "level",      "min": 12},
  {"stat": "str",        "min": 15},
  {"stat": "cpu_budget", "min": 6}
]
```

- 정수 비교뿐이다. 부동소수·비율 조건을 넣지 않는다 (R5)
- 어떤 능력치가 존재하는지는 **밸런스 데이터가 정한다.** 코드는 이름을 모른다
- 그래서 §12 의 "능력치 축을 무엇으로 둘 것인가" 를 나중에 정해도 아키텍처가 안 바뀐다

### 6.1 미충족을 어떻게 보여주는가

이 게임의 UI 규약이 이미 답을 정해 뒀다. 규칙 에디터의 조건문은
`적거리(2) <= 사거리(3)` 처럼 **각 항의 실측값을 병기**한다 (GDD §8.2, P1).
**장비 요구조건도 같은 표기를 쓴다.**

```
  강철 대검                       장착 불가
  힘(12) >= 요구(15)              거짓  ✕
  레벨(14) >= 요구(12)            참    ✓
```

"장착할 수 없습니다" 만 띄우면 P1 위반이다. 무엇이 얼마나 모자란지가 화면에 있어야 한다.

## 7. 요구조건의 순환 — 이 설계에서 가장 조용한 함정 ★

장비 A 가 `힘 >= 15` 를 요구하고 장비 B 가 `힘 +5` 를 준다고 하자.

```
힘 12 · A · B 를 가진 상태
  B 먼저 착용 → 힘 17 → A 착용 가능 → 둘 다 착용
  A 먼저 착용 → 힘 12 → A 착용 불가 → B 만 착용
```

**같은 소지품에서 다른 최종 상태가 나온다.** 순서가 결과를 바꾸므로 R5 위반이고,
서버 재검증도 불가능해진다 — 클라이언트가 어떤 순서로 착용했는지를 함께 보내야 하는데
그것은 위조 가능한 입력이다. B 를 벗으면 A 가 어떻게 되는지도 정의되지 않는다.

**해결: 요구조건은 장비 보너스를 제외한 소재 능력치로만 판정한다.**

```
판정 기준 = 기본 능력치 + 레벨 성장 + 영구 해금
          (장비·소모품·버프가 준 것은 제외)
```

- 순서 의존이 사라진다. 어떤 순서로 착용해도 같은 집합이 착용 가능하다
- 해제 시 연쇄 탈착이 없다
- 서버는 `(account, item)` 만으로 재판정할 수 있다
- 대가: "장비를 겹쳐 요구조건을 뚫는" 빌드가 불가능해진다. **의도한 대가다** — 그 빌드는
  재미보다 순서 퍼즐을 만든다

재판정 시점은 두 곳이다 — **착용 시**, 그리고 **런 시작 시**. 레벨·해금이 되돌아가는
경로는 없지만, 서버가 소재 능력치의 정본이므로 런 시작 시 한 번 더 본다.

## 8. 아이템 정체성 — 서버가 발급한다 (개정 2026-08-30)

> 이전 안은 **시드 파생**이었다. 서버 발급으로 정해졌고, 그 선택이 무엇을 바꾸는지
> 아래에 적는다.

**전리품 생성은 전투 시뮬레이션 밖에 있다.** 코어는 아이템을 만들지 않는다. 서버가
**검증된 런의 결과를 보고** 발급한다.

```
브라우저          전투를 돈다 — 아이템이 나오지 않는다
  → 제출          티켓 id + 규칙표
서버              재시뮬로 결과 확정 (verdict=verified)
  → 발급          그 결과에 걸맞은 전리품을 굴려 계정에 넣는다
```

이 배치가 지키는 것과 잃는 것.

| | 내용 |
|:--|:--|
| ✅ **전투 결정론이 온전하다** | 코어가 아이템을 모른다. 장비는 전투 **전에** 스탯·스킬로 녹아 티켓의 로드아웃이 되고, 코어는 그 수치만 받는다 — 그래서 등식은 `f(…, 로드아웃)` 으로 한 항이 늘 뿐 리플레이와 골든의 구조는 그대로다 |
| ✅ **위조가 불가능하다** | 클라이언트는 아이템을 만들 수 없다. 발급처가 서버 하나뿐이다 |
| ✅ **골든에 전리품 축이 필요 없다** | 시뮬레이션 산출물이 아니기 때문이다 (#05 가 이 결정으로 소멸했다) |
| ✅ **L1 위조 창이 없다** | 아이템이 `localStorage` 에 정본으로 존재한 적이 없다 (#03 의 함정이 소멸했다) |
| ❌ **오프라인에서는 아이템이 나오지 않는다** | 티켓이 없으면 제출할 수 없고, 제출이 없으면 발급도 없다. 오프라인 런은 연습이다 |
| ❌ **같은 시드를 다시 돌려도 같은 아이템이 아니다** | 전리품은 시드의 함수가 아니다. "이 시드에서 그 검이 나온다" 는 성립하지 않는다 |

**서버의 굴림에는 `secrets` 를 쓴다.** R5 위반이 아니다 — 게임 난수가 아니라 예측
불가능해야 하는 값이고, 코어 밖이다. 예측 가능하면 어느 자리에서 무엇이 나오는지 미리
계산해 그 판만 완주하는 골라 담기가 열린다.

**발급 기록은 남긴다.** `item_instance` 가 `origin_run_result_id` 를 들고 있어 "언제 어느
런에서 나왔는가" 를 되짚을 수 있다. 재현으로 검증하지는 못하지만, 감사와 조사에는 그
연결이 필요하다.

## 9. 스탯 연산 — 순서와 정수

GDD §6.4:

```
최종 스탯 = (기본값 + 고정 합계) × (1 + 퍼센트 합계 / 100)
```

정수로 다시 쓰면:

```python
final = (base + flat_sum) * (100 + percent_sum) // 100
```

- **곱한 뒤에 나눈다.** 먼저 나누면 정수 절삭이 두 번 일어나 값이 달라진다
- 나머지는 버린다(내림). TS 는 `Math.floor` 가 아니라 `(a * b / 100n)` BigInt 나눗셈으로
  같은 절삭을 얻어야 한다 — 음수 퍼센트(저주 접사)에서 `Math.trunc` 와 `Math.floor` 가
  갈린다. **저주 접사가 있으므로 이것은 실제로 발생한다**
- 합산 순서는 §2 의 슬롯 고정 순서 → 각 슬롯 안에서는 접사 배열 순서다.
  정수 덧셈은 교환법칙이 성립하지만, 상한·하한 클램프가 끼면 순서가 결과를 바꾼다.
  **클램프는 합산이 전부 끝난 뒤 한 번만 적용한다**

## 10. DSL 노출 — 블록 v5 (제안)

**장비를 규칙표가 볼 수 없으면 장비는 이 게임에 존재하지 않는 것과 같다.**
사거리가 바뀌었는데 규칙표가 그것을 못 읽으면, 플레이어는 무기를 바꾼 뒤 규칙을 왜
고쳐야 하는지 알 수 없다.

### 추가 인지 (perceptions)

| id | 반환 | 라벨 | 이유 |
|:--|:--|:--|:--|
| `self_weapon_hands` | enum | 내 무기 손 | 양손/한손+방패 분기 |
| `self_has_shield` | bool | 방패 착용 여부 | 방어 규칙의 전제 |
| `self_consumable_count` | int | 내 소모품[종류] 수 | `self_potion_count` 를 대체 |
| `self_has_module` | bool | 내 모듈[종류] 보유 | 모듈 유무로 규칙 분기 |

### 추가 행동 (actions)

| id | 라벨 | 비고 |
|:--|:--|:--|
| `USE_ITEM` | 소모품 사용[종류] | `USE_POTION` 을 포섭 |

**호환 처리**: `self_potion_count` 와 `USE_POTION` 을 지우지 않는다. 지우면 저장된
규칙표와 골든 리플레이가 전부 깨진다. `USE_ITEM[POTION]` 의 별칭으로 남기고,
`block_list_version` 을 v4 → v5 로 올린다. **블록 목록 버전은 코어 버전의 일부이므로
랭킹 시즌이 갈린다** (`docs/설계/3_저장과_멀티플레이` §7).

## 11. 모듈 배치

```
game/
├─ schemas/
│  ├─ item.py            아이템 계약. TS 로 이식되는 자산
│  │                     ItemCatalogEntry · ItemInstance · Requirement · Affix
│  └─ inventory.py       InventorySlot · EquipmentSet · QuestPouch
├─ app/
│  └─ items/             ← 신설. 아이템만 안다
│     ├─ catalog.py      items.json 로드·조회
│     ├─ affixes.py      시드 파생 접사 굴림 (§8)
│     ├─ requirements.py 요구조건 판정 (§6·§7) — 소재 능력치만 본다
│     └─ stats.py        스탯 합산 (§9)
└─ resources/balance/
   └─ items.json         카탈로그. 슬롯·손·요구조건·접사 풀

game/app/services/
├─ manage_inventory.py   획득·이동·버리기. 칸 상한을 아는 유일한 곳
└─ manage_equipment.py   착용·해제. 봉인(§2.1)과 요구조건(§7)을 엮는다

frontend/src/core/items/  위 넷의 TS 이식. 골든으로 대조한다
```

의존 방향: `items/` 는 `simulation/` 을 모른다. 반대로 `simulation/` 이 최종 스탯을
받아 `Entity` 를 만든다 — 지금 `abilities.py` 가 밸런스 딕셔너리로 하는 일과 같은 자리다.

**착용은 전투 밖에서만 일어난다** (GDD §2.2 — 규칙 편집은 방 사이에서만). 그래서 틱
엔진은 아이템을 모르고, 전투 시작 시 확정된 스탯만 받는다. 이 경계를 지키면 아이템이
틱 성능에 영향을 주지 않는다.

## 12. DB 스키마

`docs/설계/3_저장과_멀티플레이.md` §8 의 `item_instance` 를 확장한다. 계층은 전부 **L2**
(계정 소유), 거래만 **L3**.

```sql
-- 정적 카탈로그는 DB 가 아니라 resources/balance/items.json 이다.
-- 코어 버전에 묶여야 하고, 서버 재시뮬이 같은 값을 봐야 하기 때문이다.

item_instance(
  id, owner_account_id, catalog_id,
  origin_run_id, floor, node_id, roll_index,   -- 진위의 근거. 이것이 정본
  affixes_json,                                -- 조회 캐시. 재현으로 언제든 재생성
  bound,                                       -- 귀속 여부(거래 불가 플래그)
  verified_at, created_at
)
UNIQUE(origin_run_id, floor, node_id, roll_index)   -- 같은 자리에서 두 번 나올 수 없다

inventory_slot(
  account_id, slot_index,                      -- PK. 인덱스가 곧 칸 번호
  item_id,                                     -- 장비: item_instance 참조
  stack_catalog_id, stack_count,               -- 소모품: 카탈로그 + 개수
  CHECK ((item_id IS NULL) <> (stack_catalog_id IS NULL))
)

equipment_slot(
  account_id, slot,                            -- PK. WEAPON_MAIN|WEAPON_OFF|HEAD|BODY|FEET|HANDS
  item_id
)

quest_pouch(account_id, catalog_id, obtained_at, run_id)   -- 칸 제한 없음 (§4)

character_stat(                                -- 요구조건 판정의 소재 (§7)
  account_id, level, xp,
  stat_json,                                   -- {"str": 15, ...} 축은 데이터가 정한다
  updated_at
)

item_event(id, item_id, kind, account_id, at)  -- 획득·장착·해제·소멸·거래 이력
```

세 가지가 의도적이다.

1. **`inventory_slot` 이 `slot_index` 를 PK 에 넣는다.** 순서를 조회 시점에 정하지 않는다
2. **`item_instance` 에 최종 스탯 컬럼이 없다.** 두면 그 값을 믿게 되고, 위조를 잡을
   근거가 사라진다. `docs/설계/3_저장과_멀티플레이` 의 `run_submission` 에 결과 컬럼을 두지 않은 것과 같은 이유다
3. **`character_stat` 이 장비 보너스를 담지 않는다.** §7 의 순환 차단이 스키마에 박혀 있다

## 15. 드롭 — 등급 · 아이템 · 몬스터 레벨 (개정 2026-08-31)

§8 의 발급 규율(서버만 굴린다)은 그대로다. 바뀌는 것은 **무엇을 굴리는가**다.

### 15.1 지금 무엇이 부족한가

`app/items/loot.py` 는 런 하나당 한 번 굴리고, 후보 전부에서 균등하게 뽑는다.

```python
entry = candidates[get_below(len(candidates))]   # 대검도 단검도 물약도 각 10%
```

세 가지가 없다.

1. **등급이 없다.** 좋은 것과 흔한 것이 구별되지 않아 "좋은 걸 주웠다" 가 성립하지 않는다
2. **아이템마다 나오는 정도가 같다.** 카탈로그에 하나를 더하면 나머지 전부의 확률이 내려간다
3. **누구를 잡았는지가 입력이 아니다.** 런 단위로 굴리므로 몬스터 레벨이 개입할 자리가 없다

### 15.2 굴림을 두 단계로 나눈다 ★

**등급을 먼저 뽑고, 그 등급 안에서 아이템을 뽑는다.**

```
1단계   등급 추첨      레벨·층이 여기에 개입한다
2단계   아이템 추첨    그 등급 안에서 가중치로
```

한 테이블에 섞지 않는 이유가 이 설계의 전부다. 아이템마다 절대 확률을 적어 두면
**보통 등급에 아이템 하나를 더하는 순간 유물 등급의 확률까지 내려간다.** 콘텐츠를 늘리는
일이 밸런스를 흔드는 일이 되고, 그러면 아무도 아이템을 못 늘린다. 두 단계로 가르면
2단계는 그 등급 안의 상대 비율이라, 아이템 추가가 등급 분포를 건드리지 않는다.

몬스터 레벨은 **1단계에만** 개입한다. 레벨이 오르면 상위 등급 쪽으로 분포가 밀린다.
2단계에 개입시키면 "레벨 높은 적이 단검을 더 자주 준다" 같은, 아무도 설명할 수 없는
규칙이 생긴다.

### 15.3 굴림의 단위는 런이 아니라 **처치**다 ★

"몬스터 레벨에 따라 달라진다" 를 성립시키려면 **누구를 잡았는가**가 입력이어야 한다.
재시뮬은 이미 그것을 안다 — `RunSummary.defeated_kinds` 가 처치 하나당 한 항목이다.

레벨은 이 순서로 정한다.

| 순서 | 무엇 | 왜 |
|:-:|:--|:--|
| 1 | 티켓 스냅샷에 그 종이 있으면 그 개체의 레벨 | 지속 몬스터는 개체마다 레벨이 다르다 |
| 2 | 없으면 층에서 파생한 기준 레벨 | 방이 그때 낳은 잡몹에는 개체 레벨이 없다 |

**처치마다 굴리면 굴림 수가 는다.** 그래서 등급별 기본 확률은 지금(런당 60%)보다 훨씬
낮은 값에서 시작해야 한다 — 수식은 나중에 정하지만, 이 사실이 그 수식의 전제다.

### 15.4 등급 (결정 #42)

3등급이다. 표기는 **괘선 굵기**로 한다 — 의미색 셋이 이미 배정돼 등급색을 쓸 수 없다.

| 등급 | 괘선 | 접사 굴림 수 |
|:--|:--|:--|
| `COMMON` 보통 | 1px | 1 |
| `FINE` 상급 | 2px | 1~2 |
| `RELIC` 유물 | 2px + 모서리 | 2~3 |

**등급이 접사 개수를 정한다.** 등급을 이름표로만 두면 「유물 단검」이 「보통 단검」보다
나은 점이 없어 등급이 뜻을 잃는다.

### 15.5 인스턴스가 등급을 복사해 간다 ★

`item_instance.grade` 는 카탈로그를 참조하지 않고 **굴린 시점의 값을 복사**한다.

카탈로그의 등급을 나중에 고치면 이미 나온 아이템의 등급까지 소급해 바뀐다. 접사에서
이미 같은 함정을 겪었다 — 인스턴스가 굴린 접사가 없으면 카탈로그 기본값을 쓰므로,
카탈로그를 고치면 남의 가방에 있는 아이템의 성능이 바뀐다. 등급은 그 실수를 반복하지
않는다.

### 15.6 보완 — 수식보다 먼저 있어야 하는 것

| # | 무엇 | 없으면 |
|:-:|:--|:--|
| D1 | **등급별 최소 층** | 1층에서 유물이 나오면 깊이 들어갈 이유가 없다 |
| D2 | **천장(pity)** — 연속 미획득이 쌓이면 등급 분포가 밀린다 | 운이 나쁜 사람이 이탈한다. 확률만으로는 "나는 안 나온다" 를 못 막는다 |
| D6 | **천장이 곡선의 주도권을 쥔다** (§15.10) | 확률을 고쳐도 체감이 안 바뀐다 — 실제로 주는 것은 천장이다 |
| D3 | **드롭 테이블을 소스별로** | 특정 몬스터만 떨구는 것이 없으면 도감이 표적 목록이 되지 못한다 |
| D4 | **굴림 기록** — 입력(레벨·층·표 세대)과 결과를 원장에 남긴다 | 확률이 맞는지 사후에 증명할 수 없다. 문의가 오면 답이 없다 |
| D5 | **가방이 가득 찼을 때** | 지금은 조용히 놓친다. 놓친 사실이 원장에 남아야 한다 |

D2 는 **굴림 상태를 계정에 저장해야** 성립한다 — 그래서 스키마에 들어간다. 수식은
나중에 정해도 자리는 지금 만든다.

### 15.7 카탈로그가 DB 로 간다 — 그 대가

관리자가 아이템 종류를 조회·등록·폐기할 수 있어야 한다. 아이템 카탈로그는 **브라우저
코어가 읽지 않는 유일한 자산**이라(로드아웃으로 합산돼 티켓에 얼려 들어간다) 런타임
이관이 가능한 유일한 것이기도 하다.

대가가 둘이고, 둘 다 막아 둔다.

1. **골든·헤드리스가 DB 를 요구하게 된다.** `scripts/export_items.py` 가 DB → `items.json`
   스냅샷을 내보내고, 코어와 골든은 그 파일을 읽는다. 정본은 DB, 파일은 파생물이다
2. **삭제하면 과거 기록이 안 읽힌다.** `item_instance.catalog_id` 와 원장·경매가 그 id 를
   가리킨다. 삭제는 없다 — `is_retired` 로 **새로 안 나오게만** 한다

**수정은 새 id 로 한다.** 접사·등급을 고치면 이미 나온 아이템이 소급해 바뀌므로,
"새 id 등록 + 옛 id 폐기" 가 유일하게 안전한 수정 경로다.

### 15.8 세대와 코어 버전

카탈로그가 바뀌면 `catalog_generation` 이 오른다. 그 값이 `core_version` 의 `i` 축이며,
스냅샷 파일의 `item_list_version` 으로 내보내진다. 관리자가 아이템을 고치는 것은
**시즌을 가르는 일**이고, 그 사실이 코어 버전 문자열에 남아야 한다.

### 15.9 스키마

```sql
item_grade(code, rank, label_ko, affix_min, affix_max)      -- COMMON|FINE|RELIC

item_catalog(
  catalog_id PK, kind, slot, hands, grade, label_ko,
  tags_json, affixes_json, requirements_json, grants_skill,
  min_floor,                                  -- D1. 이 층부터 나온다
  is_retired,                                 -- 삭제 대신 폐기 (15.7)
  created_at, updated_at
)

catalog_generation(id=1, generation, updated_at)            -- 15.8. 한 줄짜리 표

drop_source(id PK, kind, ref_id)             -- kind: MONSTER_KIND | FLOOR | ANY
drop_grade_weight(source_id, grade, weight, level_scale_pct)  -- 1단계. 레벨이 여기 개입
drop_item_weight(source_id, grade, catalog_id, weight)        -- 2단계. 등급 안의 비율

drop_pity(account_id, grade, misses)          -- D2. 연속 미획득
item_roll_log(id, account_id, submission_id, source_kind, source_ref,
              monster_level, floor, generation, grade, catalog_id, detail)  -- D4
```

`drop_item_weight` 가 `(source_id, grade)` 로 묶이는 것이 15.2 의 두 단계를 스키마에
박아 둔 것이다. 아이템을 하나 더해도 그 줄의 가중치만 늘어날 뿐, 등급 분포가 있는
`drop_grade_weight` 는 손대지 않는다.


## 16. 아이템 밖의 콘텐츠 — 발행 파이프라인 (2026-08-31)

§15.7 이 아이템 카탈로그를 DB 로 옮긴 근거는 **브라우저 코어가 그것을 안 읽는다**는
것이었다. 나머지 자산은 반대다.

| 자산 | 브라우저가 읽는가 | 정본 |
|:--|:-:|:--|
| 아이템 카탈로그 | ✗ | **DB** (런타임에 바뀐다) |
| 스킬·블록·밸런스·룸·적 규칙표 | ○ | **파일** (배포해야 바뀐다) |

브라우저는 이 파일들을 **빌드 시점에 번들로 인라인한다.** 런타임에 DB 를 보게 만들면
서버가 없을 때 게임이 안 돌고, 그것은 이 저장소가 지키는 전제다. 그래서 흐름을 셋으로
가른다.

```
1. 편집   관리자가 초안을 DB(content_draft)에 저장한다 — 게임에는 아무 영향이 없다
2. 검증   코어가 쓰는 그 로더로 읽어 본다. 여기서 막히면 배포가 서버를 죽였을 것이다
3. 발행   운영자가 파일로 내보내고, 커밋·배포해야 실제로 반영된다
```

### 16.1 발행이 라우트가 아닌 이유 ★

**자동으로 반영되면 순위표 시즌이 아무도 모르게 갈린다.** 스킬 계수 하나를 고치는 것은
저장된 리플레이 전부를 무효로 만드는 일이고, 그 무게가 사람 손을 한 번 타야 한다.

기술적 이유도 있다. 서버가 파일을 고쳐도 **브라우저 번들은 그대로다.** 배포를 거치지
않으면 두 코어가 다른 데이터로 돌고, 그것이 G3 가 잡으려는 바로 그 상태다.

### 16.2 검증기를 따로 만들지 않는다 ★

초안은 **코어가 쓰는 그 로더**로 읽어 본다. 검증기가 둘이면 규칙이 둘이 되고, 검증은
통과하는데 배포하면 서버가 안 뜨는 날이 온다 — 그때는 이미 파일이 커밋된 뒤다.

버전도 함께 본다. 안 올리고 발행하면 저장된 리플레이가 조용히 거짓이 된다.

### 16.3 쓰는 법

```bash
# 편집·검증은 관리자 화면(POST /api/admin/content/draft)이 한다.
docker compose run --rm ops uv run python -m scripts.publish_content
docker compose run --rm ops uv run python -m scripts.publish_content --asset skills --apply
git add game/resources && git commit && <배포>
```


## 15.10 실측 — 천장이 유물의 대부분을 준다 (2026-08-31)

`scripts/report_drops.py` 로 지금 표를 쟀다. 런당 처치 수는 원장 실측 15.4회다.

| 레벨 | 굴림당 | 런당 | 유물 확률 | 첫 유물 (천장 없이) | **첫 유물 (천장 포함)** |
|:-:|:-:|:-:|:-:|:-:|:-:|
| 1 | 3.7% | 0.57개 | 0.045% | 144판 | **중앙값 26판** · 90%가 81판 |
| 10 | 4.1% | 0.63개 | 0.067% | 97판 | **중앙값 18판** · 90%가 73판 |

**천장을 빼고 재면 완전히 다른 그림이 나온다.** 확률만 보면 유물은 144판에 한 번이라
사실상 없는 등급이고, 천장을 이어서 재면 26판이다. 즉 **유물의 대부분은 확률이 아니라
천장이 준다.**

이것은 결함이 아니라 선택이다. 다만 그 선택의 결과가 하나 있다 — **유물 확률을 두 배로
올려도 체감이 거의 안 바뀐다.** 주는 것이 확률이 아니기 때문이다. 유물이 나오는 속도를
바꾸려면 손댈 곳은 `PITY_STEP` 과 `PITY_CAP_PCT` 이지 등급 가중치가 아니다.

**지금 값을 바꾸지 않는다.** 밸런스 목표(결정 #21)가 미결이고, 목표 없이 숫자를 고치는
것은 밸런스가 아니라 취향이다. 곡선 자체는 뒤틀린 데가 없다 — 런당 0.6개는 예전(런당
60%)과 같은 체감이고, 첫 유물 26판은 "언젠가 나온다" 가 실제로 성립하는 거리다.

측정 도구를 남겨 두는 것이 이 절의 결론이다. #21 이 정해지면 그때 이 표를 다시 찍는다.
