# 클라이언트 변조 방지

> 범위: 프런트엔드에서 데이터를 조작하는 경로와 그 방어.
> 상태: 설계. **지금은 서버가 없어 실효 노출이 없다** — §1 이 그 이유를 다룬다.
> 저장 계층은 `설계/3_저장과_멀티플레이`, 결정 항목은 `결정/1_결정대기목록`.

## 0. 전제 — 클라이언트는 적대적이다

브라우저에서 도는 코드는 **전부 조작 가능하다.** 예외는 없다.

- `localStorage` 는 개발자 도구로 자유롭게 편집된다
- JS 런타임은 패치된다 — 함수 후킹, `Math.random` 대체, 프로토타입 오염
- 네트워크 요청은 위조된다. 앱을 거치지 않고 API 를 직접 부를 수 있다
- TS 코어는 **통째로 다른 구현으로 바꿀 수 있다**

그래서 방어의 형태는 하나뿐이다.

> **클라이언트가 보낸 것을 검증 없이 저장하지 않는다.**
> 막는 것이 아니라, 조작해도 **소용이 없게** 만든다.

## 1. 지금은 노출이 없다 — 그리고 그것이 함정이다

현재 저장되는 것은 브라우저 `localStorage` 하나뿐이고, 서버는 자리표시자다.
**지금 데이터를 조작하는 것은 자기 세이브 파일을 고치는 것**이며, 싱글 플레이 치트다.
남에게 영향이 없으므로 문제가 아니다.

노출은 **서버가 생기는 순간** 시작된다 — 랭킹 · 거래 · 지속 몬스터. 셋 다 남의 경험에
영향을 준다.

**함정은 이것이다.** 서버를 붙이기 전에 쌓인 데이터는 전부 조작 가능한 상태로 쌓인다.
나중에 그것을 서버로 옮기면 **그때까지의 모든 아이템·레벨·기록을 신뢰할 수 없다**
(`설계/3_저장과_멀티플레이` §9). 방어는 서버와 함께 오지만, **그 준비는 지금 해야 한다** (§6).

## 3. 결정론이 대부분을 무료로 막는다 ★

이 프로젝트에는 대부분의 게임에 없는 것이 있다 — **두 코어가 비트 단위로 같다**(G3).
그래서 서버가 클라이언트의 주장을 **재계산해 대조**할 수 있다.

```
클라이언트 제출  →  {티켓 id, 규칙표, 코어 버전}     ← 결과가 없다
서버            →  Python 코어로 재시뮬 (런당 ~94ms)
                →  결과를 서버가 확정. 클라이언트의 주장은 저장하지 않는다
```

| 위협 | 방어 | 상태 |
|:-:|:--|:--|
| T1 | **재시뮬.** 제출 스키마에 결과 필드 자체가 없다 (§4) | 설계됨 |
| T2 | **시드 서버 발급** + 티켓 만료 + 티켓당 1회 제출 | `결정/1_결정대기목록` #01 |
| T3 | 획득 경로 재현 검증 + `UNIQUE(run, floor, node, roll)` | `설계/4_아이템` §8 |
| T4 | `entity_record.stat_json` 은 서버가 정본. 클라이언트 값을 안 받는다 | 스키마 |
| T5 | **재시뮬이 불일치를 잡는다** → `verdict = mismatch` | 설계됨 |
| T6 | `ticket_id` 당 제출 1회. 티켓은 1회용이고 만료가 있다 | 스키마 |
| T7 | 서버가 `validator.py` 를 **다시** 돌린다 | 코드 재사용 |
| T8 | **스냅샷을 클라이언트가 보내지 않는다.** 서버가 `ticket_id` 로 조회 | §4 |
| T10 | 서버 시각만 신뢰한다. 티켓 발급·만료가 서버 시각 | 설계 |
| T12 | 원장 분석 + 귀속(`bound`) 규칙 | #07 · #34 |

**T1·T5·T7 을 재시뮬 하나가 함께 막는다.** 클라이언트가 코어를 어떻게 조작하든,
서버가 같은 입력으로 다시 돌려 다른 답이 나오면 그것으로 끝이다.

## 4. 제출 스키마의 규율 — 이 문서에서 가장 중요한 한 줄

```
run_submission = { ticket_id, ruleset_json, core_version }
```

| 없는 것 | 왜 |
|:--|:--|
| 결과 | 서버가 계산한다. **자리를 두면 언젠가 그것을 믿는 지름길이 생긴다** |
| 시드 | 티켓에 있다. 받으면 T2 가 열린다 |
| 몬스터 스냅샷 | 티켓에 있다. 받으면 T8 이 열린다 |
| 아이템·능력치 | 서버가 파생·보관한다. 받으면 T3·T4 가 열린다 |

> **클라이언트가 보낸 것 중 서버가 저장하는 것은 `ruleset_json` 하나뿐이고,
> 그것마저 검증기를 통과해야 한다.**

이 규율은 **스키마에 박아야 한다.** 문서에만 적으면 "재시뮬이 느리니 이번만" 이라는
지름길이 반드시 생긴다. 컬럼이 없으면 그 지름길을 낼 수 없다.

## 5. 재시뮬이 못 잡는 것 — 정직하게

재시뮬은 **거짓말을 잡지만 선택은 못 잡는다.**

| # | 못 잡는 것 | 왜 | 완화 |
|:-:|:--|:--|:--|
| T9 | **의도적 패배** | 나쁜 규칙표로 지는 것은 위조가 아니라 플레이다. 구분할 방법이 없다 | 몬스터 XP 를 처치한 플레이어의 레벨·장비에 비례시키지 않는다. 같은 계정의 반복 사망은 XP 체감 |
| T2 | **부분적으로 남는다** | 티켓을 여러 개 받아 유리한 것만 완주하고 나머지를 버릴 수 있다 | 티켓 발급 레이트 리밋 · **미완주 티켓을 기록** · 데일리는 1일 1티켓 |
| T11 | **봇** | 재시뮬로는 사람인지 가릴 수 없다. 봇의 런도 정당한 런이다 | 레이트 리밋 · 이상 패턴 탐지 · 보상 체감 |
| — | **정보 우위** | 클라이언트는 제출 전에 결과를 안다 | 오토배틀의 본질이다. T2 완화와 같은 수단으로만 줄어든다 |

**T9 가 몬스터 시스템의 실제 위험이다.** "내 몬스터를 키우려고 일부러 죽는다" 는
`설계/6_몬스터` §3 의 경험치 설계와 직결되고, 기술이 아니라 **밸런스로 풀어야 한다.**

착각하면 서버 검증을 빠뜨린다. **둘 다 있어야 하고 역할이 다르다.**

## 7. 난독화·안티치트에 대한 입장

**하지 않는다.**

- 코드 난독화는 시간을 벌 뿐 막지 못한다. 비용 대비 효과가 낮다
- 코어를 WASM 으로 옮겨도 같다. 입력과 출력이 보이면 대체할 수 있다
- **이 게임은 그것이 필요 없다.** 재시뮬 검증이 있으면 클라이언트가 무엇을 하든 상관없다

오히려 **코어가 읽히는 편이 낫다.** 이 게임은 플레이어가 규칙을 설계하는 게임이고,
커뮤니티가 시뮬레이터·최적화 도구를 만드는 것이 콘텐츠다. 숨겨서 얻을 것이 없다.

**숨겨야 하는 것은 코어가 아니라 시드다.** 그것만 서버가 쥔다.

## 8. 탐지와 대응

`verdict = mismatch` 는 **치트의 증거가 아니다.**

불일치의 원인은 최소 셋이다 — 클라이언트 변조 · **코어 버전 불일치** · **우리 쪽 버그**.
세 번째가 실제로 있었다: 쿨타임이 설정되지 않아 모든 밸런스 측정이 무효였던 적이 있고,
그때 두 코어는 같은 값으로 틀렸다.

| 원칙 | 내용 |
|:--|:--|
| 자동 밴 금지 | `mismatch` 는 조사 대상이지 처벌 대상이 아니다 |
| 불일치 지점을 남긴다 | 어느 틱·어느 필드에서 갈렸는지. 버그 추적에 그대로 쓰인다 |
| 버전을 먼저 본다 | 클라이언트 `core_version` 이 서버와 다르면 변조가 아니라 배포 시차다 |
| 누적으로 판단 | 한 건이 아니라 계정 단위 반복 패턴 |

**불일치 로그는 안티치트이자 회귀 검증 도구다.** 두 코어가 갈리는 지점을 실사용에서
잡아 주며, 이것이 G3 게이트가 못 보는 구간을 덮는다.
