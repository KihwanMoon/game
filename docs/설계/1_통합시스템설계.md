# 통합 시스템 설계

> 전체 아키텍처의 통합 뷰. 시스템별 세부는 `설계/3_저장과_멀티플레이`·`설계/4_아이템`·`설계/5_스킬`·`설계/6_몬스터`·`설계/7_변조방지`, 기술 정본은 `02 TDD` 다.
> 여기서만 있는 것: **결정론 경계의 전체 그림**, **통합 스키마**, **통합 도입 순서**.

## 1. 아키텍처 전경

```
 브라우저                              서버                       원장
┌──────────────────────┐   티켓 요청   ┌──────────────┐        ┌────────────┐
│ React UI             │ ───────────→ │ 티켓 발급     │        │ 계정·메타   │
│  규칙 에디터          │              │  시드         │        │ 아이템      │
│  전투 관전            │ ←─────────── │  몬스터 스냅샷 │        │ 몬스터      │
│  사후 분석            │   티켓        │  코어 버전    │        │ 거래·랭킹   │
│ ┌──────────────────┐ │              └──────────────┘        └────────────┘
│ │ TS 코어 (이식)    │ │   제출        ┌──────────────┐              ↑
│ │  RuleVM · 틱엔진  │ │ ───────────→ │ Python 코어   │              │
│ │  RNG · 그리드     │ │  시드+규칙표   │  **재시뮬**   │ ── 검증됨 ──→│
│ └──────────────────┘ │  (결과 아님)   │  결과를 확정  │              │
└──────────────────────┘              └──────────────┘        ┌────────────┐
        L1 localStorage                      ↑                │ 배치 시뮬   │
                                             └────────────────│ 몬스터 전투 │
                                                              └────────────┘
```

**서버는 결과를 받지 않는다. 입력을 받아 다시 계산한다.**
클라이언트는 적대적이라고 전제한다 — 위협 모델과 방어는 `설계/7_변조방지`. 이것이 가능한 이유는 두 코어가
비트 단위로 같기 때문이고(게이트 G3), 그 성질은 R5 하나에 걸려 있다.

## 2. 결정론 경계 — 무엇이 런의 입력인가

이 등식이 시스템 설계의 전부다. **시스템을 더할 때마다 이 등식이 유지되는지 먼저 묻는다.**

| 단계 | 등식 | 등식이 바뀌었나 |
|:--|:--|:--|
| 현재 | `결과 = f(시드, 규칙표, 코어버전)` | — |
| + 아이템 | `결과 = f(시드, 규칙표, 코어버전, **로드아웃**)` | **바뀐다.** 아이템의 *생성*은 시드에서 파생하지만 **어느 것을 끼고 있는지**는 서버가 아는 세계 상태다 |
| + 스킬 | `결과 = f(시드, 규칙표, 코어버전, **로드아웃**)` | **바뀐다.** 무엇을 장착했는지가 장비에서 나오므로 같은 자리에 실린다 |
| + 지속 몬스터 | `결과 = f(시드, 규칙표, 코어버전, 로드아웃, **스냅샷**)` | **바뀐다.** 세계 상태는 시드에서 나오지 않는다 |

세계 상태 두 가지가 등식을 바꾼다 — **상대가 누구인가**(스냅샷)와 **내가 무엇을 끼고
있는가**(로드아웃). 둘 다 시드에서 나오지 않고 서버만 알며, 전투는 브라우저가 돈다.
그래서 둘 다 **런 티켓에 얼려 넣어** 입력의 일부로 만든다 (`설계/6_몬스터` §5, 결정 #13).
그러면 재시뮬·리플레이·오프라인 플레이가 전부 살아남는다.

이 처음 설계에서는 아이템이 등식을 안 바꾼다고 적었는데, 그것은 **아이템이 시드에서
나온다**는 사실만 보고 **장착 상태는 시드에서 나오지 않는다**는 것을 놓친 판단이었다.
클라이언트가 장착 상태를 보내게 두면 변조로 스탯을 올릴 수 있고(`설계/7_변조방지`),
안 보내면 화면과 서버가 다른 캐릭터로 싸운다. 티켓에 싣는 쪽만 둘 다 만족한다.

### 코어 버전의 구성

`core_version` 은 하나의 값이 아니라 세 값의 조합이다. **하나라도 바뀌면 과거 기록이
재현되지 않으므로 랭킹 시즌이 갈린다** (`설계/3_저장과_멀티플레이` §7).

```
core_version = (block_list_version, balance_version, engine_version)
                 블록 카탈로그        수치            로직
```

**블록을 파라미터화한 이유가 이것이다** (`설계/5_스킬` §4). 스킬을 하나 추가할 때마다
`block_list_version` 이 오르면 시즌이 계속 갈린다. `USE_SKILL[skill_id]` 로 묶으면
스킬이 늘어도 액션 종류는 그대로다.

### 절대 어기지 않는 것

| 금지 | 이유 |
|:--|:--|
| `random`·`os.urandom`·시스템 시간 | 코어의 모든 무작위는 `DeterministicRng` 를 거친다 |
| 집합·딕셔너리 순회로 게임 상태 생성 | 순서가 보장되지 않는다. 정렬된 시퀀스를 쓴다 |
| 부동소수 | 확률은 정수 비교 — `rng.get_below(100) < 30` |
| 축을 안 가른 난수 | `create_stream(label)`. 한 축의 호출 횟수 변화가 다른 축을 흔든다 |
| TS 에서 `Number` 로 64비트 | 53비트라 SplitMix64 가 깨진다. `BigInt` 를 쓴다 |
| 연산 순서를 정하지 않은 합산 | 클램프가 끼면 순서가 결과를 바꾼다 (`설계/4_아이템` §9) |

## 3. 모듈 지도

```
game/
├─ main.py                컴포지션 루트
├─ schemas/               I/O 계약 — TS 로 이식되는 유일한 자산
│  ├─ blocks · ruleset · room · floor_map · meta_save · preset_code   [있음]
│  ├─ item.py · inventory.py                                          [신설 09]
│  ├─ skill.py                                                        [신설 10]
│  └─ entity_record.py                                                [신설 12]
├─ app/
│  ├─ core/               도메인을 모른다 — RNG · 이벤트 로그 · 에러      [있음]
│  ├─ grid/               타일 · LOS · 포위도                          [있음]
│  ├─ pathfinding/        가중 Dijkstra · 거리장                       [있음]
│  ├─ rules/              RuleVM · 검증기 · 폴백                       [있음]
│  ├─ combat/             피해 수식                                    [있음]
│  ├─ simulation/         틱 7페이즈 · 텔레그래프 · 스케일               [있음]
│  ├─ items/              카탈로그 · 접사 굴림 · 요구조건 · 스탯 합산     [신설 09 §11]
│  ├─ skills/             계열별 효과 실행기                            [신설 10 §9]
│  ├─ monsters/           등급 · 성장 · 경험치 · 스냅샷                  [신설 12]
│  └─ services/           유스케이스. 파일 하나가 시나리오 하나          [있음+신설]
└─ resources/
   ├─ balance/  blocks · balance                                      [있음]
   │            skills.json · items.json                              [신설]
   ├─ rooms/    templates                                             [있음]
   └─ rulesets/ g0_examples · enemies · benchmark                     [있음]
```

**의존은 한 방향으로만 흐른다.** `items/`·`skills/`·`monsters/` 는 `simulation/` 을
모른다. 반대로 `simulation/` 이 확정된 스탯을 받아 `Entity` 를 만든다.

**착용·장착은 전투 밖에서만 일어난다** (규칙 편집은 방 사이에서만 — GDD §2.2).
그래서 틱 엔진은 아이템·스킬 카탈로그를 모르고, 전투 성능에 영향이 없다.

배치 기준은 하나다 — **"이것이 우리 도메인을 아는가."** 모르면 `core/`,
하나만 알면 도메인 모듈, 여러 개를 엮으면 `services/`.

## 4. 데이터 흐름

### 틱 (7페이즈 · TDD §4.1)

| 페이즈 | 하는 일 | 새 시스템이 얹히는 곳 |
|:--|:--|:--|
| UPKEEP | 쿨타임·상태 감소, 재생 | 스킬 지속효과 |
| TELEGRAPH | 예고 타일 게시 | 플레이어 스킬도 예고를 쓸지 (`결정/1_결정대기목록` #19) |
| PERCEPTION | 인지 스냅샷 | 장비·스킬 인지 블록 (`설계/4_아이템` §10, `설계/5_스킬` §4) |
| DECIDE | 규칙 평가 → 계획 | `USE_SKILL[id]` · 미장착이면 **불가** 상태 |
| ACT | 실행 (사거리·쿨타임 재검증) | 스킬 계열별 실행기 |
| RESOLVE | 피해·회복·상태 적용 | 스킬 효과 · 아이템 스탯 |
| CLEANUP | 사망·만료 | 경험치 적립 · 아이템 이전 (`설계/6_몬스터` §4) |

PERCEPTION 과 DECIDE 를 가른 이유는 동시성 공정성이다. ACT 에서 다시 검증하는 이유도
같다 — 스냅샷 이후 상대가 움직였을 수 있다.

### 런 (검증 포함)

```
1. 클라이언트 → 서버   런 시작 요청
2. 서버 → 클라이언트   run_ticket {시드, 몬스터 스냅샷, 코어 버전}
3. 브라우저            TS 코어로 전투. 방마다 규칙 편집·보상 선택
4. 클라이언트 → 서버   run_submission {티켓 id, 규칙표, 코어 버전}   ← 결과는 안 보낸다
5. 서버                Python 코어로 재시뮬 (~94ms)
6. 서버                run_result 확정 → verdict
7. 서버 (verified 만)  메타 갱신 · 아이템 발급 · 몬스터 경험치 · 랭킹
```

**4번에 결과 필드를 두지 않는 것이 설계다.** 자리가 없어야 "재시뮬 느리니 그냥 믿자"
는 지름길이 안 생긴다.

## 5. 저장 — 3계층과 통합 스키마

| 계층 | 어디 | 무엇 |
|:--|:--|:--|
| **L1** | `localStorage` | 편집 중 규칙표 · UI 설정 · 오프라인 캐시 |
| **L2** | 서버 DB | 계정 · 메타 · 아이템 · 몬스터 |
| **L3** | 서버 DB (append-only) | 거래 · 랭킹 · 경험치 원장 |

```sql
-- 계정과 진행
account(id, handle, created_at)
meta_save(account_id, best_floor, slot_cap, unlocked_perceptions[],
          unlocked_actions[], bestiary[], presets[8], core_version, updated_at)

-- 개체 — 플레이어와 몬스터가 같은 레코드 (12 §7)
entity_record(id, kind, owner_account_id, catalog_id, tier, persistence,
              level, xp, stat_json, ruleset_json, rule_slots, cpu_budget,
              origin_run_id, spawn_seed, zone_id, floor, alive, updated_at)

-- 런과 검증
run_ticket(id, account_id, seed, floor, mode, issued_at, expires_at)
monster_snapshot(ticket_id, entity_id, state_json)          -- 12 §5 봉인
run_submission(id, ticket_id, ruleset_json, core_version, submitted_at)
run_result(submission_id, outcome, ticks, player_hp, cleared_rooms,
           verified_at, verdict)                            -- verified|mismatch|rejected

-- 아이템
item_instance(id, owner_entity_id, catalog_id,
              origin_run_id, floor, node_id, roll_index,    -- 진위의 근거
              affixes_json, bound, verified_at, created_at)
  UNIQUE(origin_run_id, floor, node_id, roll_index)
inventory_slot(entity_id, slot_index, item_id, stack_catalog_id, stack_count)
equipment_slot(entity_id, slot, item_id)                    -- 6슬롯
quest_pouch(account_id, catalog_id, obtained_at, run_id)
item_event(id, item_id, kind, entity_id, at)

-- 원장 (L3)
monster_kill(id, entity_id, victim_kind, victim_id, run_result_id, xp_gained, at)
trade(id, from_account, to_account, item_id, offered_at, settled_at, state)
leaderboard(mode, core_version, account_id, score, run_result_id, rank_at)
```

의도적인 것 넷:

1. **`entity_record` 하나로 플레이어와 몬스터를 담는다.** 아이템·장비·인벤토리가
   `entity_id` 를 참조하므로 "몬스터가 내 장비를 들고 있다" 가 특수 케이스가 아니다
2. **`item_instance` 에 최종 스탯 컬럼이 없다.** 두면 그 값을 믿게 되고 위조를 못 잡는다
3. **`entity_record.stat_json` 이 장비 보너스를 담지 않는다.** 요구조건 순환 차단이
   스키마에 박혀 있다 (`설계/4_아이템` §7)
4. **`inventory_slot` 이 `slot_index` 를 PK 에 넣는다.** 순서를 조회 시점에 정하지 않는다

정적 카탈로그(`items.json`·`skills.json`·`blocks.json`)는 **DB 가 아니라 리소스**다.
코어 버전에 묶여야 하고, 서버 재시뮬이 같은 값을 봐야 한다.

## 6. 통합 도입 순서

네 문서의 순서를 하나로 합쳤다. **결정이 필요 없는 것과 필요한 것을 갈랐다.**

### A. 지금 바로 — 결정 대기 없음 ✅ **완료**

| | 내용 | 결과 |
|:-:|:--|:--|
| A1 | **메타 프로그레션 배선** (해금·도감·최고 층) | TS 이식 + 화면. 파이썬 결산과 골든 대조 |
| A2 | 스킬을 데이터로 분리 (`skills.json`) | 값 그대로라 골든 불변. 합치는 자리는 로더 하나 |
| A3 | 아이템 카탈로그·요구조건·스탯 합산 (`app/items/`) | 접사 굴림은 제외 — #02 동결 대기 |
| A4 | 시드 티켓 이음매 | 발급 서버만 남았다. **시드 상한 2⁵³−1 이 이식 제약으로 드러났다** |

### B. 서버 골격 ✅ **완료**

| | 내용 | 결과 |
|:-:|:--|:--|
| B1 | 계정 + 메타 세이브 L2 이전 | 익명 계정 + 기기 토큰(해시 저장). 프런트가 부팅에 계정을 확보하고 세이브를 합친다 — **합치기는 최대값·합집합이라 멱등** |
| B2 | 재시뮬 검증 파이프라인 | 시드는 서버가 발급, 티켓은 1회용, 제출에 결과 자리 없음. 재시뮬로 확정 |

스택은 PostgreSQL · FastAPI · 동기 검증이다. 코어는 여전히 의존성이 0개이며, 부르는
껍데기(`game/api/`)에만 붙는다 — Dockerfile 의 `runtime` 과 `api` 계층이 갈려 있다.

**아직 아닌 것**: 메타 세이브를 클라이언트가 보낸 대로 받는다. 검증된 런의 부산물로만
갱신하는 것이 최종 형태이며, 그것은 런 사슬이 서버로 올라온 뒤에 성립한다.
**그 전까지 이 세이브는 순위의 근거가 될 수 없다.**

### C. DSL 확장 — 결정 확정, **파이썬 코어 완료**

| | 내용 | 상태 |
|:-:|:--|:--|
| C1 | 블록 v5 — `USE_SKILL[id]` · `self_skill_ready` · `self_has_skill` | ✅ 기존 블록은 별칭으로 남겼다. **장비 전용 블록은 만들지 않는다**(결정 #13) |
| C2 | 규칙 상태 4번째(**불가**) — `PlannedAction.blocked` → 이벤트 로그 | ✅ 파이썬 |
| C3 | GUARD 계열 실행기 | ✅ `GUARD_BRACE` — 받는 피해를 정수 퍼센트로 줄인다 |
| C4 | **TS 이식 + G3 대조** | ✅ 골든에 `skill_id`·`blocked` 축을 더했다. 반증 셋으로 확인 |
| C5 | 디자인 표기 — 해칭(⧅) + 취소선 | ✅ 저장소 사본. **Design 정본 역이관 필요** |

### D. 아이템 실물 ✅ **완료**

| | 내용 | 결과 |

#### H1 — 지킴이가 5xx 를 못 본다

지킴이 검사 여덟은 **상태 정합성**만 본다. 그래서 `/api/run` 이 제출의 37%에서 500 을
내는 동안 여덟 검사가 전부 OK 였고, 이틀 뒤에 사람이 로그를 보고서야 잡혔다.

**5xx 를 기록하는 곳 자체가 없다.** `game/api/main.py` 에 예외 처리기가 없고, 표에도
`run_submission` 과 `run_result` 뿐이라 「제출이 실패했다」가 어디에도 안 남는다.
`item_roll_log` 처럼 작은 표 하나와 처리기 하나, 그리고 아홉 번째 검사를 붙인다.

**고아 제출을 세는 것으로는 부족하다.** `run_result` 없는 `run_submission` 은 저장 두
지점 **사이**에서 죽은 것만 잡는데, 이번 500 은 둘 다 저장한 **뒤에** 터졌다.

#### H2 — 실행기가 임계 경로인 이유

지금 `USE_SKILL[X]` 는 `action_id = X` 로 풀린 뒤 하드코딩된 이름들과 맞춰 본다
(`ATTACK_ACTIONS` · `AREA_ATTACK` · `HEAL` · `GUARD_BRACE` · `SUMMON`). 새 id 는 어느
분기에도 안 걸리고, 문법 검증도 `check_has_skill` 도 통과하므로 「불가」로도 안 잡힌다 —
**오류도 로그도 없이 사라진다.**

곁들여 같은 개념이 세 곳에 있다: `actions.AREA_ATTACK_RADIUS` 상수 · `balance.json` 의
몬스터 telegraph 절 · `skills.json` 의 `shape`(**읽는 코드가 없다**). 실행기가 이것을
하나로 모은다.

**첫 걸음이 곧 회귀 검증이었다** (2026-09-08 완료). `AREA_ATTACK_RADIUS = 2` 를
`skills.json` 의 `shape.radius` 로 옮겼다 — 값이 같으므로 골든이 안 깨져야 했고, 안
깨졌다(파이썬 978 · 컨테이너 1398 · 프런트 1974, G3 대조 포함).

**곁들여 평행한 딕셔너리 여섯이 없어졌다.** `EngineConfig` 가 `skill_coef_pct` ·
`skill_range` · `skill_cooldowns` · `skill_heal_pct` · `skill_guard_pct` ·
`skill_guard_ticks` 를 따로 들고 있었다. 속성을 하나 더할 때마다 표가 늘었고, 무엇보다
**표끼리 어긋날 수 있었다** — 계수 표에만 있고 쿨타임 표에 없는 스킬은 「쿨타임 0」으로
조용히 돈다. 이제 `skills: dict[str, SkillDef]` 하나다.

**남은 것은 `effects` 배열이다.** 지금은 `coef_pct`·`heal_pct`·`guard_pct` 가 평면
필드로 남아 있어, 「피해를 주면서 둔화도 건다」 같은 스킬을 데이터로 못 적는다.
서리 장판(H5)이 그것을 요구한다.

**TS 는 아직 상수다** (`core/sim/actions.ts`). 둘 다 2 라 지금은 같지만 JSON 만 고치면
조용히 갈린다 — 그 사실을 그 파일에 적어 뒀고, 이식은 H6 다.

#### Ha — 배선은 됐는데 아무도 안 쓰는 축이 셋

접사가 건드릴 수 있는 축은 여덟인데 다섯만 쓰고 있다.

| 안 쓰는 축 | 배선 상태 | 무엇이 열리는가 |
|:--|:--|:--|
| `potion_slots` · `scroll_slots` | `loadout_service.count_slot_bonus` 가 **이미 돈다** | 「스탯 vs 소모품 칸」이 부위마다 선택이 된다. 봉인 슬롯 규율도 이미 지킨다 |
| `attack_range` | 무기의 고정값으로만 쓴다 | 접사로 주면 방어구가 사거리를 건드린다 — 규칙표의 `적거리 <= 사거리` 가 달라진다 (P2) |

**새 코드가 0줄이다.** 지금 부위별로 등급마다 하나뿐이라 고를 것이 없는데(무기만 셋),
이 축들이 **같은 등급 안에 두 번째 선택지**를 만든다. 스탯 막대를 하나 더 놓는 것과
다르다 — 대가가 다른 축에 있어야 선택이 된다.

##### Ha 의 실제 목록 — 9종

원칙 하나다. **같은 등급 안에서 더 큰 수를 주지 않고 다른 대가를 준다.** 큰 수를 주면
고르는 것이 아니라 계산하는 것이 된다.

| 부위 | 등급 | 새 아이템 | 여는 것 | 무엇을 내주는가 |
|:--|:--|:--|:--|:--|
| BODY | 보통 | 주머니 조끼 | `potion_slots` +1 | 방어력이 판금 갑옷보다 낮다 |
| BODY | 상급 | 약사 갑옷 | `potion_slots` +1 · `scroll_slots` +1 | 최대체력이 사슬 갑옷보다 낮다 |
| BODY | 유물 | 술사 갑옷 | `scroll_slots` +2 | 방어력이 보루 갑옷보다 낮다 |
| FEET | 보통 | 등짐 신발 | `potion_slots` +1 | 선공권이 경보 신발보다 낮다 |
| FEET | 유물 | 행상 신발 | `potion_slots` +1 · 선공권 | 최대체력을 깎는다 (저주) |
| HEAD | 상급 | 조준 투구 | **`attack_range` +1** | 방어력을 깎는다 |
| HEAD | 유물 | 원견 투구 | **`attack_range` +1** · CPU | 최대체력을 깎는다 (저주) |
| WEAPON_OFF | 보통 | 보조 단검 | 공격력 · 선공권 | **방패가 아니라 `GUARD_BRACE` 를 못 쓴다** |
| WEAPON_OFF | 상급 | 각인 등불 | `scroll_slots` +1 · CPU | 위와 같다 |

**`attack_range` 접사가 규칙표를 바꾸는 지점이다.** 사거리는 무기가 기본값을 **대체**한
뒤 접사가 그 위에 더해진다(`items/loadout.py` 의 `apply_weapon_range`) — 조준 투구를
쓰면 단검으로도 `적거리 <= 사거리` 가 한 칸 더 멀리서 참이 된다. 무기를 안 바꾸고
규칙표의 뜻이 달라지는 자리이며 P2 를 만족한다.

**오프핸드 둘이 「방패를 포기한다」를 처음으로 선택지로 만든다.** 지금은 오프핸드 셋이
전부 방패라 `GUARD_BRACE` 가 사실상 공짜다 — 안 낄 이유가 없다. 방패가 아닌 오프핸드가
생기면 그때부터 방벽이 **고른 것**이 된다.

칸 상한은 쓰임새마다 5 다(`MAX_SLOTS_PER_TAG`). 기본이 물약 2 · 주문서 1 이므로 위
아이템을 겹쳐도 상한에 안 닿는다 — 닿으면 `list_consumable_slots` 가 잘라 낸다.

**세대를 올린다.** 카탈로그가 바뀌면 `catalog_generation` 이 오르고(§15.8) 그것이
`core_version` 의 `i` 축이다. 시딩이 심은 것이 있으면 자동으로 오른다 (2026-09-08).

#### Hb 와 §2.2 — 방어구가 스탯 막대인 진짜 이유

투구·갑옷·신발은 셋 다 스킬을 안 열고 스탯만 준다. GDD §6.2 는 *"센서: 특정 인지 변수
해금"* 을 적어 뒀는데 **인지 18개가 전부 열려 있어** 센서라는 개념이 성립하지 않는다.
무엇을 잠글지 고르는 것이 곧 초반 난이도 설계이며, 이것은 구현이 아니라 **결정**이다
(`결정/2_기획공백과_잔여작업` §2.2).

같은 절이 하나 더 짚는다 — **CPU 예산과 슬롯이 거의 동시에 걸려 트레이드오프가 안
생긴다**(실측 규칙표 12개가 CPU 6~8/8, 슬롯 4~5/5). 마법이 CPU 를 먹을지(`설계/5_스킬`
§8 S2)를 정하기 전에 이 둘 중 어느 쪽이 진짜 제약인지가 먼저다.

**임계 경로: H2 → H3 → H4 → H5 → H6 → H7.** 실행기 없이는 나머지가 전부 데이터만
쌓인다.

**임계 경로: A4 → B2 → E4.** 시드 서버 발급 없이는 검증이 없고, 검증 없이는 지속
몬스터가 어뷰징에 열린다.

**D1 과 E4 는 되돌릴 수 없는 지점이다.** 그 전에 `결정/1_결정대기목록` 의 🔴 동결 8건이 정해져야 한다.

전리품 축이 필요하고(`설계/3_저장과_멀티플레이` §4), 그러지 않으면 파생식을 바꿔도 게이트가 침묵한다.

강제 수단은 네 계층이다 — 규칙 문서(쓰기 전) · PostToolUse 훅(파일 하나) ·
`check_all.sh`(저장소 전량, pre-push) · 컨테이너(도구 버전).
**Python 3.11 · uv 0.12.7 · ruff 0.16.3 이 네 곳에 같은 값으로 박혀 있다. 하나를 올리면 전부 올린다.**

## 8. 배포
