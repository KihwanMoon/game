> **게이트 G0:** 규칙표 예시 3개를 손으로 써서 "이 규칙이면 이 방을 클리어한다"가

## 규칙표 예시 3개

제약은 슬롯 5, CPU 예산 8, 비용 1항=1 / 2항=2 / 3항=4 다. 전부 거짓이면 DEFAULT
행동(가장 가까운 적에게 접근)이 나간다(TDD §5.2).

### A. 근접 압박 — `open_field` (슬롯 4 / CPU 6)

```
[1] HP% < 25  AND  포션 > 0                  → 포션 사용                cpu 2
[2] 적거리 <= 1  AND  쿨타임[SKILL_1] 완료    → SKILL_1 @가장가까운적    cpu 2
[3] 적거리 <= 1                              → 기본공격 @가장가까운적    cpu 1
[4] 방 체류 틱 > 35                          → 문/계단으로 이동          cpu 1
                                     (전부 거짓) → 가장 가까운 적에게 접근
```

**종이 위 추적:** 개활지는 엄폐가 없어 포위가 성립한다. 접근 → 인접 → 강타/기본공격
순환으로 돌격병(hp 40)을 4틱에 하나씩 지운다. [4]가 추격자 스폰(당시 40틱, W6 실측 후
20틱 — docs/05)보다 앞서 있어
장기전이 되면 방을 뜬다. **성립한다.**

**약점:** 소환사를 따로 노리지 않으므로 잡몹이 계속 는다. `spring_bait` 처럼
소환사가 있는 방에서는 [4]가 먼저 뜨는 방식으로 도망칠 뿐 이기지는 못한다.

### B. 카이팅 — `corridor` (슬롯 4 / CPU 7)

```
[1] HP% < 30  AND  포션 > 0                   → 포션 사용                cpu 2
[2] 적거리 <= 1                               → 후퇴 @가장가까운적  SET FLAG_A=true   cpu 1
[3] FLAG_A  AND  쿨타임[SKILL_2] 완료          → 사격 @가장가까운적  SET FLAG_A=false  cpu 2
[4] 적거리 <= 4  AND  쿨타임[SKILL_2] 완료     → 사격 @가장가까운적       cpu 2
```

**종이 위 추적:** GDD §3.5 가 예시로 든 구조 그대로다. 통로 방에서 좁은 목으로
물러나면 근접 적이 한 번에 하나만 붙으므로 [2]→[3] 순환이 성립한다. **성립한다.**

**전제:** 플레이어에게 원거리 수단이 있어야 한다. 아래 F-4 참조.

### C. 엄폐 우선 — `pillars` (슬롯 5 / CPU 7)

```
[1] HP% < 30  AND  포션 > 0                       → 포션 사용             cpu 2
[2] 위험 예고 타일 위                              → 엄폐물 뒤로 이동       cpu 1
[3] LOS 노출  AND  적유형존재[RANGED]              → 엄폐물 뒤로 이동       cpu 2
[4] 적거리 <= 1                                    → 기본공격 @가장가까운적  cpu 1
[5] 쿨타임[SKILL_2] 완료                           → 사격 @소환사 유형      cpu 1
```

**종이 위 추적:** 기둥 방에서 [3]이 궁수의 LOS 를 끊고, [5]가 소환사를 먼저 지운다.
[2]가 예고 타일 회피를 맡는다. **성립한다.**

**약점:** [5]에 사거리 조건이 없어 소환사가 4칸 밖이면 헛친다. 아래 F-1 과 같은
문제다 — 조건이 "그 셀렉터가 고를 대상"의 거리를 물을 수 없다.

**세 규칙표가 서로 다른 행동으로 갈린다**(강타 / 후퇴 / 엄폐 이동). GDD §11 의
"단일 정답 수렴 여부" 지표를 볼 최소 조건은 갖췄다.

## 판정 전에 정해야 하는 것 6가지

규칙표를 실제로 써 보면서 나온 것이다. 블록 목록은 "이후 변경 금지"이므로 **동결을
확정하기 전에** 정하는 편이 싸다.

### F-1. 조건이 참조하는 "대상"이 정의되지 않았다 ★ 가장 중요

인지 변수에 `대상 HP%`·`대상이 시전 중인가` 가 있는데, **대상은 행동의 TARGET
셀렉터가 고른다.** 조건은 행동보다 먼저 평가되므로, 조건 평가 시점에 "대상"이
무엇인지 정의가 없다.

예시 C의 `[5] 쿨타임 완료 → 사격 @소환사` 가 이 문제에 걸린다. 소환사가 사거리
밖이어도 규칙이 발동해 틱을 버린다. `적거리` 는 *가장 가까운* 적까지의 거리일 뿐
소환사까지의 거리가 아니다.

선택지:
- (a) 규칙마다 TARGET 을 먼저 확정하고, 조건의 "대상"은 그것을 가리킨다.
- (b) `대상` 계열 인지에 셀렉터 인자를 준다 — `대상거리[TYPE_SUMMONER] <= 4`.
- (c) 그대로 두고 헛치는 것을 플레이어 책임으로 둔다.

(a)가 자연스럽지만 RuleVM 의 평가 순서가 바뀐다. **W2 전에 정해야 한다.**

### F-2. 조건 우변이 리터럴뿐인가

TDD §3.3 의 예시는 `{"rhs": 20}` 처럼 숫자만 보여준다. 그런데 디자인 시트의 규칙 행은
`적거리(2) <= 사거리(3)` 로 **스탯을 우변에** 둔다.

리터럴만 허용하면 사거리가 장비로 바뀔 때 `적거리 <= 1` 이라고 적어 둔 규칙이
조용히 틀린다 — 모듈로 사거리를 늘려도 규칙이 그것을 모른다. 아이템이 "로직 표현력을
확장"하는 축(GDD §6.2)이라는 설계와 어긋난다.

### F-3. 회복타일이 있는지 물을 방법이 없다

행동에 `회복타일로 이동` 이 있는데, 인지에는 `내 위치가 회복타일인가`(이미 위에
있는지)뿐이다. **회복타일이 방에 있는지, 얼마나 먼지 물을 블록이 없다.**

디자인의 규칙 행 상태 시트가 `회복타일(없음) != null → 회복타일로 이동` 을 예시로
쓰고 있어, 디자인은 이 블록이 있다고 전제한다. 인지 18개 동결과 정면으로 충돌한다.

선택지: `가장 가까운 문/계단 거리` 를 `가장 가까운 목표 거리[문|계단|회복타일]` 로
일반화하면 개수를 늘리지 않고 해결된다.

### F-4. 플레이어의 원거리 수단 — 이미 조정했음, 확인 필요

밸런스 초안에서 SKILL_1·SKILL_2 의 사거리를 둘 다 1로 뒀더니 **GDD §3.5 가 대표
예시로 든 카이팅이 성립 불가**였다. 그 예시가 `쿨타임[사격]` 을 전제하기 때문이다.

SKILL_2 를 사거리 4 / 계수 110% / 쿨 2 의 "사격" 으로 바꿨다. 예시 B가 이것에 의존한다.
**이 조정이 의도와 맞는지 확인이 필요하다.**

### F-5. 이동이 4방향인가 8방향인가

`주변 8칸 중 이동 가능 칸 수(포위도)` 는 8칸을 세는데, 이동 자체가 4방향인지
8방향인지 어디에도 없다. 거리 정의(맨해튼/체비셰프)도 여기 딸려 온다 — `적거리 <= 1`
이 대각선 적을 포함하는지가 달라진다.

룸 도달성 검사는 4방향으로 했다. 4방향으로 닿으면 8방향으로도 닿으므로 더 엄격한
쪽이다. **W1 에서 확정해야 한다.**

### F-6. 인자를 받는 블록의 JSON 표현이 TDD 에 없다

`쿨타임[스킬]`·`플래그[A~D]`·`적유형존재[유형]` 은 인자를 받는데, TDD §3.3 의
term 형식에는 자리가 없다. 예시에서 `lhs_param` 을 임시로 더했다. **확정 전이다.**

### S-1 — SUMMON 을 행동에 넣은 이유

GDD §5 는 "몬스터도 플레이어와 완전히 동일한 DSL 로 기술한다" 를 몬스터 설계의 축으로
둔다. 그런데 소환만 `balance.json` 의 kind 속성이었고 엔진이 UPKEEP 에서 처리했다.
결과적으로 **도감이 소환 주기만 규칙표 밖에서 따로 보여줘야 하는 예외**가 생겼고,
그 예외 하나 때문에 "적의 논리를 읽고 카운터를 설계한다" 는 학습 경로가 끊겼다.

주기는 `쿨타임[SUMMON]` 이 맡는다. 새 인지 변수를 만들지 않고 기존 쿨타임 블록의 인자를
하나 늘린 것이라 인지 개수는 18 그대로다.

`ai_summoner` 는 `IF 쿨타임[SUMMON] 완료 AND 대상거리[NEAREST] <= 사거리 THEN SUMMON`
으로 적었다. 조건에 사거리 항을 함께 둔 것이 핵심이다 — 쿨타임만으로 두면 그 규칙이
매 틱 참이 되어 아래 규칙도 DEFAULT(접근)도 영영 평가되지 않고, 소환사가 제자리에
굳어 버린다. 규칙 순서가 결과를 가른다는 §11 의 관찰이 적 규칙표에도 그대로 적용된다.

### F-2 — 조건 우변에 스탯을 허용한 이유

리터럴만 허용하면 `적거리 <= 1` 로 박아 둔 규칙이 모듈로 사거리를 늘린 뒤에도 1 을
본다. 아이템이 로직 표현력을 확장하는 축(GDD §6.2)이라는 설계와 정면으로 어긋난다.

JSON 표현은 `{"rhs": {"stat": "attack_range"}}` 다. 객체 한 겹으로 감싼 이유는 언어
중립성이다 — Phase 3 의 TypeScript 코어가 `typeof rhs === "object"` 만으로 분기할 수
있고, 문자열 우변으로 뒀을 때와 달리 뒷날 문자열 리터럴을 더해도 뜻이 겹치지 않는다.

허용 스탯은 `blocks.json` 의 `rhs_stats` 에 닫힌 목록으로 둔다 — `attack_range`,
`attack`, `defense`, `hp_max`, `cpu_budget`, `potions` 여섯이며 검증기가 그 밖의 이름을
거부한다. 열어 두면 오타 난 스탯이 조용히 거짓이 되어 규칙이 영영 발동하지 않는다.

로그는 GDD §8.2 가 요구하는 형태로 양변에 실측값을 병기한다.

```
T008 | [2] 내 쿨타임[스킬] 완료[SUMMON](참) == 참 AND 대상 거리[NEAREST](3) <= 사거리(3) → SUMMON
```

기존 규칙표 JSON 은 손대지 않아도 그대로 돈다. 리터럴 우변은 v2 와 같은 경로를 탄다.

## 실측 — 규칙표가 결과를 바꾸는가

셋 다 폴백(단순 접근·공격)을 이기고, 낭비 틱이 0이다. 결과 프로파일이 서로 다르다.

| 규칙표 | 방 | 결과 | 폴백 |
|:--|:--|:--|:--|
| `g0_pressure` | open_field | WIN 15틱 HP 52 | LOSS 17틱 |
| `g0_kite` | corridor | WIN 14틱 HP 62 | LOSS 54틱 |
| `g0_cover` | pillars | WIN 20틱 HP 51 | WIN 20틱 HP 23 |

GDD §0 의 주축(퍼즐형 — 성장은 로직 설계 실력으로)이 성립한다는 첫 증거다.

> **Phase 2 W6 통합 후 재측정 (같은 시드 12345).** 위 표는 W1 시점 값이며 그대로
> 둔다 — 판정 기록이기 때문이다. 통합 이후 값은 아래와 같다.
>
> | 규칙표 | 방 | 결과 | 폴백 |
> |:--|:--|:--|:--|
> | `g0_pressure` | open_field | WIN 11틱 HP 51 | WIN 13틱 HP 30 |
> | `g0_kite` | corridor | WIN 14틱 HP 82 | LOSS 34틱 |
> | `g0_cover` | pillars | **LOSS 37틱** | LOSS 22틱 |
>
> `g0_cover` 가 뒤집힌 것은 종이 위 추적(위 C절)이 틀렸기 때문이 아니라, 그 추적이
> 전제한 "[3]이 궁수의 LOS 를 끊고 [5]가 소환사를 지운다"에서 **[3]이 [5]를 굶긴다**
> 는 순서 문제를 놓쳤기 때문이다. LOS 가 실제로 도는 지금 [3]의 조건이 거의 매 틱
> 참이라 [5]까지 평가가 내려가지 않는다. 상세는 docs/05 의 `g0_cover` 절에 있다.
> 아래 F-1 이 잡아낸 것과 같은 종류의 결함이며, 이번에는 종이가 아니라 실측이 잡았다.
