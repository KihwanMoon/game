# 디자인 명세 (통합)

> **토큰의 정본은 Claude Design 프로젝트 `fae25530-140a-4873-b9f9-684645b541c6` 다.**
> `design/` 은 사본이고, 토큰을 고칠 일이 생기면 사본이 아니라 정본을 고쳐 다시 가져온다.
> 컴포넌트 계약과 반응형 실측은 `design/README.md` 에 있다.
> **이 문서만 있는 것**: 새 시스템(아이템·스킬·몬스터)이 디자인에 요구하는 것.

## 1. 성격 — 기계 도면

게임 UI 의 관습을 대부분 쓰지 않는다.

| 규율 | 내용 |
|:--|:--|
| **황동 예산** | `--brass`(#C89A4E)는 화면의 유일한 광원. **한 화면에 3곳까지** |
| **그림자 없음** | 층위는 명도차와 1px 괘선으로만 |
| **4px 모듈** | 그 사이 값은 없다 |
| **등속 모션** | 명도 전환 90ms · 틱 교체 140ms. 바운스·오버슛 금지 |
| **3중 표기** | 참/거짓은 **색 + 글리프 + 명도**. 흑백 인쇄와 색약에서도 구분돼야 한다 |
| 이모지 금지 | 아이콘은 유니코드 도형만 |
| `border-radius` | 2px 고정 |

색 팔레트는 사실상 여섯이다 — `ink` `plate` `plate-high` `rule-line` `chalk` `chalk-dim`
에 의미색 셋(`brass` `verdigris` `rust`)이 얹힌다. **의미색은 예산이 있다.**

## 2. 새 시스템이 디자인에 요구하는 것

### 2.1 규칙 상태가 4종이 된다 ★ 가장 큰 변경

스킬을 정체로 지시하면(`10` §3) 네 번째 상태가 생긴다.

| 상태 | 뜻 | 현재 표기 |
|:--|:--|:--|
| 참·발동 | 조건 참, 이 규칙이 실행됨 | `--verdigris` + 글리프 + 밝음 |
| 참·미발동 | 조건 참, 상위 규칙이 먼저 발동 | `--verdigris` + 글리프 + 어두움 |
| 거짓 | 조건 거짓 | `--chalk-dim` + 글리프 |
| **불가** | **조건 참, 그러나 실행할 수단이 없다** (스킬 미장착) | **없음** |

**거짓과 다르다.** 거짓은 "조건이 안 맞았다", 불가는 "조건은 맞는데 수단이 없다" 다.
플레이어가 고쳐야 할 곳이 완전히 다르므로 구분하지 않으면 P1 위반이다.

**표기 제안 — 색을 쓰지 않는다.** 의미색 셋은 이미 다 쓰였고 황동은 예산이 3곳뿐이다.

```
  참·발동   ▣  녹청 · 밝음
  참·미발동 ▢  녹청 · 어두움
  거짓      ▫  회색
  불가      ⧅  회색 + 해칭(대각선) + 취소선          ← 색을 추가하지 않는다
```

기계 도면에서 **해칭은 "해당 없음"의 관용 표기**다. 성격에 맞고, 색약·흑백에서도
셋과 구분되며, 황동 예산을 건드리지 않는다.

**영향 범위**: `GlyphState.state` · `RuleRow.state` 열거값, 이벤트 로그 `fired` 필드,
그리고 `LogRow` 의 `outcome` 표기. `docs/14` C2 단계에서 함께 바뀐다.

### 2.2 아이템 등급을 색으로 표시할 수 없다

게임의 관습은 등급별 색(흰·초록·파랑·보라·주황)이지만 **이 디자인에는 그 색이 없다.**
의미색 셋은 참/위험/광원에 이미 배정돼 있고, 색은 유일한 채널이 될 수 없다.

**대안 — 괘선과 글리프로 표기한다.**

```
  일반   ┌──────┐   1px 괘선
  고급   ┏━━━━━━┓   1px 이중 괘선
  희귀   ┏━━━━━━┓ + 모서리 표식 ⌐
  전설   ┏━━━━━━┓ + 황동 괘선          ← 황동 예산 1곳 소비. 화면당 3개까지만 표시
```

**전설 등급이 황동 예산을 먹는다.** 인벤토리에 전설이 4개 있으면 규율이 깨진다.
목록에서는 황동을 쓰지 않고 **상세 패널에서만** 쓴다 — 화면당 1곳으로 고정된다.

### 2.3 장비 화면은 인체가 아니라 분해도다

6슬롯(무기 2 · 투구 · 갑옷 · 신발 · 장갑)을 인체 실루엣에 배치하는 것이 관습이지만,
**이 디자인에 인체는 없다.** 기계 도면의 관용 표현은 **분해 조립도(exploded view)** 다.

```
        ┌─────┐
   ⌐────┤HEAD ├────⌐
   │    └──┬──┘    │
┌──┴──┐ ┌──┴──┐ ┌──┴──┐
│HANDS│ │BODY │ │W-MAIN│    각 칸은 4px 모듈 격자
└──┬──┘ └──┬──┘ └──┬──┘    연결선은 1px 괘선
   │    ┌──┴──┐    │
   ⌐────┤FEET ├────⌐       W-OFF 봉인 시: 해칭 + "양손 점유"
        └─────┘
```

양손무기의 `W-OFF` 봉인은 §2.1 의 **해칭 표기를 재사용**한다. 새 표기를 만들지 않는다 —
"해당 없음" 이라는 뜻이 같다.

### 2.4 도감은 위키가 아니라 표적 목록이다

지속 몬스터(`12` §8)가 도감의 성격을 바꾼다.

| 항목 | 표시 |
|:--|:--|
| 규칙표 (현재 레벨) | `RuleTable` 재사용. **읽기 전용 모드가 필요하다** |
| 레벨·성장 이력 | 지난 조우 대비 차분 |
| **장비 — 내 아이템 표시** | 되찾기 동기. **여기에 황동 1곳** |
| 스킬 목록 | 계열 글리프 |
| 마지막 목격 위치 | 층·구역 |

**`RuleTable` 에 읽기 전용 모드가 필요하다.** 지금은 편집 전용이고 `onClick` 이 계약에
있다. 몬스터의 규칙표를 같은 부품으로 보여주는 것이 이 게임의 핵심 장치이므로
(GDD §2.3 — 실패한 런도 자산이 된다) 계약을 넓힌다.

## 4. 컴포넌트 계약 — 추가·확장

기존 계약은 `design/README.md` 에 있다. 새 시스템이 요구하는 변경만 적는다.

| 컴포넌트 | 변경 | 이유 |
|:--|:--|:--|
| `GlyphState` | `state` 에 **`blocked`** 추가 | §2.1 |
| `RuleRow` | `state` 에 **`blocked`** 추가 | §2.1 |
| `RuleTable` | **`readonly`** prop 추가 | §2.4 도감 |
| `LogRow` | `fired` 가 4상태를 표현 | §2.1 |
| `ItemCell` | 신설 — `item, tier, selected, equipped, glyph` | 인벤토리 칸 |
| `SlotFrame` | 신설 — `slot, item, locked, lockReason` | 장비 분해도. `locked` 가 해칭 |
| `RequirementRow` | 신설 — `label, actual, required, met` | **실측값 병기** (§5) |
| `SkillCell` | 신설 — `skill, family, cooldown, ready, equipped` | 스킬 슬롯 |

`_adherence.oxlintrc.json` 이 선언되지 않은 prop 을 막으므로, **컴포넌트를 만들기 전에
이 표에 행을 먼저 추가한다.** 한 행에 두 부품을 적지 않는다 — 그러면 한쪽 props 가
반드시 지워진다(이미 `PlanGrid`/`PlanActor` 에서 겪었다).

## 5. 디자인이 코어에 거는 요구

UI 취향이 아니라 **코어의 출력 계약**이다. 나중에 붙이면 코어를 다시 짜야 한다.

기존 다섯(`design/README.md`)에 새 시스템이 셋을 더한다.

| # | 요구 | 대상 |
|:-:|:--|:--|
| 1 | 조건문에 **각 항의 실측값을 병기** — `적거리(2) <= 사거리(3)` | RuleVM (있음) |
| 2 | 규칙 상태 구분 — 참·발동 / 참·미발동 / 거짓 | RuleVM (있음) |
| 3 | CPU 초과를 오류가 아니라 **수치**로 — `cpu 10 / 8`, 그 상태로 편집 계속 | 검증기 (있음) |
| 4 | 텔레그래프 **남은 틱 수** | 텔레그래프 (있음) |
| 5 | `LogRow` 필드 — `tick, rule, expr, outcome, delta, fired` | 이벤트 로그 (있음) |
| **6** | **규칙 상태 네 번째 — `blocked`(수단 없음)** | RuleVM · 이벤트 로그 |
| **7** | **요구조건도 실측값을 병기** — `힘(12) >= 요구(15)` | 아이템 요구조건 판정 |
| **8** | **몬스터 규칙표를 그대로 내보낸다** (도감·읽기 전용) | 도감 서비스 |

**7번이 중요하다.** "장착할 수 없습니다" 만 띄우면 P1 위반이다. 무엇이 얼마나 모자란지가
화면에 있어야 하고, 그것은 규칙 에디터의 조건문 표기와 **같은 부품·같은 규약**을 쓴다.

## 6. 반응형

- 브레이크포인트는 **`design/tokens/spacing.css` 한 곳에만** 있다
- 데스크톱 골격(320 + 300 + 도면 768)은 **841px 부터** 성립한다.
  600~840px 는 태블릿이 아니라 세로 배치다 (실측: 834px 에서 7px, 768px 에서 73px 넘침)
- `--layout-mode` 를 `useViewportMode()` 가 읽는다
- 터치 타깃은 `--btn-tap-h`/`--btn-tap-sm-h` — 데스크톱 값은 유지하고 터치 레이아웃만 44px
- **앱 셸이 화면을 클립한다.** 안쪽 패널이 저마다 스크롤을 갖는다 —
  문서가 12,327px 로 자라 메뉴가 손이 닿지 않는 곳으로 밀려난 적이 있다

새 화면(인벤토리·장비·스킬·도감)은 **세로 배치 설계를 함께 만든다.** 나중에 붙이면
같은 문제를 반복한다.
