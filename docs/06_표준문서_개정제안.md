# 표준 문서 개정 제안 — RULESET_VERSION 14 → 15

대상: Confluence 라벨 `python-coding-standard` 문서
(제목 「[표준] 파이썬 코드 작성 규칙 및 Claude Code 자동 적용 절차」, RULESET_VERSION 14)

작성 근거: 이 저장소(`game`)에 표준을 실제로 적용해 M3 까지 오면서 게이트·훅·pre-commit 을
전부 돌려 본 결과다. 정본 문서는 Confluence 에 있어 여기서 고칠 수 없다. **이 문서는 개정
제안이며, 저장소 로컬 수정의 사유서이기도 하다**(§11). 로컬 수정 이력은
`.claude/conventions.lock` 에 있다.

판정 기준은 표준 자신의 원칙이다. 특히 §7.1 의 두 문장을 계속 인용한다.

> 검사할 수 없는 규칙을 검사되는 것처럼 적지 마라. (…) 도구가 _존재 여부_만 보는데
> _내용_이 맞다고 믿으면 위반이 조용히 쌓인다 — 애너테이션은 있는데 타입이 틀린 코드,
> 디렉터리 규칙은 있는데 아무도 안 보는 배치가 그 결과다.

> 본 문서가 배포하는 파일도 본 문서의 규칙을 통과해야 한다. (…) 표준이 배포한 파일이
> 표준의 게이트를 깨뜨리면 규칙 전체의 신뢰가 무너진다.

## D1~D4 — 이미 로컬에서 푼 것 (재확인만)

세 건 모두 `.claude/conventions.lock` 에 사유와 함께 기록돼 있다. 여기서는 제안 diff 만
다시 적는다. 넷 다 §8 코드 블록의 결함이며, 규칙 내용이 아니라 **배포된 파일**의 결함이다.
§7.1 이 "본 문서가 배포하는 파일도 본 문서의 규칙을 통과해야 한다"고 적은 대상이 정확히
이것들이다.

### D1 · §8.5 — `python` → `python3`

```diff
-   | xargs -r python tools/check_naming.py; then
+   | xargs -r python3 tools/check_naming.py; then
```

§8.3 의 주석은 같은 함정을 이미 경고한다("다수의 리눅스 배포판은 `python3` 만 제공해
훅이 Executable `python` not found 로 실패한다"). 그 경고가 §8.5 에는 반영돼 있지 않다.
§10.5 2단계의 코드 블록에도 같은 `python` 이 남아 있으므로 함께 고친다.

### D2 · §8.5 — grep 0건이 게이트 실패가 된다

```diff
-if ! git ls-files '*.py' \
-    | grep -v -E '(/tests/|/migrations/|_pb2\.py$)' \
-    | xargs -r python tools/check_naming.py; then
+if ! git ls-files '*.py' \
+    | { grep -v -E '((^|/)tests/|(^|/)migrations/|_pb2\.py$)' || true; } \
+    | xargs -r python3 tools/check_naming.py; then
```

`grep` 은 선택된 줄이 0개면 1 을 반환한다. 이 파이프라인은 `set -o pipefail` 아래이므로
"검사 대상 없음"이 곧 게이트 실패가 된다. 추적 중인 `.py` 가 전부 예외 경로인 저장소는
첫날부터 푸시가 막힌다. §10.5 2단계 블록은 같은 자리에 `|| true` 를 이미 쓰고 있어,
정본 안에서 두 블록이 서로 다른 말을 한다.

### D3 · §8.3·§8.5 — `/tests/` 가 저장소 루트 `tests/` 를 놓친다

```diff
-    --exclude '\.git|\.tox|\.venv|venv|\.direnv|node_modules|/tests/' \
+    --exclude '\.git|\.tox|\.venv|venv|\.direnv|node_modules|(^|/)tests/' \
```
```diff
-        exclude: '(/tests/|/migrations/|_pb2\.py$)'
+        exclude: '((^|/)tests/|(^|/)migrations/|_pb2\.py$)'
```

§8.1 은 같은 대상을 `"**/tests/**/*.py"` 로 올바르게 적는다. §12 의 표준 구조가 `tests/`
를 **저장소 루트**에 두라고 정하므로, 표준을 그대로 따른 저장소가 정확히 이 결함을 밟는다.
§1 이 경고한 "한 곳만 고치면 나머지 경로에서 예외가 동작하지 않는다"가 정본 자체에 있다.
D12 도 같은 뿌리다.

### D4 · §8.3 + §8.5.3 — 두 선택지를 함께 고르면 충돌한다

`core.hooksPath` 가 설정된 상태에서 `pre-commit install` 은
`Cowardly refusing to install hooks with core.hooksPath set` 로 거부한다. §8.3 과 §8.5.3 은
독립 선택지로 제시되지만 §10.2 12단계는 "§8.3 을 도입했다면 `pre-commit install` 도
실행한다"고 적고, 7단계는 `git config core.hooksPath .githooks` 를 실행한다. **정본의 절차를
순서대로 따르면 반드시 실패한다.**

제안: §8.3 에 다음을 덧붙이고 §10.2 12단계에 분기를 넣는다.

```markdown
§8.5.3 의 pre-push 훅을 함께 도입하면 `pre-commit install` 을 쓰지 않는다.
`core.hooksPath` 가 설정된 저장소에서는 pre-commit 이 설치를 거부한다.
대신 `.githooks/pre-commit` 에 아래를 직접 기록한다(내용은 §8.3 과 같다).

    #!/usr/bin/env bash
    if ! command -v pre-commit >/dev/null 2>&1; then exit 0; fi
    exec pre-commit run --config .pre-commit-config.yaml
```

## D5 · §8.9 — `BANNED` 목록이 잘려 있다 (미해결)

**무엇이 문제인가.** PDF 내보내기본에서 §8.9 구조 검사의 9행이 다음에서 끊긴다.

```
BANNED='fastapi|django|flask|tornado|starlette|express|nest|functions|misc|stuff|temp|tmp|etc
```

닫는 작은따옴표가 없다. 뒤에 값이 더 있었는지, `etc` 가 마지막이고 따옴표만 유실된 것인지
PDF 로는 판정할 수 없다. 이 저장소는 확인된 앞부분까지만 담고 `TODO(victor)` 를 남겼다.

**왜 문제인가.** 구조 검사는 §8.9 를 도입한 저장소가 §7 표의 「디렉터리 구조」 행을
「완전 자동」으로 올려 적는 근거다. 근거가 되는 목록이 불완전한 채로 그 행을 올리면
§7.1 이 경고한 착각이 그대로 생긴다.

**제안.** ① Confluence 원문에서 9행 전문을 확인해 문서에 반영한다. ② 재발 방지로,
§8 의 코드 블록 중 한 줄이 지면 폭을 넘는 것들은 개행 이스케이프로 접어 적는다 —
PDF·복사 붙여넣기에서 잘리지 않게 하기 위해서다.

```diff
-BANNED='fastapi|django|flask|tornado|starlette|express|nest|functions|misc|stuff|temp|tmp|etc…'
+BANNED='fastapi|django|flask|tornado|starlette|express|nest'
+BANNED="${BANNED}|functions|misc|stuff|temp|tmp|etc"
```

**우선순위 P1.** 게이트를 막지는 않지만 원문 유실이라 시간이 지날수록 복원이 어렵다.

## D6 · §2.1 — 동사 목록에 `move` 가 없다

**무엇이 문제인가.** 이 저장소는 그리드 위에서 개체를 움직이는 시뮬레이션이다.
가장 자주 쓰는 동작이 "이동"인데 §2.1 의 79개 동사 목록에 `move` 가 없다. 결과가
`game/app/simulation/actions.py` 에 그대로 남아 있다.

```
apply_move   apply_attack   apply_area_attack   apply_summon   apply_heal
apply_potion apply_hold     apply_flag          apply_damage   _apply_strike  _apply_step
```

행동 11종이 전부 `apply_` 로 시작한다. 이 자리에서 `apply` 는 아무 정보도 주지 않는다 —
검사기를 통과시키는 접두어일 뿐이다. `move`·`strike`·`summon` 이 있었다면 이름이 동작을
말했을 것이다.

**왜 문제인가.** §11 이 직접 이 상황을 다룬다.

> 규칙이 정보를 지우게 만들면 규칙을 의심한다. 규칙을 지켰더니 호출자가 알아야 할 것이
> 사라지거나, 검사를 통과시키려고 사실과 다른 것을 쓰게 된다면 그 규칙이 그 상황을
> 안 보고 있는 것이다. 저장소에서 우회하지 말고 정본에 보고한다 — 다음 도입자가 같은
> 자리에서 같은 선택을 강요받는다.

§2 는 "같은 개념에는 항상 같은 동사를 쓴다"고 요구하지만, 목록이 도메인 동사를 담지
못하면 **서로 다른 개념이 하나의 동사로 뭉개진다.** 위 11개가 그 예다.
`# naming: allow` 로 11곳을 억제하는 것은 §11 이 "규칙이 아니라 소음"이라고 부른 상태다.

**제안.** §2.1 목록에 이동·상태 변화 계열을 더한다. 게임·시뮬레이션·로보틱스·미디어
파이프라인이 공통으로 쓰는 동사다.

```diff
 9  plan scan store record evaluate embed promote
+10 move place attach detach emit consume advance
```

최소한 `move` 하나는 반드시 넣는다. 넣으면 `tools/check_naming.py` 의 `ALLOWED_VERBS` 도
같은 커밋에서 함께 고친다 — 그 파일의 주석이 "2.1 의 동사 목록과 항상 일치해야 한다.
문서와 코드가 갈라지면 사람이 통과시킨 이름을 게이트가 막는다"고 적고 있다.

**우선순위 P1.** 저장소는 `apply_` 로 돌아가지만, 그 우회가 코드를 읽기 어렵게 만든
상태가 이미 고정돼 있다.

## D7 · §4·§7 — 모듈 400줄 상한을 아무것도 검사하지 않는다 (게이트에 추가함)

**무엇이 문제인가.** §4 는 임계값 셋을 정한다.

| 상황 | 조치 |
|:--|:--|
| 모듈이 400줄 초과 또는 책임이 둘 이상 | 파일 분리 |
| 함수가 50줄 초과 또는 순환 복잡도 10 초과 | 분해 |

§7 표에는 「함수 길이·복잡도 → ruff C90(mccabe), PLR0915 → 완전 자동」 행이 있다.
**모듈 400줄에는 행이 아예 없다.** §8 의 어느 단계도 이것을 보지 않는다. ruff 에 대응
규칙이 없기 때문이다(C90 은 순환 복잡도, PLR0915 는 문장 수를 잰다. 파일 줄 수를 재는
규칙은 ruff 에 없다).

재현 — 이 저장소는 게이트가 **초록인 상태로** 400줄을 넘긴 모듈을 11개 갖고 있었다.

```
$ ./tools/check_all.sh   # → 전부 통과
$ git ls-files '*.py' | xargs wc -l | sort -rn | head
   1048 scripts/export_rules_golden.py
    643 tests/test_rule_vm.py
    608 tests/test_resources.py
    442 tests/test_pressure.py
    439 tests/test_telegraph.py
    434 tests/test_replay.py
    433 tests/test_meta.py
    425 tests/test_floor_map.py
    413 scripts/export_grid_golden.py
    409 scripts/export_golden.py
    406 game/app/simulation/pressure.py
```

> **참고 — `telegraph.py` 403줄 건은 사실이 아니다.**
> 사전 보고에는 `game/app/simulation/telegraph.py` 가 403줄로 상한을 넘겼다고 돼 있었다.
> 확인 결과 이 파일은 **정확히 400줄**이고, 저장소의 모든 커밋에서 400줄이었다
> (`for c in $(git log --format=%H); do git show $c:game/app/simulation/telegraph.py | wc -l; done`
> → 전부 400). `wc -l`·`splitlines()` 둘 다 400 이며 마지막 줄에 개행도 있다.
> §4 는 "400줄 **초과**"이므로 400줄은 위반이 아니다. 실제 위반은 위 11개이고, 그중
> 프로덕션 코드는 `pressure.py` 406줄 하나였다.
> 이것이 D7 의 성격을 오히려 잘 보여 준다 — 검사가 없으면 **위반이 있는지도, 어느
> 파일인지도 사람이 눈으로 세게 되고, 그 셈은 틀린다.**

**왜 문제인가.** §7.1 이 그대로 적용된다. §4 는 임계값 셋을 나란히 적어 두어 셋 다 같은
수준으로 강제되는 것처럼 읽히고, §7 표는 그중 둘만 「완전 자동」으로 올려 적으면서
나머지 하나는 표에서 통째로 빠뜨렸다. 사람 판단으로도 적혀 있지 않다 —
**어느 계층이 이 규칙을 보는지가 문서 어디에도 없다.**

**제안 ①** §7 표에 행을 더한다.

```diff
 함수 길이·복잡도              ruff C90 (mccabe),     완전 자동
                             PLR0915
+모듈 길이 (§4 400줄)          tools/check_module_    완전 자동
+                            length.py
```

**제안 ②** §8.5 `check_all.sh` 에 단계를 더한다. 검사 대상은 `check_naming` 과 같되
**테스트를 빼지 않는다** — §1 이 테스트에 면제하는 것은 독스트링·타입 힌트·함수명
셋뿐이고, §8.1 은 "E501·SIM·C90 은 넣지 않는다 — 테스트도 읽기 쉬워야 하고, 그쪽은
테스트라서 정상이 되는 종류가 아니다"라고 적는다. 줄 수 상한은 그 셋과 같은 성격이다.

```diff
+printf '\n── check_module_length\n'
+if ! git ls-files '*.py' \
+    | { grep -v -E '((^|/)migrations/|_pb2\.py$)' || true; } \
+    | xargs -r python3 tools/check_module_length.py; then
+    FAILED="${FAILED} check_module_length"
```

## D8 · §7 — 「함수 길이·복잡도 = 완전 자동」이 사실이 아니다

**무엇이 문제인가.** §7 표는 이렇게 적는다.

| 규칙 | 강제 수단 | 수준 |
|:--|:--|:--|
| 함수 길이·복잡도 | ruff C90 (mccabe), PLR0915 | 완전 자동 |

`PLR0915` 는 `too-many-statements` 로 **문장 수**를 센다(기본 상한 50). `C901` 은 **순환
복잡도**를 잰다. §4 가 요구하는 "함수가 50줄 초과"의 **줄 수를 재는 규칙은 ruff 에 없다.**

재현 — 게이트가 초록인 상태에서 50줄을 넘긴 함수가 10개다. 가장 긴 것은 184줄이다.

```

$ ./tools/check_all.sh                            # → 전부 통과
   184줄  scripts/rules_golden_validator_cases.py  build_validator_specs
   119줄  scripts/rules_golden_condition_cases.py  build_rule_vm_specs
   105줄  scripts/rules_golden_condition_cases.py  build_condition_specs
    91줄  game/app/services/run_battle.py          build_engine
    77줄  game/app/services/run_chain.py           run_room_chain
    70줄  game/app/simulation/perception.py        build_snapshot
    65줄  game/schemas/blocks.py                   load_block_catalog
    55줄  game/app/simulation/pressure.py          create_hunter
    55줄  game/app/services/run_room_loop.py       create_node_visit
    54줄  game/app/services/run_batch.py           run_batch
```

184줄 함수가 `PLR0915` 를 통과하는 이유는 그 몸통이 **리터럴 하나**이기 때문이다 —
검증기 기준 항목을 담은 큰 리스트라 문장 수로는 1이다. 문장 수와 줄 수는 다른 것을 재고,
§4 가 적은 것은 줄 수다.

**왜 문제인가.** §7 표 바로 위에 이렇게 적혀 있다.

> 이 표의 「수준」은 사실이어야 한다. 검사할 수 없는 것을 「완전 자동」으로 적어 두면,
> 아무도 안 보는 규칙이 지켜지고 있다고 착각하게 된다 — 규칙을 어긴 것보다 나쁘다(§7.1).

이 행은 그 문장이 금지한 바로 그 상태다. D7 과 성격이 다르다는 점이 중요하다 — D7 은
행이 **없어서** 아무 말도 안 하지만, D8 은 행이 **있으면서 틀린 말을 한다.**

**제안 ①** 표를 사실대로 나눈다.

```diff
-함수 길이·복잡도              ruff C90 (mccabe),     완전 자동
-                             PLR0915
+함수 복잡도·문장 수            ruff C90 (mccabe),     완전 자동
+                             PLR0915
+함수 길이 (§4 50줄)           tools/check_module_    완전 자동
+                             length.py (도입 시)
+                             / 없으면 코드 리뷰       / 사람 판단
```

**제안 ②** `tools/check_module_length.py` 에 함수 단위 검사를 함께 넣는다. AST 로
`end_lineno - lineno` 를 재면 되고, `check_naming.py` 가 이미 같은 방식으로 AST 를 훑는다.
데코레이터를 포함할지는 명시한다(포함을 권한다 — 읽는 사람이 보는 것은 그 블록 전체다).

**제안 ③** 순수 데이터 리터럴을 돌려주는 빌더는 예외로 다룰지 §4 에 명시한다.
"검증 케이스 표 184줄"을 50줄씩 넷으로 자르면 읽기가 나빠진다. §11 의 "규칙이 정보를
지우게 만들면 규칙을 의심한다"에 해당한다. 권장안은 **줄 수 상한을 코드 문장에만 걸고,
모듈 상수로 승격된 데이터에는 §4 의 모듈 400줄만 적용**하는 것이다.

**저장소 상태 — 켜지 않았다.** 존량 10건 중 절반이 위 데이터 리터럴 성격이라 §10.5 3단계로

§11 이 금지한 "저장소 설정 파일만 개별 수정" 이 된다. **켜지 않았다는 사실 자체를 여기에
적어 두는 것이 §7.1 이 요구하는 처리다.**

**우선순위 P0.** 표가 틀린 말을 하고 있고, 그 표가 도입자의 유일한 판단 근거다.

## D9 · §8.5 — `step()` 이 실패한 단계의 이름을 잘못 보고한다

**무엇이 문제인가.** §8.5 의 `step()` 은 이렇게 돼 있다.

```bash
step() {
    printf '\n── %s\n' "$1"
    shift
    if ! "$@"; then
        FAILED="${FAILED} $1"      # ← shift 뒤라서 $1 은 라벨이 아니라 명령어다
    fi
}
```

`shift` 뒤의 `$1` 은 라벨이 아니라 **실행한 명령의 첫 낱말**이다. 따라서
`step "ruff check" ruff check .` 와 `step "ruff format" ruff format --check .` 는
**둘 다 `ruff` 로 보고된다.** 실제 실행 결과가 이것이다.

```
$ ./tools/check_all.sh
...
실패: ruff check_module_length
```

`ruff check` 가 실패한 것인지 `ruff format --check` 가 실패한 것인지 요약 줄만으로는
구별할 수 없다. `check_structure` 는 `./tools/check_structure.sh` 로 보고된다.

**왜 문제인가.** §7.1 은 "검사 결과는 종료 코드로 판정한다"를 강조하며 게이트가 **무엇이
실패했는지 정확히 말해야** 한다는 전제 위에 있다. §10.2 15단계는 "게이트를 실제로
실행하고 **검사별** 위반 건수를 요약한다"고 요구하는데, 정본이 배포한 코드가 검사별
구분을 지운다. 그리고 §7.1 의 "본 문서가 배포하는 파일도 본 문서의 규칙을 통과해야
한다"는 자체 검사(ruff·pydoclint·check_naming)로는 이 결함이 잡히지 않는다 —
셸 스크립트는 그 넷 중 어느 것의 대상도 아니다.

**제안.** 라벨을 `shift` 전에 지역 변수로 잡는다.

```diff
 step() {
-    printf '\n── %s\n' "$1"
+    local label="$1"
+    printf '\n── %s\n' "${label}"
     shift
     if ! "$@"; then
-        FAILED="${FAILED} $1"
+        FAILED="${FAILED} ${label}"
     fi
 }
```

`local` 이 쓰기 싫으면 `label="$1"` 로도 된다(이 스크립트는 다른 전역을 쓰지 않는다).
덧붙여 §7.1 에 **"§8 의 셸 스크립트는 `shellcheck` 를 통과한 상태로 유지한다"** 를 넣기를
제안한다. `shellcheck` 는 이 종류를 잡는다. 지금 §7.1 의 자체 검사 네 가지는 파이썬 파일만
본다.

**우선순위 P1.** 게이트를 막지는 않지만, 게이트가 실패했을 때 **가장 필요한 정보**를 지운다.

## D11 · §8.9 — 선택 검사 도입 시 「완전 자동」 승격 범위가 과장돼 있다

**무엇이 문제인가.** §8.9 는 이렇게 적는다.

> §7 표에서 사람 판단으로 적힌 두 규칙(디렉터리 구조, 타입 힌트 정확성)을 기계로 올리고
> 싶은 저장소가 쓴다. (…) 도입하면 §7 표의 해당 행을 그 저장소 기준으로 「완전 자동」으로
> 올려 적는다.

그런데 두 검사가 실제로 보는 것은 그 행의 일부뿐이다.

**구조 검사.** `check_structure.sh` 는 25줄이고, 하는 일은 추적 파일의 디렉터리 이름을
모아 12낱말짜리 블랙리스트와 `grep -x -E` 로 맞춰 보는 것뿐이다. §12.1 은 원칙을 셋
적는다 — ① 이름이 역할을 말한다 ② **의존은 한 방향으로만 흐른다** ③ 구조 규칙은
리뷰에서 본다. 스크립트가 보는 것은 ①의, 그것도 블랙리스트에 있는 이름에 한정된 일부다.
`§12` 의 계층 경계(`core/` 가 도메인을 모르는가, `services/` 만 여럿을 엮는가)는 전혀 보지
않는다. 그런데 승격 대상 행의 이름은 「디렉터리 구조 (12장)」 **전체**다.

**타입 검사.** `mypy --ignore-missing-imports --no-strict-optional` 은 기본값에서
애너테이션이 없는 함수의 몸통을 검사하지 않는다. §8.1 이 테스트에 `ANN` 을 면제하므로
이 저장소의 테스트 22개 파일 전체가 그 상태다. 게이트 출력이 직접 그렇게 말한다.

```
$ ./tools/check_all.sh
── mypy
tests/test_rule_blocks.py:173: note: By default the bodies of untyped functions
  are not checked, consider using --check-untyped-defs  [annotation-unchecked]
Success: no issues found in 89 source files
```

「타입 힌트 정확성 = 완전 자동」으로 올려 적으면, 실제로는 **애너테이션이 붙은 코드에
한정된 자동**이다.

**왜 문제인가.** §7.1 이 든 실패 예시가 정확히 이것이다 — "애너테이션은 있는데 타입이
틀린 코드, 디렉터리 규칙은 있는데 아무도 안 보는 배치". 승격 범위를 과장하면 §8.9 를
도입한 저장소가 도입하지 않은 저장소보다 **더 확신에 차서 틀리게 된다.**

**제안.** §8.9 의 승격 문구를 범위 한정으로 바꾼다.

```diff
-필수가 아니다 — 도입하면 §7 표의 해당 행을 그 저장소 기준으로 「완전 자동」으로 올려 적는다.
+필수가 아니다. 도입하면 §7 표의 해당 행을 아래 범위에서만 올려 적는다. 두 검사는 각 행의
+일부만 본다 — 전체를 올려 적으면 §7.1 이 경고한 착각이 그대로 생긴다.
+
+  구조 검사  →  「디렉터리 이름이 역할을 말하는가 (§12.1 ①)」 를 새 행으로 나누어
+               완전 자동. 계층 경계와 의존 방향(§12.1 ②)은 사람 판단으로 남긴다.
+  타입 검사  →  「타입 힌트 정확성 (애너테이션이 붙은 코드에 한정)」 로 적는다.
+               ANN 이 면제된 경로(테스트 등)는 몸통이 검사되지 않는다.
```

**우선순위 P1.**

## D12 · §1·§8.7 — 같은 예외 경로가 다섯 갈래로 적혀 있다

**무엇이 문제인가.** §1 은 "예외 경로는 §8.1·§8.3·§8.5·§8.7 에 함께 반영한다. 한 곳만
고치면 나머지 경로에서 예외가 동작하지 않는다"고 적는다. 그런데 정본이 배포하는 네 파일이
같은 집합을 **네 가지 다른 문법**으로 적고, 그중 둘이 서로 다른 것을 뜻한다.

| 자리 | 표현 | 루트 `tests/` 를 거르는가 |
|:--|:--|:--|
| §8.1 `per-file-ignores` | `"**/tests/**/*.py"` | ○ |
| §8.5 `pydoclint --exclude` | `/tests/` | ✗ (D3) |
| §8.5 `check_naming` grep | `(/tests/\|...)` | ✗ (D3) |
| §8.3 `pre-commit exclude` | `(/tests/\|...)` | ✗ (D3) |
| §8.7 훅 `case` | `*/tests/*` | **절대경로일 때만 ○** |

다섯째가 새로 확인된 자리다. §8.7 의 훅은 셸 글로브를 쓴다.

```bash
$ case "tests/test_x.py" in */tests/*) echo MATCH;; *) echo "NO MATCH";; esac
NO MATCH
$ case "/data/workspace/game/tests/test_x.py" in */tests/*) echo MATCH;; esac
MATCH
```

Claude Code 가 훅에 넘기는 `tool_input.file_path` 가 절대경로라 지금은 동작하지만,
상대경로로 오는 순간 **저장소 루트의 테스트가 네이밍 검사를 받는다.** §8.1 이 테스트에
`N802` 를 면제하는 이유(한글·서술형 테스트 이름)가 여기서 무너진다. D3 과 같은 결함이
표현만 달리해 한 자리 더 남아 있는 것이다.

**왜 문제인가.** §1 은 "한 곳만 고치면 나머지가 실패한다"를 경고하면서, 정작 **다섯 곳을
다섯 문법으로 적어 두어 그 실수를 구조적으로 유도한다.** 도입자가 예외 경로를 하나
추가하려면 정규식·글로브·ruff 패턴 세 문법을 동시에 정확히 다뤄야 한다.

**제안 ①** §8.7 의 `case` 를 상대경로에도 걸리게 한다. (이 저장소는 손대지 않았다 —
Claude Code 가 넘기는 `file_path` 가 절대경로라 지금은 동작하며, 정본이 고칠 자리다.)

```diff
 case "${FILE_PATH}" in
-    */migrations/*|*_pb2.py) exit 0 ;;
+    migrations/*|*/migrations/*|*_pb2.py) exit 0 ;;
 esac
 ...
 case "${FILE_PATH}" in
-    */tests/*) NAMING_OUTPUT=""; NAMING_STATUS=0 ;;
+    tests/*|*/tests/*) NAMING_OUTPUT=""; NAMING_STATUS=0 ;;
```

**제안 ②** 구조적으로 고칠 것 — §1 에 **예외 경로 표를 한 곳에 두고**, 각 자리에는 그
표에서 옮겨 적은 값임을 명시한다. 표에는 세 문법을 나란히 적는다.

```markdown
| 대상 | ruff 패턴 | 정규식 (pydoclint·grep·pre-commit) | 셸 글로브 (훅) |
|:--|:--|:--|:--|
| 테스트 | `**/tests/**/*.py` | `(^\|/)tests/` | `tests/*\|*/tests/*` |
| 마이그레이션 | `**/migrations/**/*.py` | `(^\|/)migrations/` | `migrations/*\|*/migrations/*` |
| 자동 생성 | `**/*_pb2.py` | `_pb2\.py$` | `*_pb2.py` |
```

**우선순위 P1.** D3 을 고쳐도 같은 뿌리가 남는다.

## D13 · §10.2 — `apply-conventions.md` 자체가 배포 목록에 없다

**무엇이 문제인가.** §10.2 5단계는 §8 의 코드 블록을 기록할 경로 일곱 개를 나열한다.
그 목록에 **`.claude/commands/apply-conventions.md` 자체가 없다.** 이 저장소에도 없다.

```
$ ls .claude/commands
ls: cannot access '.claude/commands': No such file or directory
```

§10.3 은 이렇게 적는다.

> 본 문서가 개정되면 RULESET_VERSION 을 올리고, 각 저장소에서 **같은 커맨드를 재실행한다.**

재실행할 커맨드가 저장소에 없다. 최초 적용은 사람이 문서를 보고 하지만, 재동기화는
**저장소 안에 커맨드가 있어야** 성립한다. RULESET_VERSION 15 가 배포되는 순간 모든
저장소가 이 자리에서 멈춘다.

**왜 문제인가.** §10 전체가 "Claude Code 가 본 문서를 스스로 찾아 읽고 저장소 설정을
구성한다"를 전제로 하는데, 그 진입점이 배포되지 않는다. §10.4 가 "조용한 오작동보다
명시적 실패가 안전하다"고 적은 원칙에도 어긋난다 — 커맨드가 없으면 실패조차 나지 않고,
**아무 일도 일어나지 않는다.**

**제안.** §10.2 5단계 목록에 한 줄 넣는다.

```diff
 5. "8. 저장소 표준 설정 파일" 섹션의 각 코드 블록을 아래 경로에 기록한다.
+   - .claude/commands/apply-conventions.md   (본 절 10.2 의 블록 자체 — 재동기화 진입점)
    - ruff.toml
    - tools/check_naming.py
```

덧붙여 §10.2 를 코드 블록으로 감싸 그대로 복사할 수 있게 한다. 지금은 번호 목록이라
"어디부터 어디까지가 파일 내용인가"가 문서 서식에 묻힌다.

**우선순위 P1.** 개정 배포 경로 전체가 여기에 걸린다.

## D14 · §3·§7 — 매직 넘버·매직 스트링에 강제 수단 행이 없다

**무엇이 문제인가.** §3 은 "매직 넘버·매직 스트링은 모듈 상단 상수로 승격한다"고 단정한다.
§7 표에는 이 규칙의 행이 없다. `ruff` 의 `PLR2004` 는 이름이 말하는 대로
`magic-value-comparison` — **비교 연산의 우변만** 본다. 산술·인자·기본값 자리의 리터럴과
매직 스트링은 전부 통과한다.

재현 — 게이트가 초록인 상태에서 `game/` 안 산술식의 매직 넘버가 10곳이다.

```
$ ruff check --select PLR2004 game/ --statistics    # → 0건
game/app/combat/damage.py:65   raw = (attack * skill_coef_pct * (denominator - defense)) // (100 * denominator)
game/app/combat/damage.py:70   return max(rules.min_damage, raw * surround_pct // 100)
game/app/simulation/engine.py:343   base = entity.regen_base * regen_pct // 100
game/app/simulation/state.py:47     return self.hp * 100 // self.hp_max
game/app/services/analyze_battle.py:48   return self.wasted * 100 // attempts if attempts else 0
```

같은 저장소의 `pressure.py` 는 같은 100 을 `PERCENT_BASE = 100` 으로 승격해 두었다.
**규칙을 지킨 자리와 안 지킨 자리가 공존하고, 게이트는 둘을 구별하지 못한다.**

**왜 문제인가.** §7.1 이 말한 "규칙은 있는데 아무도 안 보는" 전형이다. 게다가 §8.1 은
테스트에 `PLR2004` 를 면제하면서 그 사유를 정성껏 적어 두어(기댓값이 곧 매직 넘버다),
읽는 사람은 **매직 넘버가 기계로 강제되고 있다고 믿게 된다.** 면제 사유가 상세할수록
그 착각은 강해진다.

**제안.** §7 표에 사실대로 행을 넣는다. 이 규칙은 도구가 뜻을 못 보는 종류다 —
`3` 이 매직 넘버인지 자명한 상수인지는 도메인이 정한다.

```diff
+매직 넘버·매직 스트링 (§3)     비교 자리는 ruff        근사 검출
+                             PLR2004. 그 밖의 자리는  / 사람 판단
+                             코드 리뷰
```

`PLR2004` 를 "완전 자동"으로 적지 않는 것이 핵심이다. §7 표의 「중복 제거」 행이 이미
「근사 검출」이라는 수준을 쓰고 있으므로 표기 선례도 있다.

**우선순위 P2.** 지금 게이트를 막지 않고, 고쳐도 자동화되지 않는다. 그래도 표가 사실이
아니면 §7.1 위반이다.

## D15 · §8.5 — 게이트가 추적되지 않은 파일을 보지 않는다

**무엇이 문제인가.** `check_naming`·`check_structure`·(제안한) `check_module_length` 는
모두 `git ls-files` 로 대상을 모은다. 아직 `git add` 하지 않은 파일은 **인덱스에 없으므로
목록에 나오지 않는다.** 확인:

```
$ # springs.py 를 만들고 아직 add 하지 않은 상태에서 400줄을 넘겨 두면
$ ./tools/check_all.sh
── check_module_length          ← 아무것도 보고하지 않는다
전부 통과
```

반면 `ruff` 는 워킹트리를 스캔하므로 같은 파일을 검사한다. **같은 게이트 안에서 검사마다
대상 범위가 다르다.**

**왜 문제인가.** §1 과 §7.1 이 "도구마다 검사 대상 범위가 다르다"를 두 번 경고하는데,
그 경고는 서브모듈·가상환경만 다룬다. "추적되지 않은 새 파일"은 다루지 않는다.
pre-push 트리거에서는 커밋된 것만 남으므로 대체로 안전하지만, **§8.5 는 사람이 직접 부를
수도 있는 명령**이고(§10.2 15단계가 그렇게 시킨다) 그때는 갓 만든 파일이 조용히 빠진다.

**제안.** §8.5 서두 주석에 한 문장을 더한다. 동작을 바꾸는 것이 아니라 사실을 적는 것이다.

```diff
 # 1장의 예외 경로는 도구마다 반영 지점이 다르다 — ruff 는 ruff.toml, pydoclint 는 아래
 # --exclude, check_naming.py 는 아래 grep. 한 곳만 고치면 나머지가 그 코드에서 실패한다.
+#
+# git ls-files 기반 검사(check_naming·check_structure)는 **추적되지 않은 파일을 보지
+# 않는다.** ruff·pydoclint 는 워킹트리를 스캔하므로 본다. 게이트를 손으로 부를 때는
+# 새 파일을 먼저 git add 한다 — pre-push 트리거에서는 이미 커밋된 상태라 문제가 없다.
```

**우선순위 P2.**

## D16 · §10.3 — RULESET_VERSION 드리프트 대조가 어디에서도 돌지 않는다

**무엇이 문제인가.** §10.3 은 이렇게 적는다.

> 동기화 누락을 막기 위해 정본 문서의 RULESET_VERSION 과 `.claude/conventions.lock`
> 값을 **주기적으로 비교하고 불일치 시 알린다.**

누가·무엇이 비교하는지가 문서 어디에도 없다. §8 은 이 검사를 배포하지 않고, §7 표에도
행이 없다. `.claude/conventions.lock` 자신은 첫 줄에 "이 파일은 이력 추적용이다.
다음 실행 시 조회 기준으로 쓰지 않는다"고 적혀 있어, 오히려 **자동화가 이 값을 읽지
않는다**고 선언한다.

**왜 문제인가.** §10.3 은 "버전이 그대로면 각 저장소가 낡은 사본을 계속 쓰게 되고, 그
사본이 게이트를 깨뜨려도 재동기화 신호가 가지 않는다"고 정확히 진단해 놓고, 그 신호를
보낼 주체를 정하지 않았다. D13(커맨드 미배포)과 겹치면 **개정이 배포되지 않는 경로가
둘로 늘어난다.**

**제안.** 둘 중 하나를 고른다.

- (가) 사람이 한다고 사실대로 적는다 — "표준 담당자가 개정 시 라벨 구독자에게 알린다.
  저장소 쪽 자동 대조는 없다."
- (나) 자동으로 만든다 — §8.5 에 선택 단계를 더한다. 다만 게이트가 네트워크에 의존하게
  되므로(§10.3 이 "매번 읽으면 네트워크 실패에 취약해진다"고 반대한 것) 게이트가 아니라
  주 1회 도는 별도 워크플로에 둔다.

권장은 (가)다. 지키지 못할 자동화를 적는 것보다 사람이 한다고 적는 편이 §7.1 에 맞는다.

**우선순위 P2.**

## D17 · §7.1 × §8.5.2 — 도구 버전 핀이 ruff 하나뿐이다

**무엇이 문제인가.** §7.1 은 "계층마다 도구 버전을 맞춘다 (…) 버전 차이는 곧 검사 범위
차이다"라고 하고, §11 은 "도구 버전 핀(§8.3 rev, §8.5.2 ruff==) 갱신도 규칙 개정으로
취급한다"고 한다. 그런데 핀이 있는 도구는 `ruff` 뿐이다. 게이트가 실제로 부르는 도구는
넷이다 — ruff, pydoclint, mypy(§8.9), pre-commit(§8.3).

이 저장소의 상태가 그 결과를 보여 준다. `pyproject.toml` 의 dependency-group 은
`ruff==0.16.3` 만 핀하고 나머지는 이름만 적는다. `.claude/conventions.lock` 은 설치된
값을 `pydoclint 0.9.1 / mypy 2.3.1 / pre_commit 4.6.2` 로 **기록**해 두었지만, 그 기록이
다음 `uv sync` 를 구속하지 않는다. 다른 기기에서 동기화하면 다른 버전이 들어오고,
그때 pydoclint 가 새 검사 항목을 들고 오면 **어제 통과한 코드가 오늘 막힌다** — §7.1 이
ruff 에 대해 경고한 것과 같은 일이다.

**제안.** §8.5.2 와 §10.2 12단계, §11 의 문구를 네 도구로 확장한다.

```diff
-도구 버전 핀(§8.3 rev, §8.5.2 ruff==) 갱신도 규칙 개정으로 취급한다 — 세 계층을 한 번에
-올리고 RULESET_VERSION 을 올린다(§7.1).
+도구 버전 핀 갱신도 규칙 개정으로 취급한다. 핀 대상은 게이트가 부르는 도구 전부다 —
+ruff(§8.3 rev·§8.5.2), pydoclint(§8.5.2), 그리고 §8.9 를 도입했다면 mypy 도.
+세 계층을 한 번에 올리고 RULESET_VERSION 을 올린다(§7.1).
```

**저장소에서 지금 고치지 않은 이유.** 핀을 넣으려면 `uv sync` 로 재해석해 `uv.lock` 을
함께 갱신해야 하고, 그것은 게이트 결과를 바꿀 수 있는 변경이다. §11 이 "저장소 설정
파일만 개별 수정하는 것은 금지한다"고 한 자리이므로 제안만 남긴다.

**우선순위 P2.**

```
$ cd frontend && npx tsc --noEmit && npx vitest run && npm run build
                                # 743 passed, 빌드 성공
```

분해가 동작을 바꾸지 않았음의 근거는 D7 절에 적었다.

**주의 — 새로 만든 파일 16개는 아직 `git add` 되지 않았다.** 그래서 위 게이트 실행에서
`check_naming`·`check_module_length` 는 그 파일들을 보지 않았다(D15). 아래처럼 명시적으로
돌려 따로 확인했고, 커밋한 뒤에는 게이트가 자동으로 본다.

```
$ find game scripts tests tools -name '*.py' -not -path '*/__pycache__/*' \
    | sort | xargs python3 tools/check_module_length.py
$ echo $?
0
```
