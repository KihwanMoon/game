## 사본이 썩는 것을 그날 잡는다

`design/tokens.lock.json` 이 **마지막으로 정본에서 받아온 순간의 값**을 그대로 적어 둔다.
`tests/test_design_tokens.py` 가 지금 사본을 그것과 대조한다.

| 잡히는 것 | 안 잡히는 것 |
|:--|:--|
| 저장소의 사본을 누가 손댔다 | 정본이 바뀌었다 |

**검사는 네트워크를 타지 않는다.** 정본을 직접 부르면 정본이 잠깐 안 뜰 때 게이트가
막히고, 그러면 사람이 검사를 끈다. 오른쪽 칸은 받아올 때 알게 된다 — 받아온 값이 잠금과
다른 것이 곧 「정본이 바뀌었다」는 신호다.

```bash
uv run python -m scripts.lock_design_tokens --check   # 대조만
uv run python -m scripts.lock_design_tokens           # 받아온 뒤 다시 잠근다
```

정본을 고쳤을 때의 순서는 이렇다.

1. Claude Design (`7a323244`) 에서 토큰을 고친다
2. `design/tokens/*.css` 를 받아온다 — 이 시점에 검사가 빨개진다. **그것이 정상이다**
3. 바뀐 값이 코드에 무슨 뜻인지 확인한다 (프런트는 `@design` 별칭으로 원본을 직접 읽는다)
4. `uv run python -m scripts.lock_design_tokens` 로 다시 잠근다

컴포넌트 쪽은 값이 아니라 계약이라 잠금이 아니라 `components.contract.json` 이 받는다 —
프롭과 **글리프**를 함께 기록하고 `tests/test_design_contract.py` 가 대조한다.

## 피그마로 내보내기

`design/tokens.json` 이 피그마가 읽는 형식이고, `scripts/export_design_tokens.py` 가
`tokens/*.css` 에서 만든다. **손으로 옮기지 않는다** — 이 디렉터리가 정본의 사본이라
손으로 옮기면 또 어긋나고, 실제로 열한 개가 어긋나 있었다.

```bash
uv run python -m scripts.export_design_tokens
```

받는 곳: **Coding Roguelike — Design Tokens**
(`h1Hd5uHx5csRvCBceUxq87`, team `The matrix`)
<https://www.figma.com/design/h1Hd5uHx5csRvCBceUxq87>

가져오는 절차는 피그마 쪽에서 사람이 한다.

1. 그 파일에서 **Tokens Studio** 플러그인을 연다
2. Tools → **Import** → `design/tokens.json`
3. 셋 순서는 `$metadata` 가 정한다: `primitive` → `semantic` → `layout/*`
4. Themes 에서 `desktop`·`portrait`·`landscape` 를 켜고 **Create Variables** 를 누른다

셋이 셋으로 갈린 이유가 그 3단계다.

| 셋 | 무엇 | 어떻게 정했나 |
|:--|:--|:--|
| `primitive` | 실제 값을 든 것 | 값에 `var()` 가 없다 |
| `semantic` | 다른 토큰을 가리키는 것 | 값이 `var()` 하나뿐이다 |
| `layout/{모드}` | 배치마다 달라지는 것 | `@media` 안에서 다시 정의된다 |

**반응형이 모드가 된다.** 피그마 변수에는 미디어쿼리가 없고 모드가 있다 — 이 저장소가
브레이크포인트를 `tokens/spacing.css` 한 곳에만 두기로 한 규율이 마침 그 모양과 맞는다.
재정의하지 않은 값은 기본 배치(desktop)에서 채운다: CSS 는 이어받는 것을 전제로 쓰였지만
피그마는 모드에 값이 없으면 그냥 빈다.

**MCP 로 직접 밀어 넣지 않는 이유.** 이 계정은 Starter · View 좌석이라 **월 20 호출**이
상한이고, 피그마 공식 스킬은 디자인 시스템 하나에 20~100 호출을 요구한다. 중간에 끊기면
절반만 올라간 파일이 남는다. 좌석을 Full/Dev 로 올리면 그때는 직접 올려도 된다.

읽기(`get_design_context`·`get_screenshot`·`get_metadata`)가 바로 그 한도 대상이므로,
예산은 **피그마에서 디자인한 것을 코드로 가져올 때** 쓴다.

정본을 고쳤으면 이 파일도 함께 고친다. 남겨 둘 차이라면 `divergences` 에 **사유와 함께**
적는다 — 사유 없는 예외는 기록이 아니라 알리바이다.

지금 상태: 정본에 없는 것 셋(`CellGrid`·`Thumb`·`PlanActor`), 어긋난 것 아홉.
셋 다 등급·연결선 토큰을 쓰는 쪽이라, **정본에 그 토큰을 읽는 컴포넌트가 하나도 없다.**

## 성격

기계 도면(technical drawing)이다. 게임 UI 의 관습을 대부분 쓰지 않는다.

- **황동(`--brass`)은 화면의 유일한 광원이고 한 화면에 3곳까지.** 예산이다.
- **그림자가 시스템에 없다.** 층위는 명도차와 1px 괘선으로만 만든다.
- **모눈 한 칸이 4px.** 그 사이 값은 없다.
- **움직임은 명도 전환(90ms)과 틱 교체(140ms)뿐.** 등속, 바운스·오버슛 금지.
- **색은 정보의 유일한 채널이 될 수 없다.** 참/거짓은 색 + 글리프 + 명도 3중으로
  표기한다 — 흑백 인쇄와 색약 조건에서도 구분되어야 한다.
- 이모지 금지. 아이콘은 유니코드 도형만.
- `border-radius` 는 2px 고정.

## 반응형 — 이 사본이 정본보다 앞서 있는 지점

**`design/tokens/spacing.css` 를 이 저장소에서 고쳤다.** 원칙은 "사본을 고치지 않는다"
이므로, 무엇을 왜 고쳤는지 여기 적는다. **Design 프로젝트(정본)에도 같은 값을 반영해야
하고, 반영된 뒤에는 이 절을 지우고 다시 가져온다.**

### 무엇을 고쳤나

토큰이 1440×900 고정 px 뿐이라 모바일을 **표현할 자리가 없었다**(D-3). `--plan-cell` 이
64px 단일 값이라 12×64 = 768px 이고, 390px 화면에 12×9 도면이 들어갈 방법이 없다.
그래서 미디어쿼리로 재정의할 수 있는 값들을 토큰에 넣었다.

| 토큰 | 데스크톱 | 모바일 세로 | 모바일 가로 |
|:--|--:|--:|--:|
| `--layout-mode` | desktop | portrait | landscape |
| `--plan-cell` | 64px | **30px** | **32px** |
| `--plan-pad` | 16px | 14px | 8px |
| `--bar-top` | 56px | 44px | 40px |
| `--bar-speed` | 0px | 44px | 0px |
| `--bar-status` | 0px | 34px | 0px |
| `--bar-bottom` | 48px | 48px | 40px |
| `--col-rules` | 320px | 100% | 340px |
| `--col-log` | 300px | 100% | 340px |
| `--col-sheet` | 0px | 100% | 340px |
| `--sheet-tab-h` | 0px | 44px | 36px |
| `--row-h` | 44px | 54px | 50px |
| `--btn-h` | 36px | 44px | 30px |
| `--speed-box-h` | 32px | 32px | 28px |
| `--bar-edit` | 48px | 60px | 0px |

배치와 무관하게 같은 값인 것도 함께 넣었다. 세 화면이 같은 수를 쓰게 하려는 것이다.

| 토큰 | 값 | 쓰임 |
|:--|--:|:--|
| `--tap-min` | 44px | 탭·버튼의 최소 히트 영역 |
| `--speed-cell-w` | 44px | 배속 칸 하나의 폭 |
| `--edit-col` | 300px | 가로 모바일 편집 화면의 우열 |
| `--field-h` | 40px | 편집 카드의 조건·행동 칸 |
| `--card-head-h` | 32px | 편집 카드 헤더 |
| `--edit-cmp-w` | 78px | 편집 카드 조건 줄의 비교 칸 (`1fr 78px 1fr`) |
| `--edit-op-h` | 36px | 연산자 줄(AND·OR·조건 추가) |
| `--sheet-gauge-w` | 140px | 가로 시트 하단의 CPU 게이지 폭 |

편집 화면의 취소·저장만 배치를 탄다. 세로는 히트 영역 하한(44)에 맞추고 가로는 명세 C 가
정한 36 이다 — 시트 버튼(`--btn-h` 30)과 다른 값이라 토큰을 따로 두었다.

| 토큰 | 데스크톱 | 세로 | 가로 |
|:--|--:|--:|--:|
| `--edit-btn-h` | 36px | **44px** | 36px |

수치는 전부 모바일 원본(`모바일 화면.dc.html`·`모바일 시뮬레이션.dc.html`)에서 왔다.
**데스크톱 값은 하나도 바뀌지 않았다** — 미디어쿼리가 맞지 않으면 전과 같은 CSS 다.

`--col-rules`·`--col-log` 가 세로에서 `100%` 인 것에 주의한다. 세로에는 열이 없고 시트가
화면 폭 전체를 쓰기 때문이다. **아직 세로 배치를 짜지 않은 화면이 이 토큰으로 3열 그리드를
그리고 있으면 가로로 넘친다** — 조용히 좁아지는 대신 눈에 띄게 넘치도록 둔 값이다.

### 브레이크포인트를 어디에 그었나

```
@media (max-width:599px)  and (orientation:portrait)                        → portrait
@media (max-width:1023px) and (max-height:559px) and (orientation:landscape) → landscape
```

- **599px**: 세로 도면은 12×30 = 360px 에 좌우 여백 14 를 더해 388px 이 필요하고, 그보다
  넓은 폰은 없다. 600px 부터는 태블릿 폭이라 데스크톱 3열이 다시 성립한다.
- **max-height 559px**: 가로는 **높이로 가른다.** 가로로 눕힌 폰의 짧은 변은 가장 큰 것이
  430px(Pro Max)이라 전부 들어오고, 노트북 최소 높이 720px 은 들어오지 않는다.
  폭이 아니라 높이로 가르는 이유는 844×390 과 1280×720 을 폭으로는 가를 수 없기 때문이다.
- **max-width 1023px**: 가로 태블릿(1024px 이상)이 폰 배치로 떨어지는 것을 막는다.
- **orientation**: 390×390 처럼 두 규칙이 동시에 맞는 창을 없앤다. 세로/가로 배치는
  DOM 구조가 다르므로 경계가 겹치면 안 된다.

### 규율 — 브레이크포인트는 한 곳에만 있다

화면 CSS(`battle.css`·`editor.css`·`hud.css`·`ds.css`)는 **미디어쿼리를 적지 않는다.**
토큰만 읽는다. 이유는 둘이다.

1. 경계가 네 파일에 흩어지면 한 화면만 다른 폭에서 바뀌는 상태가 생기고, 그것은 특정
   폭에서만 드러나 재현이 어렵다.
2. 그 CSS 들은 「생 px 금지」를 기계로 검사받는다. `@media (max-width:599px)` 자체가
   생 px 라 검사에 걸린다 — 규율과 구현이 같은 방향을 가리킨다.

DOM 구조가 달라져야 하는 곳(세로의 탭 시트, 전용 편집 화면)은 CSS 가 아니라 스크립트가
가른다. `useViewportMode()` 가 `--layout-mode` 토큰을 읽어 `desktop`·`portrait`·
`landscape` 를 돌려주므로, 경계는 여전히 토큰 한 곳이다.

### 컴포넌트 계약 하나를 늘렸다 — `RuleRow.enabled`

모바일 원본(`모바일 시뮬레이션.dc.html`)이 정한 세로 전용 상호작용이 있다. **규칙 행을
눌러 켜고 끈다** — 꺼진 줄은 `opacity 0.4` 로 내려가고 조건문 뒤에 `  · 꺼짐` 이 붙는다.
규칙 편집 화면까지 가지 않고 가설을 시험하는 수단이며, 그것이 이 게임의 동사다.

`state`(true·false·pending)로는 표현할 수 없다. **"조건이 거짓이었다" 와 "판에 실리지
않아 평가되지 않았다" 는 다른 사실**이고, 규칙표가 그 둘을 구분해 보여주지 못하면
플레이어는 자기 우선순위를 읽을 수 없다(§2 와 같은 이유). 그래서 상태 여섯에 일곱째를
더하는 대신 직교하는 prop 하나(`enabled`, 생략하면 켜짐)를 열었다 — `armed` 가 `state`
와 직교하는 것과 같은 꼴이다. 구현은 `ds-rule-row--off` 클래스와 `aria-pressed` 두
채널로 나간다.

**정본에도 이 prop 을 넣어야 한다.** 위 컴포넌트 표의 `RuleRow` 행에 굵게 표시해 두었다.

### 편집 화면의 부품은 화면 폴더에 있다

모바일 규칙 편집(명세 C)이 쓰는 카드·선택 칸·세그먼트는 `frontend/src/editor/EditParts.tsx`
에 있고 `ds/` 에 넣지 않았다. 아래 컴포넌트 표가 정본이 선언한 부품 열여섯이고, 거기에
없는 부품을 우리가 늘리는 것은 **사본이 정본을 앞서는 두 번째 지점**을 만드는 일이다.
지금은 편집 화면 하나만 쓰는 표현이므로 그 화면 폴더에 두었다 — 다른 화면이 같은 모양을
원하게 되면 그때 정본에 올린다.

### 4px 모듈의 예외 하나

`--plan-pad:14px` 는 4의 배수가 아니다. 390 − 360 = 30 이라 좌우 16px(=`--sp-4`)이면
392px 로 화면을 넘긴다. 모바일 원본이 정한 값이며, 4px 모듈이 390px 폭과 충돌하는
유일한 자리다. **정본에 반영할 때 이 예외를 함께 결정해야 한다.**

## 시뮬레이션 코어에 거는 요구

디자인이 UI 취향이 아니라 **코어의 출력 계약**을 정하는 지점들이다. Phase 1 에서
이벤트 로그를 설계할 때 이미 반영해야 한다 — 나중에 붙이면 RuleVM 을 다시 짜야 한다.

1. **조건문에 실측값을 병기한다.** `RuleRow.condition` 이 받는 문자열은
   `적거리(2) <= 사거리(3)` 형태다. 즉 RuleVM 은 참/거짓만이 아니라 **각 항이 실제로
   무슨 값이었는지**를 함께 내보내야 한다. GDD §8.2 가 요구하는 것과 같고, P1(실패는
   정보다)의 실현 수단이다.
2. **규칙 하나의 상태가 4종이다** (블록 v5, 결정 #04) — 참·발동(`armed`), 참·미발동,
   거짓, **불가(`blocked`)**. 넷째는 "조건은 참인데 실행할 수단이 없다" 이고 거짓과
   다르다 — 플레이어가 고쳐야 할 곳이 앞은 조건, 뒤는 장비다. 의미색 셋이 이미
   배정돼 색을 더 쓸 수 없으므로 **해칭(⧅) + 취소선**으로 가른다: 색약과 흑백에서도
   나머지 셋과 구분되고 황동 예산을 건드리지 않는다.
   ~~2. 규칙 하나의 상태가 3종이다~~ "더 높은
   우선순위가 이미 발동해서 실행되지 않았다"를 UI 가 구분해 보여주므로, 코어도
   그 구분을 내보내야 한다.
3. **CPU 예산 초과 상태를 값으로 낸다.** `cpu 10 / 8` 처럼 초과분을 그대로 표시하고
   그 상태에서도 편집이 계속 가능하다. 코어는 초과를 오류로 막지 말고 수치로 보고한다.
4. **텔레그래프는 남은 틱 수를 낸다.** `ThreatNotice.ticks`.
5. **`LogRow` 가 `tick, rule, expr, outcome, delta, fired` 를 받는다.** 이벤트 로그
   레코드의 필드가 사실상 여기서 정해졌다.

## 검토 결과 — 기획서와 어긋나는 지점

디자인을 읽으면서 나온 것이다. 어느 쪽이 맞는지는 결정이 필요하다.

### D-1. 적 유형이 3종만 표현된다

`PlanActor.kind` 는 `self · charge · shoot · summon` 뿐이다. GDD §5 는 적을 6종으로
정의한다 — 돌진·사격·소환·**자폭·치유·보스**. 뒤 세 종은 도면에 그릴 방법이 없다.

자폭형은 GDD §4.2 텔레그래프의 주 사용처이고 보스는 페이즈별 규칙표 교체가 핵심이므로,
빠뜨린 것이 아니라면 Phase 1 범위(적 3종)에 맞춘 것으로 보인다. Phase 4 에서 8종 +
보스 3종을 채울 때 `kind` 열거를 확장해야 한다.

### D-2. 도면 격자가 12×9 로 고정이다

토큰이 `--plan-cols:12`, `--plan-rows:9`, `--plan-cell:64px` 로 못박혀 있다.
GDD §9 의 룸 템플릿 12×9 와는 일치하지만, **TDD §6 은 방 크기를 최대 20×15 로 적었다.**

기준 해상도에서 가운데 열 가용 폭은 `1440 - 320 - 300 - 2 = 818px` 이다.

| 방 크기 | 64px 셀 기준 | 결과 |
|:--|:--|:--|
| 12×9 | 768×576 | 들어감 |
| 16×12 | 1024×768 | 넘침 |
| 20×15 | 1280×960 | 넘침 |

셀 크기를 고정한 채로는 12×9 를 넘길 수 없다. 방 크기 상한을 12×9 로 내리든지,
셀 크기를 가변으로 바꾸든지 둘 중 하나를 정해야 한다. 후자를 고르면 4px 모듈 규칙과
충돌하므로(64px 은 4의 배수지만 가변 셀은 아니게 된다) 디자인 쪽 결정이 필요하다.

**부분적으로 정해졌다.** 셀 크기는 이제 화면 폭에 따라 셋(64/32/30)이 되었지만 그것은
**같은 12×9 를 좁은 화면에 넣기 위한 것이고, 격자는 여전히 12×9 고정**이다. 「방을 키우는
문제」는 그대로 남아 있다 — 20×15 는 어느 배율에서도 들어가지 않는다. 그리고 예상대로
4px 모듈과 부딪쳤다: 32 는 4의 배수지만 **30 은 아니다.** 방 크기 상한과 이 예외는 여전히
디자인 쪽 결정이 필요하다.

### D-3. 플랫폼이 갈린다

GDD §1 은 플랫폼을 **"PC (웹 빌드 우선, 이후 Steam)"** 로 적었는데, Design 프로젝트에는
`모바일 화면.dc.html` 과 `모바일 시뮬레이션.dc.html` 이 있다. 토큰은 전부 1440×900
기준 고정 px 이고 브레이크포인트가 없다 — 모바일 화면은 다른 배율 체계를 쓸 것이다.

모바일이 정식 타깃이면 GDD §1 과 활자 계단(§ 활자배율 M)을 함께 고쳐야 한다.

**토큰 쪽은 열었다** — 위의 「반응형」 절이 브레이크포인트와 모바일 치수를 정의한다.
아직 남은 것은 (a) GDD §1 의 플랫폼 문장, (b) 활자 계단이다. 모바일 명세가 쓰는
15px(가로 상단바의 틱 표기)이 활자배율 M 에 없다. 지금은 가장 가까운 계단
(`--fs-display-s` 16px)을 쓰며, 정본이 모바일 계단을 정해 주면 그때 맞춘다.

### D-4. 디자인은 전투 화면만 덮는다

컴포넌트 17종이 전부 전투 화면·규칙표·로그용이다. 로드맵 Phase 2 가 요구하는
**몬스터 도감, 보상 선택, 프리셋 8슬롯, 사후 분석 리플레이 슬라이더**에 대응하는
컴포넌트가 없다. W5·W8 에 들어가기 전에 디자인이 필요하다.
