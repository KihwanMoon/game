# frontend (Phase 3)

Vite + React + TypeScript. 파이썬 코어(`game/`)가 정본이고 여기는 그것을 이관·관전하는 층이다.

```bash
npm install
npm run dev        # 0.0.0.0:8090
npm run typecheck  # tsc --noEmit
npm run test       # vitest
npm run build      # tsc --noEmit && vite build
```

## 포트 8090

Cloudflare Tunnel 이 host:8090 으로 직접 들어오므로 개발 서버 포트는 8090 고정이고
`strictPort` 를 켰다. 다른 포트로 조용히 옮겨 가면 터널이 빈 포트를 가리키게 된다.

**지금 8090 은 배포 스택의 nginx 자리표시자(`game-frontend-1`)가 물고 있다.** 개발 서버를
띄우려면 먼저 그것을 내린다.

```bash
export COMPOSE_FILE=deploy/docker-compose.yml
docker compose stop frontend
```

## design/ 과 game/resources/ 를 참조하는 방법

둘 다 **복사하지 않는다**. `vite.config.ts` 의 별칭이 저장소 안의 원본을 직접 가리킨다.

| 별칭 | 가리키는 곳 | 쓰는 법 |
|:--|:--|:--|
| `@design` | `../design` | `import '@design/styles.css'` |
| `@resources` | `../game/resources` | `import blocks from '@resources/balance/blocks.json'` |

사본을 두지 않는 이유는 갈라짐이다. 밸런스 JSON 은 파이썬 코어가 읽는 것과 **같은 파일**
이어야 게이트 G3(두 코어 동일 결과)가 뜻을 갖는다. 토큰 CSS 도 이미 Claude Design
프로젝트의 사본이라(CLAUDE.md), 여기서 또 복사하면 정본에서 두 단계 떨어진다.

심볼릭 링크를 쓰지 않은 이유는 배포다 — Docker 빌드 컨텍스트와 git 체크아웃에서 링크가
깨지거나 대상 밖을 가리키면 조용히 다른 파일을 읽는다. 별칭은 빌드 시점에 해소되어
산출물에 값이 인라인되므로 런타임 경로 의존이 남지 않는다.

별칭이 프로젝트 루트 밖(상위 디렉터리)을 읽으므로 개발 서버에는 `server.fs.allow` 로
저장소 루트를 열어 뒀다. 저장소 밖은 열지 않는다.

## 격자·길찾기·시야 (W9)

`src/core/grid/geometry.ts` · `src/core/grid/vision.ts` · `src/core/pathfinding/distanceField.ts`
가 `game/app/grid/` 와 `game/app/pathfinding/` 의 이식이다. 파이썬과 디렉터리 경계를 맞췄다 —
거리장은 격자가 아니라 길찾기 계층이다.

여기서 결과를 가르는 것은 값이 아니라 **순서**다.

- `STEP_OFFSETS` 는 북·동·남·서. 같은 비용의 경로가 여럿일 때 이 순서가 한 걸음을 고른다.
  `src/core/schemas/room.ts` 에도 같은 이름의 상수가 있지만 그쪽은 도달성 검사용(북·남·서·동)
  이고 순서가 다르다. 파이썬도 두 상수를 따로 두고 있으므로 합치지 않는다.
- `NEIGHBOR_OFFSETS` 는 포위 판정용 8방향이다. 이동에 쓰지 않는다.
- LOS 는 정수 브레젠험이며 **늘 사전순 작은 좌표에서 긋는다**. 그래야 A→B 와 B→A 가 같은
  선을 쓴다. 부동소수 기울기를 들이면 그 자리에서 리플레이가 깨진다.
- 거리장의 `Map` 은 삽입 순서가 곧 BFS 방문 순서이고, 그것이 파이썬 dict 와 같아야 한다.
- 가시 좌표·엄폐 후보는 행 우선 `(y, x)` 로 내보낸다. 집합을 그대로 순회하지 않는다.

기준값은 파이썬에서 뽑아 `src/core/golden/grid_golden.json` 에 고정했고
`src/core/grid/grid.test.ts` 가 대조한다. 좌표 목록은 순서까지 비교한다. 재생성:

```bash
uv run python -m scripts.export_grid_golden
```

대조 대상은 룸 템플릿 5종과 가시덤불·파괴 가능 벽을 넣은 합성 격자 2종이다. 합성 격자를
두는 이유는 템플릿에 그 타일이 없어서다 — 가시덤불은 시야를 막지 않고 파괴 가능 벽은 막는데,
둘을 대조에 넣지 않으면 그 차이를 뒤집어도 테스트가 통과한다.

## 틱 엔진 7페이즈 (W9)

`src/core/sim/` 이 `game/app/simulation/` 의 이식이다. 곁들여 `src/core/eventLog.ts`(이벤트
로그) · `src/core/combat/damage.ts`(전투 수식) · `src/core/rules/fallbackPolicy.ts`(폴백
결정기) · `src/core/services/runBattle.ts`(전투 1회 조립·실행)도 함께 왔다 — 엔진이 그것들
없이는 한 틱도 돌지 않는다.

```
state.ts       Entity · WorldState. listActors() 가 이니셔티브 내림차순 · 동률 시 id 사전순
plan.ts        PlannedAction · EngineConfig · DecisionPolicy · PolicyFactory
phases.ts      페이즈 7개와 판정 4개의 이름
perception.ts  인지 스냅샷. 틱당 한 번 만들고 그 틱의 모든 결정이 공유한다
selectors.ts   타겟 셀렉터 7종
telegraph.ts   예고 등록·카운트다운·발동
abilities.ts   소환과 예고 등록 (종류 데이터가 정하는 능력)
actions.ts     행동 13개 전량 실행
pressure.ts    추격자 · 층 스케일 · 샘 잔여량 (GDD §7)
engine.ts      7페이즈 고정 순서
```

순서를 흔들면 조용히 틀리는 자리가 셋 있다.

- **PERCEPTION 과 DECIDE 는 분리돼 있다.** 모든 엔티티가 같은 시점의 세계를 보고 판단해야
  하므로 DECIDE 는 부작용을 내지 않고 계획만 돌려준다. 실제 변경은 ACT 부터다.
- **난수는 두 곳에서만 뽑는다** — UPKEEP 의 추격자 스폰 위치(`getChoice`)와 ACT 직전의
  이니셔티브 동률 가르기(계획 하나마다 `getUint64` 하나). 뽑는 지점이나 횟수가 파이썬과
  어긋나면 그 뒤의 모든 난수가 밀려 결과가 통째로 갈린다.
- **좌표를 집합·대응표의 열쇠로 쓸 때는 `formatPositionKey` 를 거친다.** 객체를 그대로
  `Set` 에 넣으면 동등성이 참조로 판정돼 같은 칸이 서로 다른 원소가 된다.

정수 나눗셈은 `divideFloor`(= 파이썬 `//`) 하나로 모았다. `/` 를 그대로 쓰면 HP 가 소수점을
갖고, 그 순간 두 코어가 갈린다.

기준 전투는 파이썬에서 뽑아 `src/core/golden/sim_golden.json` 에 고정했고
`src/core/sim/sim.test.ts` 가 **로그 전문까지 줄 단위로** 대조한다. 재생성:

```bash
uv run python -m scripts.export_sim_golden
```

기준은 정책 두 가지로 돌린다. `fallback` 은 실제 전투에 가깝지만 폴백 정책이 접근·공격·
포션·대기 넷만 내므로 나머지 행동 아홉 개가 실행되지 않는다. 그 빈자리를 메우는 것이
`cycle` — 틱과 엔티티 id 만 보고 행동 13개를 차례로 돌리는 **대조 전용** 결정기이며 파이썬
스크립트와 TS 테스트 양쪽에 같은 것이 하나씩 있다. 소환·예고·자폭·엄폐 이동·플래그가
거기서 검증된다. RuleVM 이 이식되면 규칙표 사례로 갈음한다.

## RuleVM · 검증기 · 셀렉터 (W9)

`src/core/rules/` 가 `game/app/rules/` 의 이식이다.

```
ruleVm.ts          규칙표를 읽어 매 틱 행동 하나를 고른다
validator.ts       규칙 에디터가 타이핑 도중 부르는 네 가지 검증 (TDD §5.1)
fallbackPolicy.ts  규칙표가 없을 때의 기본 결정기
selectors.ts       sim/selectors 를 이름만 다시 내보낸다 (아래 참조)
```

**셀렉터의 구현은 `src/core/sim/selectors.ts` 하나뿐이다.** 파이썬 정본이
`game/app/simulation/selectors.py` 라 이식도 같은 자리에 두었고, `sim/perception.ts` 가
셀렉터를 부르므로 구현을 `rules/` 로 옮기면 `sim → rules → sim` 순환이 생긴다.
`rules/selectors.ts` 는 규칙 모듈에서 부를 이름만 빌려주는 재수출이며, 그래서
`rules/index.ts` 는 셀렉터를 배럴에 넣지 않는다 — `sim` 배럴과 같은 이름이 두 곳에서
들어오면 어느 쪽인지 알 수 없게 된다.

평가 순서는 **셀렉터 → 조건 → 행동**이다. 조건의 `대상 HP%` 는 그 규칙의 TARGET 이
가리키는 적을 뜻하므로 순서를 뒤집으면 조건이 무엇을 재는지 정의되지 않는다. 셀렉터가
아무도 못 고르면 그 규칙은 **발동하지 않고 건너뛴다** — 없는 소환사를 공격하라는 규칙이
틱을 버리지 않게 하는 장치다.

조용히 틀리는 자리가 셋 있다.

- **불리언은 비교 직전에 0·1 로 접는다.** 파이썬의 `bool` 은 `int` 의 하위형이라
  `True == 1` 이 참인데 자바스크립트의 `===` 는 거짓이다. `COMPARATORS` 가 수만 받는
  이유가 이것이며, 양변을 접지 않으면 불리언 인지 변수를 쓴 규칙이 파이썬과 갈린다.
- **값이 없는 것과 값이 0 인 것은 다르다.** 아직 만들 수 없는 인지 변수와 읽을 수 없는
  스탯은 `undefined` 이고 그 항은 거짓으로 떨어진다. 0 으로 채우면 구현되지 않은 기능이
  동작하는 것처럼 보인다.
- **검증기의 위반 메시지는 순서까지 계약이다.** 에디터가 첫 줄을 띄우므로 순서가 바뀌면
  화면이 바뀐다. 인자를 고르지 않은 항을 파이썬이 `인자 None 는` 으로 적는 것까지 맞췄다 —
  `null` 로 적으면 같은 규칙표에 두 메시지가 생긴다.

조건 문자열에는 **양변의 실측값을 병기한다** — `적거리(2) <= 사거리(3)` (GDD §8.2).
이 문자열이 UI 의 `RuleRow.condition` 과 `LogRow.expr` 로 그대로 간다.

기준값은 파이썬에서 뽑아 `src/core/golden/rules_golden.json` 에 고정했고
`src/core/rules/rules.test.ts` 가 대조한다. 재생성:

```bash
uv run python -m scripts.export_rules_golden
```

세계는 서비스 계층을 거치지 않고 골든에 적힌 엔티티 배치로 양쪽이 직접 세운다. 셀렉터
7종이 서로 다른 답을 내도록 거리·HP·공격력의 **동점을 일부러 만들어 두었다** — 동점을
`entityId` 사전순으로 가르는 규약이 깨지면 같은 시드가 다른 전투를 만든다 (R5).

## 골든 리플레이 대조 — 게이트 G3

`src/core/goldenReplay.test.ts` 가 이 저장소의 **최종 관문**이다. 위의 골든들이 모듈
하나씩을 고정한다면 이것은 **완성된 전투 한 판**을 고정한다 — 실제 플레이와 같은 배선으로,
플레이어는 자기 규칙표(RuleVM)로, 적은 각자의 규칙표로, 소환물은 `EnemyPolicyFactory` 가
붙여 주는 규칙표로 싸운다.

기준은 `scripts/export_golden.py` 가 파이썬 코어에서 뽑아 둔 `src/core/__golden__/cases.json`
이다. 재생성:

```bash
uv run python -m scripts.export_golden
```

케이스는 25개다. 방 5개 × 대표 규칙표 3종(`g0_pressure`·`g0_kite`·`g0_cover`)에 방마다
다른 시드를 준 15개, 벤치마크 규칙표 5종을 태운 5개, 그리고 **템플릿에 없는 적을 덧붙인**
5개다. 마지막 묶음이 있는 이유는 방 다섯 개의 스폰이 전부 고블린 3종이라, 그것 없이는
폭탄 슬라임의 예고(TELEGRAPH 페이즈)·대소환사의 소환·수복사의 회복·장궁병의 사거리가
한 번도 돌지 않기 때문이다. 그 경로가 갈려도 대조가 통과하면 게이트가 없는 것과 같다.

대조하는 것은 세 가지다.

- **이벤트 로그 전문** — `tick·entity_id·phase·expr·outcome·rule·delta·fired·target_id`
  를 필드 단위로 본다. 포맷된 문자열이 아니라 필드로 비교하므로 서식을 고쳐도 대조가
  깨지지 않고, 어긋난 **필드**를 지목할 수 있다. 4,800줄이 걸린다.
- **승패·틱·플레이어 HP** — 판의 결말.
- **최종 개체 상태와 소환 카운터** — 좌표·HP·공격력·포션·쿨타임·플래그. 로그에 찍히지
  않는 상태까지 봐야 어긋난 지점이 좁혀진다.

어긋나면 `findFirstMismatch` 가 **최초 불일치 하나**만 메시지에 싣는다. 로그 수천 줄을
통째로 diff 로 뱉으면 어디서 갈렸는지 읽어 낼 수 없기 때문이다. 출력은 이런 모양이다.

```
로그 #50 (틱 6, goblin_rusher_1, DECIDE) 의 outcome 가 다르다 — TS="..." PY="..."
```

**어긋나면 TypeScript 가 틀린 것이다.** `cases.json` 을 손으로 고치지 않는다. 파이썬
코어가 정본이며, 저장된 리플레이·데일리 챌린지·헤드리스 밸런싱이 전부 그 값을 기준으로
한다 (TDD §12 R5).

### 주의점

- 조립 **순서가 계약이다**. 플레이어 규칙표를 먼저 걸고 `assignEnemyPolicies` 를 나중에
  부른다. 순서를 바꾸면 그 안의 `registerNewcomers` 가 플레이어 자리를 공장으로 먼저
  채워 규칙표가 조용히 덮인다. 덧붙일 적은 그다음이다.
- 덧붙인 적의 id 는 `{종류}_x{순번}` 이다. 템플릿 스폰의 `{종류}_{index}` 와 겹치면
  한 쪽이 조용히 덮인다.
- 이 대조는 `src/core/sim/sim.test.ts` 와 겹치지 않는다. 그쪽은 폴백·순환 정책으로 엔진의
  실행 경로를 고정하고(규칙표를 타지 않는다), 이쪽은 RuleVM 이 걸린 배선을 고정한다.
  RuleVM 이 규칙 하나를 다르게 평가하면 이쪽만 깨진다.
- 골든 디렉터리가 둘이다. 모듈별 골든은 `src/core/golden/`, 전투 케이스는
  `src/core/__golden__/` 다. 후자는 W10 과업이 지정한 경로다.

## 디자인 시스템 부품 (W10)

`src/ds/` 에 design/README.md 의 컴포넌트 계약 17종이 있다. **UI 는 여기서만 가져간다.**

```ts
import { Button, Panel, RuleRow, RuleTable, LogPanel } from '../ds'
```

### 배럴이 유일한 경계다

`src/ds/index.ts` 가 `ds.css` 를 함께 싣는다. 그래서 `from '../ds/Button'` 처럼 파일을
직접 찌르면 **스타일이 딸려오지 않는다.** 컴포넌트마다 CSS 를 import 해 두면 깊은 경로도
살지만, 그러면 배럴이 공개 경계라는 사실이 흐려진다. 경계를 하나로 두는 쪽을 골랐다.

토큰(`@design/styles.css`)은 컴포지션 루트가 싣는다 — `src/main.tsx` 와
`src/ds/galleryMain.tsx`. `ds.css` 는 토큰을 **쓰기만** 하고 정의하지 않는다.

### 하드코딩 금지가 테스트로 강제된다

`src/ds/ds.test.tsx` 의 "토큰 규율" 묶음이 `ds.css`·`gallery.css` 를 읽어 주석을 걷어낸
뒤 생 hex(`#1F2836`)와 생 px(`16px`)가 남아 있으면 실패시킨다. `box-shadow` 도 전부
`var(--shadow-none)` 인지 본다. 생 값은 리뷰에서 놓치기 쉽고 한 번 새면 화면마다 다른
값이 자라므로, 사람 눈이 아니라 테스트가 막는다.

### 부품 카탈로그 — `/ds.html`

`src/ds/gallery.tsx` 가 17종과 그 상태를 한 화면에 늘어놓는다. 특히 **RuleRow 의 여섯
상태**(기본 / 참·미발동 / 거짓 / 발동 / CPU 초과 / 포커스)는 여기서만 나란히 보이므로
규칙표를 고칠 때 이 페이지를 먼저 연다. 전투 화면 골격(56 / 320 / 가변 / 300 / 48)도
같은 페이지 위쪽에 있다.

진입점을 `index.html` 과 나눈 이유는 수명이다. 카탈로그는 부품을 **보는** 곳이고 제품
화면은 부품을 **쓰는** 곳이라, 한 파일을 두 목적이 나눠 쓰면 전투 화면 작업과 계속
충돌한다. `vite.config.ts` 의 `build.rollupOptions.input` 에 두 html 이 모두 적혀 있다.

### 황동 예산

`--brass` 계열을 쓰는 자리는 셋뿐이다 — `Button variant="primary"`, armed 상태
(`GlyphState state="armed"` 와 RuleRow 의 좌측 세로바), `PlanActor kind="self"`.
`:focus-visible` 외곽선도 황동이지만 한 번에 하나만 보이고 조작 중에만 나타나므로
예산에서 뺀다. **새 부품에 황동을 더하지 마라** — 예산은 부품 수가 아니라 화면 수라서,
부품이 하나 늘 때마다 전투 화면이 조용히 넘친다.

### 계약표와 갈리는 지점

design/README.md 의 표는 **표현 상태**만 열거한다. 아래 셋은 표현이 아니라 기능이라
더했고, 빼면 대체 수단이 더 나쁘다.

| 더한 것 | 왜 |
|:--|:--|
| `Button.onClick` · `children` · `title` | 핸들러가 없으면 소비자가 `<div onClick>` 으로 감싸 키보드 조작을 잃는다. `title` 은 글리프만 있는 버튼의 이름이다 |
| `Panel.meta` 가 노드도 받음 | 문자열로 좁히면 헤더에 작은 버튼이 필요한 화면이 Panel 을 버리고 헤더를 직접 짠다. 시스템 밖으로 내보내는 것보다 슬롯을 여는 편이 낫다 |
| `SegmentedGauge.readout` 이 문자열도 받음 | 규칙 에디터는 **누적** CPU 를 적는다. 눈금과 숫자의 출처가 다른 자리가 있다 |
| `RuleRow.cpu` 가 `{used, budget}` 도 받음 | 상태 05(CPU 초과)를 판정할 근거가 필요하다. state 열거(true·false·pending)는 조건 판정이라 예산 초과가 들어갈 자리가 아니다 |

### LogPanel 은 코어 로그를 변환 없이 받는다

`LogRowProps` 는 `src/core/eventLog.ts` 의 `LogEntry` 가 그대로 들어가도록 짜여 있다.

```tsx
<LogPanel entries={engine.log.entries} />
```

변환 계층을 두지 않은 이유는 코어가 필드를 늘릴 때 UI 가 조용히 옛 값을 그리기 때문이다.
`rule` 과 `delta` 는 `number | null` 이며 **null 을 0 으로 접지 마라** — 코어에서 "없음"
과 0 은 다른 답이다.

### 조건은 고르는 것이지 쓰는 것이 아니다

조건 한 줄이 `{인지변수} {비교} {값}` 세 개의 `select` 다. 블록 id 를 타이핑하게 하면
오타가 곧 위반 메시지가 되고, 사람은 자기 논리가 아니라 철자를 의심하며 시간을 쓴다.
고를 수 있는 것만 화면에 있으면 **틀린 규칙표는 만들 수 있어도 읽을 수 없는 규칙표는
만들 수 없다.**

인자를 받는 인지 변수(`쿨타임[스킬]`·`플래그[A~D]`·`적유형존재[유형]`·`대상거리[셀렉터]`·
`가장가까운목표거리[타일]`)는 인자 `select` 가 좌변 바로 옆에 함께 뜬다. 인자는 좌변의
일부이지 따로 붙는 옵션이 아니다.

우변은 리터럴과 자기 스탯 참조 둘 다 고를 수 있다 (F-2). bool 인지 변수는 비교를 `==`·`!=`
로 좁히고 우변을 참/거짓 `select` 로 바꾼다 — `내 상태이상 < 3` 같은 항을 만들 길을 없앤다.

**한 조작이 여러 값을 함께 옮기는 자리가 둘 있다.** 좌변을 바꾸면 인자와 우변이 새 블록
기준으로 함께 맞춰지고(`applyLhsChoice`), 행동을 바꾸면 TARGET 절이 함께 맞춰진다
(`applyActionChoice`). 이것을 빼면 사람이 고르지도 않은 값 때문에 뜬 위반 메시지를 읽게 된다.

### 키보드만으로 규칙 하나를 완성할 수 있다

전부 네이티브 `select`·`input` 이라 Tab 으로 순회된다. 구조 변경은 Alt 조합이며, 전부
입력칸 타이핑과 겹치지 않는다.

| 키 | 하는 일 |
|:--|:--|
| `Alt+↑` / `Alt+↓` | 규칙 순서 변경 (= 우선순위 변경) |
| `Alt+Enter` | 아래에 규칙 추가 |
| `Alt+D` | 규칙 복제 |
| `Alt+T` | 조건 항 추가 |
| `Alt+Backspace` / `Alt+Delete` | 규칙 삭제 |

조작 뒤에는 포커스가 대상 행으로 옮겨 간다(`focusIndex`). 그래서 `Alt+Enter` → Tab →
조건 고르기 → `Alt+Enter` 로 손이 키보드를 떠나지 않는다.

**행과 항의 React key 는 인덱스로 고정돼 있다.** `key` 에 `rule.action` 이나 `term.lhs`
같은 내용을 섞으면 행동·좌변을 바꾸는 순간 remount 되어 **포커스가 날아간다.** 키보드
흐름이 거기서 끊긴다.

### 순서가 곧 평가 순서다

리스트에서 위에 있는 줄이 먼저 평가된다(TDD §5.2). 순서를 바꾸는 길이 두 개다 — 좌측
손잡이(`≡`) 드래그, 그리고 `Alt+↑/↓`. 드래그만 두면 키보드로는 규칙표를 완성할 수 없다.

우선순위는 조작마다 **1..n 으로 다시 매긴다**(`renumberRules`). 번호에 구멍이 나면
검증기의 `[N]` 라벨과 화면의 행 번호가 어긋나 "몇 번 규칙이 틀렸다" 를 따라갈 수 없다.

CPU 비용도 항 수에서 다시 계산한다(1항=1 / 2항=2 / 3항=4). 사람이 손으로 맞출 값이 아니다.

### CPU 초과는 오류가 아니라 수치다

`SegmentedGauge(tone="cpu")` 가 예산선 너머까지 칸을 그리고, **누적 비용이 예산을 넘는
지점부터** 규칙 행의 좌측 세로바가 `--rust` 로 바뀐다. 어느 줄에서 넘겼는지가 얼마나
넘겼는지보다 쓸모 있다. 넘긴 상태에서도 편집은 그대로 계속된다 (GDD §3.6).

### 검증은 타이핑마다 부른다

`validateRuleSet` 은 순수 함수라 세계 상태를 건드리지 않는다. 메시지의 `[N]` 라벨을 떼어
**그 규칙 줄 아래**에 되붙인다(`buildProblemIndex`) — 위반 목록만 따로 있으면 어느 줄이
문제인지 사람이 다시 찾아야 한다 (P1). 우측 검증 패널에는 같은 목록을 순서 그대로 싣는다.

### 텍스트 뷰 — 프리셋 공유의 통로

```
# ruleset g0_pressure v1
[1] IF self_hp_percent < 25 AND self_potion_count > 0 THEN USE_POTION
[2] IF target_distance[NEAREST] <= 1 THEN ATTACK TARGET NEAREST SET A=true
[3] IF self_hp_percent < $hp_max THEN RETREAT TARGET NEAREST
```

- 우변의 `$이름` 이 자기 스탯 참조다. `사거리` 를 이름으로 쓰면 값 `3` 과 눈으로 구별되지
  않기 때문에 한 글자로 갈리는 표기를 골랐다.
- 머리글이 규칙표 id 와 세대를 나른다. 없으면 부르는 쪽의 기본값을 쓴다 — 규칙 줄만
  붙여넣어도 읽힌다.
- `#` 로 시작하는 줄과 빈 줄은 건너뛴다. 채팅에서 설명이 섞여 와도 읽힌다.
- 번호(`[N]`)는 생략할 수 있고 그때는 줄 순서로 매긴다.
- **읽히는 동안에만 규칙표에 반영한다.** 반쯤 쓴 줄이 규칙표를 덮으면 오타 하나에 규칙표
  전체를 잃는다. 오류는 줄 번호와 함께 그 자리에 적는다.

**왕복이 계약이다.** `parseRuleText(formatRuleText(x))` 는 `x` 와 같다. `src/editor/editor.test.ts`
가 `g0_examples`·`enemies`·`benchmark` 의 규칙표 전량을 왕복시킨다 — 손으로 만든 사례만
돌리면 실제 규칙표에만 있는 조합(스탯 우변·OR·SET 절·인자 있는 좌변)이 검증에서 빠진다.

왕복하지 **않는** 것이 하나 있다. `cpu_cost` 는 텍스트에 적지 않고 항 수에서 다시 계산한다.
자원 JSON 의 규칙표는 전부 그 관계를 지키므로 그대로 왕복한다. `op: SINGLE` 인데 항이
둘 이상인 규칙은 왕복하면 `AND` 가 된다 — RuleVM 이 `OR` 가 아닌 op 를 전부 AND 로 읽으므로
(`ruleVm.ts`) 뜻은 같다.

### 남은 것

- **되돌리기가 없다.** `Alt+Backspace` 로 지운 규칙은 돌아오지 않는다. `draft.ts` 가 전부
  순수 함수이므로 이전 규칙표를 스택에 쌓기만 하면 되는데, 그 스택을 둘 자리는 에디터가
  아니라 규칙표 상태를 들고 있는 쪽이다.
- 프리셋 8슬롯 저장(`game/schemas/meta_save.py`·`preset_code.py`)이 아직 화면에 없다.
  `formatRuleText` 의 결과를 `v2:` 공유 코드로 감싸는 자리가 그 지점이다.
- 해금 상태를 아직 넘기지 않는다. `validateRuleSet` 의 다섯째 인자가 `null`(전부 해금)로
  고정돼 있어, 팔레트가 아직 못 얻은 블록도 보여 준다 (GDD §6.2 모듈).

### 캔버스인데 토큰을 쓴다

`ctx.fillStyle` 은 문자열이라 그냥 짜면 생 hex 가 렌더러에 쌓이고, `design/` 을 다시
가져와도 도면만 옛 색으로 남는다. 그래서 그리기 직전에 `getComputedStyle` 로 커스텀
속성을 읽어 `PlanTheme` 을 만든다. **없는 토큰은 이름을 달고 던진다** — 빈 문자열을
`fillStyle` 에 넣으면 캔버스가 직전 색을 그대로 써서 원인을 알 수 없는 화면이 된다.

캔버스의 CSS 크기도 `calc(var(--plan-cell) * 12)` 로 준다. 백버퍼만 배율이 곱해진
화소 수다. 테스트가 둘 다 확인한다.

### 색은 정보의 유일한 채널이 아니다 — 꼴도 아니다

타일 열 종은 서로 다른 **꼴**을 갖는다. 벽은 45도 해칭 + 실선, 파괴 가능 벽은 같은 해칭을
성기게 + 점선, 엄폐물만 면을 채우고, 용암은 물결, 함정은 점선 사각형 안의 대각선, 계단은
평행한 단, 문은 여닫이 호, 샘은 동심원, 가시덤불은 작은 갈고리, 바닥은 점 하나다.
테스트가 열 종의 그리기 자취(좌표까지)를 비교해 겹치지 않는지 본다.

**적 유형 여덟 종이 `PlanActor.kind` 네 종에 접힌다** (design/README.md D-1). 그래서
글리프만으로는 구분되지 않으므로 글리프 아래에 두 글자 표기(`돌진`·`자폭`·`장궁` …)를
함께 그린다. 색 + 글리프 + 표기 세 채널이다. 접는 규칙은 `actorKind.ts` 에 적혀 있다.

### 예고 타일 — 관전의 긴장감 (GDD §4.2)

예고는 `--plan-hazard` 로 역방향 해칭을 깔고 **남은 틱 수를 칸에 적는다**. 여기에 채널이
하나 더 있다.

- 실선 테두리 — 플레이어의 인지 폭 안에 들어온 예고. 규칙표의 회피 조건이 참이 된다.
- 점선 테두리 — 아직 못 읽는 예고. 붉게 보이지만 인지 변수는 거짓이다.

둘을 같은 모양으로 그리면 "붉은데 왜 회피 규칙이 안 도는가" 를 설명할 길이 없다. 이
차이가 센서 모듈(GDD §6.2)이 파는 값이다.

방 다섯 개의 스폰은 전부 고블린 3종이라 **덧붙이지 않으면 예고가 한 번도 뜨지 않는다.**
확인용 페이지의 `정예 편성` 토글이 폭탄 슬라임·수복사·대소환사를 넣는 이유다.

### 움직임 — 틱 경계의 명도 전환뿐

말은 칸에서 칸으로 순간 이동한다. 보간하지 않는다. 관전자가 읽어야 하는 것은 궤적이
아니라 **어느 틱에 어느 칸에 있었는가** 이고, 도면이 흔들리면 눈이 좌표를 매번 다시
잡는다. 캔버스 내용은 전환할 수 없으므로 캔버스 **자체**에 140ms 등속 명도 전환을 건다
(`battle.css` 의 `battle-plan-swap`). `transform` 은 쓰지 않으며 테스트가 막는다.

### 배속 — 틱은 정수 단위로만 는다

`core/services/runSteppedBattle.ts` 가 파이썬 `run_stepped_battle.py` 의 이식이고,
일시정지 / 1x / 2x / 4x / 즉시가 전부 "한 번에 몇 틱" 하나로 환산된다. rAF 는 **언제**
한 배치를 돌릴지만 정하고, 몇 틱인지는 그 표가 답한다. 프레임에 비례해 진행을 나누면
기기의 주사율이 곧 게임 속도가 되고, 7페이즈 한 바퀴 중간에서 멈추면 DECIDE 가 고정한
스냅샷과 ACT 가 보는 세계가 갈린다 (TDD §4.1).

`Date.now` 를 쓰지 않는다. rAF 가 주는 타임스탬프만 본다 — 탭이 뒤로 갔다 돌아왔을 때
밀린 시간만큼 몰아서 돌지 않는 효과도 함께 얻는다.

배치 간격은 `--dur-tick` 의 두 배다. 전환이 끝나고 한 박자 쉰 뒤 다음 틱이 온다.

### 규칙 줄의 상태 셋을 화면이 어떻게 아는가

`TracingRuleVm` 이 `RuleVm` 을 감싸되 **계획은 안쪽 VM 이 낸 것을 그대로 돌려준다.**
줄의 상태는 그 계획의 `ruleIndex` 를 경계로 가른다.

| 우선순위 | 상태 | 조건문 |
|:--|:--|:--|
| 발동한 규칙보다 앞 | `false` | 실측값을 병기해 다시 평가한다 |
| 발동한 규칙 | `true` + armed | **코어가 만든 `expr` 그대로** |
| 발동한 규칙보다 뒤 | `pending` | 값 없이 이름만. 단축 평가로 보지 않았다 |

경계를 계획에서 얻으므로 화면과 로그가 어긋날 수 없다. 여기서 루프를 다시 짜면 언젠가 두
판정이 갈리고, 그때 플레이어는 규칙표와 로그 중 어느 쪽을 믿어야 할지 알 수 없다.

셀렉터가 아무도 고르지 못한 규칙은 VM 이 조건을 보지도 않고 건너뛴다(F-1). 그 줄에는
`— 대상 없음` 을 붙인다. 적지 않으면 플레이어가 조건식을 의심하며 시간을 버린다.

조건 평가(`evaluateCondition`·`resolveTarget`)는 순수 함수이고 난수를 쓰지 않는다.
**그래서 추적기를 끼워도 난수 소비 순서가 바뀌지 않는다.** 테스트가 추적기를 끼운 판과
끼우지 않은 판의 로그를 필드 단위로 통째 비교한다 — 화면을 켜도 판이 달라지지 않는다 (R5).

### 황동 예산 셋

1. 도면 위 플레이어 말 (`--plan-actor-self`)
2. 발동한 규칙 줄의 좌측 세로바 (ds `RuleRow armed`)
3. 그 줄에서 말로 잇는 지시선과 고리 (`--line-accent`)

그래서 상단의 `즉시`·`다시` 는 `primary` 를 쓰지 않는다. 테스트가 `ds-button--primary` 가
화면에 없는지 본다.

### 남은 것

- 방 크기가 12x9 로 고정이다 (design/README.md D-2). 렌더러는 `room.width/height` 를
  그대로 쓰므로 더 큰 방도 그리지만, 기준 해상도의 가운데 열이 818px 이라 16x12 부터는
  넘친다. 셀 가변으로 갈지 방 상한을 12x9 로 내릴지는 디자인 결정이다.
- `PlanActor.kind` 가 네 종이라 자폭형·치유형이 다른 유형의 글리프를 빌려 쓴다. Phase 4
  에서 열거를 넓힐 때 `actorKind.ts` 의 표를 지우고 글리프를 새로 정하면 된다.
- 규칙표 열이 **읽기 전용**이다. 줄을 눌러 에디터로 가는 길(`RuleRow.onClick`)이 아직
  비어 있다.

## HUD — 관전과 진단, 사후 분석 (W13)

오토배틀은 플레이어 입력 공백 시간이 길다. 그 시간을 **관찰과 진단**으로 채우지 못하면
게임이 지루해진다 (GDD §8). `src/hud/` 는 그 시간을 채우는 계층이다 — 틱으로 묶인 로그,
되감기, 그리고 사망하면 저절로 뜨는 사후 분석.

`/hud.html` 이 확인용 페이지다. 파이썬 기준 문서와 **같은 여섯 조합**을 돌리며, 화면에서
이상해 보이는 것을 그대로 대조 테스트로 옮길 수 있다.

### `src/battle` 과의 경계는 시간이다

두 디렉터리가 같은 화면을 두 벌 그리는 것이 아니다. 경계는 **시간축**이다.

| | `src/battle` | `src/hud` |
|:--|:--|:--|
| 무엇을 하는가 | 엔진을 앞으로 민다 | 끝난 판을 앞뒤로 걷는다 |
| 규칙표 상태 | `TracingRuleVm` 이 이번 틱을 다시 평가 | 그 틱의 DECIDE 로그 한 줄로 복원 |
| 되감기 | 없다 (엔진은 앞으로만 간다) | 프레임 배열의 첨자를 옮긴다 |

판 조립(`buildBattleSession`)·도면 렌더러(`PlanCanvas`·`buildPlanScene`)·규칙표 문구
(`formatPendingCondition`·`formatActionText`)는 **battle 것을 그대로 쓴다.** 여기서 다시
만들면 같은 시드가 두 화면에서 다른 판을 그리게 되고, 그때 어느 화면을 믿어야 할지 알 수
없다. hud 가 더하는 것은 "지나간 틱을 다시 볼 수 있게 남긴다" 하나뿐이다.

### 파일

| 파일 | 하는 일 |
|:--|:--|
| `analysis.ts` | 규칙별 발동 횟수·피격 좌표·피해 히트맵. **계산만 한다** |
| `analysisText.ts` | 진단 문구·틱 표기·강도 단계. **표현만 한다** |
| `battleRecorder.ts` | 판을 한 번 돌리며 틱마다의 프레임과 피격 좌표를 적는다 |
| `logWindow.ts` | 로그 창 고르기·틱 묶기·직전 15틱 |
| `replayTrace.ts` | 지나간 틱의 규칙표 상태를 로그 한 줄로 되짚는다 |
| `LogStream.tsx` | 우 300px 로그 열 |
| `PostMortem.tsx` | 사후 분석 — 성적표·히트맵·되감기 |
| `RuleStatsTable.tsx` `DamageHeatmap.tsx` `TickScrubber.tsx` | 사후 분석의 부품 |
| `HudScreen.tsx` `HudCheck.tsx` | 화면 골격과 확인용 페이지 |

### 왜 미리 다 돌려 두는가

되감기 때문이다. 엔진은 앞으로만 가므로 슬라이더를 뒤로 밀 방법이 없고, 그때마다 처음부터
다시 돌리면 화면이 멈춘다. `recordBattle` 은 판을 한 번 끝까지 돌리며 틱마다
`RecordedFrame`(도면 장면·로그 구간·HP·물약·예고)을 쌓아 두고, 재생·되감기는 그 배열의
첨자를 옮기는 것으로 끝낸다. **결정론이 UI 에서 값을 하는 지점이다** — 미리 돌린 판과 다시
돌린 판이 같다는 보장이 없으면 이 구조가 성립하지 않는다 (R5).

피격 좌표를 함께 적는 것은 파이썬 `replay_battle.BattleRecorder` 와 같은 이유다. 로그는
"누가 얼마를 맞았는가" 까지만 남기고 "어디에서" 는 그 틱의 세계 상태에만 있다. 틱 전후의
좌표표를 그때 같이 읽어 두지 않으면 나중에 복원할 수 없다.

### 집계와 표현을 나눈 이유

`analysis.ts` 는 문자열을 한 줄도 만들지 않고, `analysisText.ts` 는 수를 만들지 않는다.
파이썬도 같은 경계를 둔다(`build_rule_stats` / `format_rule_stats`). 섞어 두면 문구를 다듬을
때마다 대조가 깨지고, 그러면 아무도 문구를 다듬지 않게 된다.

### 파이썬과 같은 값을 내는지 대조한다

기준은 `src/hud/__golden__/analysis.json` 이고 파이썬이 만든다.

```bash
uv run python -m scripts.export_analysis_golden   # 또는 python3 -m ...
```

**손으로 고치지 마라 — 값이 어긋나면 TS 쪽이 틀린 것이다.**

대조 방식이 골든 리플레이와 다르다. 로그 파일을 비교하는 것이 아니라 **같은 조합을 TS 로
다시 돌린 뒤 그 로그로 집계**해 파이썬의 집계와 맞춘다. 그래서 한 번에 둘이 걸린다 — 전투가
갈렸는지, 집계가 갈렸는지. 실패 메시지의 순서(승패 → 틱 → 로그 수 → 피격 → 집계)가 곧
좁혀 가는 순서다.

여섯 조합은 집계가 갈리는 지점이 서로 다르다. `hazard_field` 는 용암 피해가 UPKEEP 에 나므로
"틱 **시작** 좌표에서 맞았다" 는 규칙(`PRE_MOVE_PHASES`)을 태우고, 폭탄 슬라임을 덧붙인
조합은 TELEGRAPH 발동 피해를, 대소환사를 덧붙인 조합은 전투 도중 등장한 개체의 피격 좌표를
태운다. **조합을 줄일 거면 뒤 둘부터 줄이지 마라.**

`scripts/__init__.py` 가 생긴 것도 이 대조 때문이다. `export_analysis_golden` 이
`export_golden` 의 전투 조립을 그대로 쓰는데, 패키지가 아니면 같은 파일이 두 이름으로 잡혀
mypy 가 막는다.

### 로그는 가상 스크롤이 아니라 윈도잉이다

픽셀을 재는 가상 스크롤을 쓰지 않았다. 화면 높이를 재려면 행 높이를 스크립트가 알아야 하는데
그 값은 토큰(`--log-row-h`)에 있고, 토큰을 스크립트에 다시 적는 순간 디자인 시스템의 정본이
둘이 된다. `selectLogWindow` 는 **줄 수**로 자르고 잘린 쪽의 수를 화면에 적는다 —
`앞의 25줄 접힘`. 숨기면 로그가 거짓말을 한다.

로그는 틱으로 묶고, 틱 안에서는 같은 엔티티의 연속 구간으로 다시 묶는다. `LogRow` 계약에
엔티티 칸이 없어서(tick·rule·expr·outcome·delta·fired) 구간 머리에 한 번 적는 것이다.
그렇게 하면 모노 컬럼이 흐트러지지 않으면서 누구의 판단인지가 남는다.

**로그는 현재 프레임까지만 보여 준다.** 앞선 틱의 줄이 보이면 관전자가 미래를 보고 판단하게
되어 "지금 이 규칙이 왜 이렇게 결정했는가" 를 되짚는 훈련이 되지 않는다.

### 황동 예산 셋

1. 발동한 규칙 줄의 좌측 세로바 (ds `RuleRow armed`)
2. 도면 위 플레이어 말 (ds `PlanActor kind="self"`)
3. **지금 보고 있는 틱**의 발동 로그 세로바 (`.hud-log__row--armed`)

"발동한 줄을 황동으로" 를 이번 틱으로 한정한 이유가 3번이다. 규칙이 발동한 줄은 한 판에
수백 개라 전부 칠하면 예산이 무의미해지고 광원이 여러 개인 화면이 된다. 지난 틱의 발동은
명도 한 단(`--line-strong`)으로 남는다. 되감기 슬라이더 손잡이에 황동을 쓰지 않은 것도
같은 이유다. 테스트가 `hud.css` 의 황동 참조가 정확히 한 자리인지 센다.

### 남은 것

- 사후 분석이 **방 하나**만 본다. 연쇄(층)를 다 담으려면 파이썬 `run_chain` 에 대응하는
  기록이 필요하다.
- `HudScreen` 의 규칙표 열도 읽기 전용이다. 줄을 눌러 에디터로 가는 길이 비어 있다.
- 사후 분석의 성적표가 플레이어만 본다. 적 규칙표의 성적은 `buildRuleStats(entries, id)` 로
  이미 나오므로 도감(Phase 2 W5)이 그대로 쓸 수 있다.

## W13 — 앱 조립과 배포 배선 (M3)

`src/App.tsx` 가 지금까지 나온 계층을 한 바퀴로 잇는다. **M3 의 정의는 "JSON 없이 플레이
가능" 이며, 그 정의를 만족시키는 것은 화면 하나가 아니라 흐름이다.**

```
규칙 에디터 ──[출격]──▶ 전투 관전 ──[사망/시간초과]──▶ 사후 분석
     ▲                                                    │
     └──────────────────[규칙 고치기]──────────────────────┘
```

### 상태는 App 하나가 든다

규칙표 · 방 · 시드 · 진행 중인 판이 전부 `App` 의 상태다. 에디터도 전투 화면도 사본을
만들지 않는다 — 어느 한쪽이 사본을 들면 고친 규칙이 전투에 반영되지 않거나 그 반대가
되고, 그 순간 이 게임의 유일한 동사("고쳐서 다시 도전한다")가 끊긴다.

- **판은 `RunSpec` 하나가 특정한다.** 출격을 누른 순간의 방·시드·규칙표를 얼려서 들고,
  전투 중에는 그 값이 흔들리지 않는다. 도는 판의 입력이 도중에 바뀌면 같은 시드가 같은
  결과를 내지 않는다 (R5).
- **`RuleEditor` 와 `BattleView` 에 `controls` 슬롯을 쓴다.** 두 화면의 상단 바 오른쪽에
  앱이 조작부를 끼운다. 에디터가 "출격" 을 직접 알 필요는 없다 — 규칙표를 어디로
  내보내는지는 에디터의 일이 아니다.
- `BattleView` 에 `onOutcome` 을 더했다. 판정이 바뀔 때만 부르므로 관전 중에 앱이 매 틱
  다시 그려지지 않는다.

### 출격은 막고, 편집은 막지 않는다

`validateRuleSet` 이 한 줄이라도 내면 출격 버튼이 잠기고 **첫 번째 위반이 그대로 버튼
툴팁에 적힌다.** 편집을 막지 않는다는 규칙(GDD §3.6)은 그대로다 — 막는 것은 내보내기다.
목록에 없는 블록이나 예산을 넘긴 규칙표를 그대로 던지면 엔진이 도중에 죽거나 규칙이
조용히 무시되고, 플레이어는 자기 논리를 의심하게 된다 (P1).

렌더 중에 터지는 경우를 위해 `ErrorBoundary` 가 전투 화면을 감싼다. 흰 화면 대신 사유와
에디터로 돌아가는 문을 남긴다.

### 사후 분석은 판을 한 번 더 돌려 만든다

`BattleView` 는 엔진을 앞으로만 밀어 지나간 틱의 화면을 남기지 않는데, 되감기와 히트맵은
틱마다의 좌표가 있어야 한다. 그래서 판이 끝나면 같은 `setup` 으로 `recordBattle` 을 한 번
더 돌려 `BattleRecording` 을 만들고 `PostMortem` 에 넘긴다. **두 번째 실행은 다른 판이
아니라 첫 번째의 재현이다** — 결정론이 보장하는 것이 정확히 이것이고, `src/app.test.tsx`
가 "4배속으로 몰아 돌린 판" 과 "한 틱씩 돌린 기록" 의 로그가 줄 단위로 같음을 확인한다.
400틱 상한이라 즉시 끝난다.

저절로 뜨는 것은 **이기지 못했을 때**다. 이긴 판까지 덮으면 사후 분석이 성적표가 아니라
방해물이 된다. 이긴 판은 상단의 `사후 분석` 버튼으로 연다.

### 실제 브라우저에서 잡은 것 두 가지

정적 렌더 테스트가 덮지 못하는 자리라 헤드리스 크롬(CDP)으로 눌러 보며 확인했다.

1. **`--dur-tick` 이 `.14s` 로 계산돼 배속이 무의미했다.** 토큰 파일에는 `140ms` 라고
   적혀 있지만 크롬의 `getComputedStyle` 은 정규화한 `.14s` 를 돌려준다. `parseFloat` 만
   쓰던 `readBatchIntervalMs` 가 0.14 를 밀리초로 읽어 간격이 0.28ms 가 됐고, 시계가 매
   프레임 한 틱씩 돌아 35틱짜리 판이 1초 만에 끝났다. `parseDurationMs` 가 단위를 본다.
   가짜 토큰을 쓰는 단위 테스트는 `140ms` 를 그대로 돌려주므로 이 자리를 볼 수 없다.
2. **사후 분석이 가로로 넘쳤다.** `hud-post__body` 가 `1fr 2fr` 이라 리플레이 로그 열이
   123px 로 눌렸다(내용은 176px 필요). 도면이 768px 로 고정이므로(design/README.md D-2)
   남는 폭이 곧 로그 폭이다. 왼쪽을 `--col-rules`(320px)로 고정해 로그에 262px 를 준다.

### 배포

`deploy/Dockerfile.frontend` + `deploy/nginx/frontend.conf`. 왜 프로덕션 빌드인지,
개발할 때 무엇을 내려야 하는지는 `deploy/README.md` 의 "프런트엔드 이미지" 절에 있다.

### 남은 것

- **층 진행이 없다.** 방 하나를 골라 돌리는 것까지다. 상단 표기가 `1층` 으로 고정인 것도
  그래서다. 연쇄는 파이썬 `run_chain` 에 대응하는 이식이 필요하다.
- 전투 화면의 규칙 줄을 눌러 에디터의 그 줄로 가는 길이 아직 없다(`RuleRow.onClick` 이
  비어 있다).

## 저장 · 프리셋 · 공유 코드 (M3)

`src/storage/` 와 `src/session.ts` 다. **짠 것이 탭을 닫는 순간 사라지면 "JSON 없이 플레이
가능" 이라는 M3 의 정의를 만족하지 못한다.**

```
storage/base64.ts        urlsafe base64. btoa/atob 를 쓰지 않는다(latin1 왕복이 낀다)
storage/deflateCodes.ts  DEFLATE 고정 표 — 굽는 쪽과 푸는 쪽이 한 파일을 본다
storage/inflate.ts       DEFLATE 풀기. 저장·고정·동적 블록 셋 다 받는다
storage/deflate.ts       DEFLATE 굽기. 고정 허프만 + 탐욕 LZ77
storage/gzip.ts          gzip 컨테이너(RFC 1952) + CRC32
storage/canonicalJson.ts 키를 정렬해 좁게 찍는 JSON — 파이썬 json.dumps 와 같은 글자
storage/presetPayload.ts 규칙표·프리셋 ↔ JSON 절 (game/schemas/meta_save.py 이식)
storage/presetCode.ts    `v2:` 공유 코드 (game/schemas/preset_code.py 이식)
storage/editorSave.ts    `v1` 로컬 저장 형식. 첫 필드가 형식 태그다 (TDD §9)
storage/saveStore.ts     Storage 접근과 디바운스 저장
editor/history.ts        되돌리기 스택. 규칙표 한 벌을 통째로 쌓는다
session.ts               세션 하나 = 저장 한 벌. 전이는 전부 순수 함수
```

### 저장 형식에 버전 접두어를 두는 이유

`{"format":"v1", ...}` 이고, 공유 코드는 `v2:` 로 시작한다. 태그를 **본문을 풀기 전에**
읽어 마이그레이션을 판정한다 (TDD §9). 풀어 보고서야 세대를 알면, 형식이 바뀐 값은 풀이
자체가 예외로 끝나 판정할 기회가 없다. 이 코어보다 새 세대는 거부한다 — 모르는 필드를
무시하고 다시 저장하면 그 필드가 사라져, 최신 탭에서 만든 프리셋이 옛 탭을 한 번 열었다는
이유로 없어진다.

읽기 실패는 **저장이 없는 것과 같이** 다룬다. 깨진 값 하나로 화면이 안 뜨면 사람은 저장이
아니라 게임을 잃는다.

### 공유 코드는 파이썬과 같은 형식이다 — 압축 바이트까지는 아니다

`v2:` + gzip(정렬 JSON) + urlsafe base64. gzip 머리의 mtime 은 0 으로 박는다 — 시각이
들어가면 같은 규칙표가 1초 뒤에 다른 코드가 되어, 코드 비교로 규칙표 비교를 대신할 수
없다 (R5).

zlib 의 탐색 방식(lazy 매칭·블록 분할·트리 생성)까지 옮기지는 않았다. 옮긴 사본은 원본이
한 번 바뀌면 조용히 갈라진다. **지켜야 하는 것은 바이트가 같은 것이 아니라 형식이 같은
것이다** — 한쪽이 구운 것을 다른 쪽이 푼다. 그래서 검사가 양방향으로 둘이다.

| 방향 | 기준 파일 | 검사 |
|:--|:--|:--|
| 파이썬 → TS | `src/storage/__golden__/preset_code.json` | `src/storage/presetCode.test.ts` |
| TS → 파이썬 | `src/storage/__golden__/ts_preset_code.json` | `tests/test_preset_code_interop.py` |

파이썬 쪽 기준은 `uv run python -m scripts.export_preset_code_golden` 으로 다시 만든다.
TS 쪽 기준은 압축 구현을 바꿨을 때만 다시 만든다.

```bash
UPDATE_TS_PRESET_GOLDEN=1 npx vitest run src/storage/presetCode.test.ts
uv run pytest tests/test_preset_code_interop.py   # 파이썬이 그것을 푸는지 확인
```

절(payload)을 정렬해 찍은 글자까지 파이썬과 대조한다. 압축 이전 단계가 어긋나면 거기서
먼저 드러나고, gzip 바이트를 비교하는 것보다 어긋난 자리를 짚기 쉽다.

### 되돌리기는 규칙표만 되돌린다

`draft.ts` 가 전부 순수 함수라 편집 결과가 새 규칙표 하나로 나온다. 스택은 그것을 통째로
쌓기만 한다(`editor/history.ts`, 상한 50). 방·시드·직전 판 결과는 편집이 아니라 판의
조건이므로 되돌리기 대상이 아니다 — `Ctrl+Z` 로 시드가 되돌아가면 사람은 자기가 무엇을
되돌렸는지 알 수 없다.

`Ctrl+Z` / `Ctrl+Shift+Z` / `Ctrl+Y` 를 모두 받는다. 관례가 플랫폼마다 갈리므로 어느 쪽을
눌러도 되게 두는 편이 낫다. 전투 화면에서는 듣지 않는다 — 도는 판의 입력은 되돌릴 수 없다.

### 저장 시점

편집이 있을 때마다 예약하고 400ms 디바운스한다. 숫자 칸에 `12` 를 치면 저장이 두 번 도는데
그 사이 값(`1`)은 아무도 필요로 하지 않는다. 탭을 닫거나(`pagehide`) 화면을 떠날 때는
예약을 버리지 않고 즉시 쓴다 — 마지막 편집이 400ms 안에 있었다는 이유로 사라지면 저장이
없는 것과 같다.


## 브라우저 e2e (Playwright)

jsdom 렌더 테스트가 못 보는 것을 본다. 마크업이 맞는 것과 **플레이되는 것**은 다른
사실이고, 이 층을 붙이기 전까지 후자는 한 번도 확인된 적이 없었다.

```bash
cd frontend
npm i -D @playwright/test                    # 최초 1회
npx playwright install --with-deps chromium  # 최초 1회 (브라우저는 ~/.cache 에 받는다)
npm run e2e            # 개발 서버를 알아서 띄운다 (127.0.0.1:5199)
npm run typecheck:e2e  # e2e 는 tsconfig 의 include 밖이라 따로 본다
```

**포트가 5199 인 이유**는 8090 을 배포 컨테이너(`game-frontend-1`)가 잡고 있고 Cloudflare
Tunnel 이 거기로 직접 들어오기 때문이다. e2e 를 돌리려고 그것을 내리면 그동안
`stock.nullmovie.com` 이 죽는다. `playwright.config.ts` 의 `reuseExistingServer` 가 이미 떠
있는 개발 서버를 그대로 쓴다.

| 파일 | 보는 것 |
|:--|:--|
| `e2e/coreLoop.spec.ts` | 규칙 추가 → 인자칸 → CPU 초과 → 출격 → 로그 실측값 → 사후 분석 → 재도전, 키보드 단축키 |
| `e2e/authoring.spec.ts` | G3 관문 — 빈 판에서 카이팅 규칙표를 짜고 그것으로 `corridor` 를 이긴다 |
| `e2e/persistence.spec.ts` | 새로고침 뒤 규칙표·방·시드, 프리셋 슬롯, 공유 코드 왕복 |
| `e2e/viewport.spec.ts` | 1280×720 에서 무엇이 먼저 눌리는지의 실측 기록 |

스크린샷은 `e2e/screenshots/` 에 덮어쓰기로 남는다. **커밋한다** — 화면이 그때 어떻게
보였는지가 검증 기록의 일부다.

세 시나리오 모두 **콘솔 에러·페이지 예외·실패한 요청을 수집해 끝에서 0 인지 본다**
(`e2e/fixtures.ts`). 이 단언이 `hud/LogStream.tsx` 의 중복 key 결함을 잡았다 — 한 틱 안에
같은 개체가 결정·행동 두 번 등장하는데 key 가 `틱-개체` 여서 React 가 줄을 겹쳤다.
**프로덕션 빌드에서는 그 경고가 지워지므로** 개발 서버로 도는 이 층이 아니면 드러나지
않는다.


## 화면은 다섯이다

`/` 가 제품 화면이고, `/admin.html` 이 관리 화면이다. 나머지 셋(`/ds.html`·`/battle.html`·
`/hud.html`)은 부품·렌더러·되감기 확인용이다.

**관리 화면을 갈라 둔 이유는 폭이다.** 표와 격자가 폭을 다 써야 하는데, 서랍 탭에 있을
때는 좁은 열이라 게임 UI 와 공간을 다퉜다.

경로의 존재는 드러나지만 데이터는 안 드러난다 — 관리 API 는 여전히 404 로 답하고, 이
페이지는 관리자가 아니면 "여기엔 아무것도 없다" 만 말한다. `noindex` 를 걸어 색인에서도
뺀다.

## 콘텐츠 팩 (설계/4_아이템 §18)

브라우저는 시작할 때 `/api/content/pack` 을 받아 그것으로 돈다. **못 받으면 번들에 박힌
것으로 돈다** — 그것이 "서버가 없어도 게임은 돈다" 를 지키는 자리이고, 그때는 팩 세대가
0 이라 코어 버전이 다르며 그 판은 로컬 티켓이라 제출되지 않는다.

**받은 팩도 코어의 로더로 읽는다.** 서버가 보낸 것을 그냥 믿으면 깨진 절 하나가 화면을
통째로 죽인다. 못 읽으면 번들로 떨어진다 — 콘텐츠 하나 잘못 발행했다고 아무도 못
들어오는 상태가 되면 안 된다.

갈아 끼우는 것은 **렌더 전에 한 번**이다. 도는 중에 바꾸면 같은 판이 중간에 다른
데이터로 돌고, 그것이 R5 가 막으려는 것이다.

골든과 검사는 **번들을 본다.** G3 가 대조하는 것은 파일이고, 팩은 그 위에 얹히는 것이다.
